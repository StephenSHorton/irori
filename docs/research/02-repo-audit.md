# Repo audit: what folds into Irori (2026-10-25)

What each existing StephenSHorton repo actually does today, and how it relates to Irori. Produced by reading the code, not the READMEs.

## tsukumo — `fold-in`

**What it does:** Bun/TS, v0.5.1 (mod v0.9.0), last commit 2026-10-16. Two halves: (1) src/mcp.ts, a stdio MCP server for any client that reads and posts in Discord, plus bind/get_mentions for Grok, which wakes only when run as `grok-fork --channels` via `notifications/claude/channel`; (2) claude-mod/, a Claude Code mod loaded with CLAUDE_CODE_PLUGIN_DIRS. It is still loaded on this Mac. hooks/register.tsx (1347 lines) wakes a session by calling `$.prompt.submit` with a fenced <discord-message> prompt. It also uses $.tool.register, $.ui.toast/open/status, $.store, $.process.spawn and $.command.register (/discord). The brains are in src/router/core.ts (894 lines) and src/lib/route.ts, take.ts, sweep.ts, ledger.ts, refs.ts and prmeta.ts. A mention is routed by an authorship ledger, in order: the chat that posted the replied-to message, then the thread claimer, then the PR owner (from gh pr create/review commands and PR refs such as owner/repo#N, aliases or a bare #N), then the 'front desk'. A per-message take lock means exactly one chat wakes. Engaged and defer states, a 10-minute sweeper that reassigns stalled new work, a 3-minute gone-detection, a 90-second hand-off timeout, 30s/90s claim heartbeats, block/allow lists and held mentions are all handled. One shared router process (unix socket .watch/router.sock) is started on demand and exits 30 minutes after the last chat leaves. The latest commit a5220f4 added `message_chat` and `list_chats`: chat-to-chat direct messages through the router that skip Discord, rate-limited to 8 per pair per 10 minutes so agents can't loop, and logged to .watch/direct.jsonl. That is the first transport that does not use Discord.

**What to take:** Port the transport-agnostic routing core: src/router/core.ts (the RouterEvent union: mention/direct/moved/handoff/overdue/claims), src/lib/route.ts (routeMention, frontDesk), take.ts (per-message take lock, defer), sweep.ts (planSweep/planReminders), ledger.ts + refs.ts + prmeta.ts (authorship ledger, PR ref parsing, Cursor-agent PR detection), and the direct-message anti-loop rate limit. Keep the test suites (router/core.test.ts, route.test.ts, sweep.test.ts, ledger.test.ts) as the behavioral spec. Keep the claude-mod as the hub's Claude Code adapter, but swap its source: instead of attach.ts->Discord router it attaches to the hub daemon; keep $.prompt.submit wake, fenced untrusted-content prompts, block/allow + held queue, pane UI concept. Keep the 'router started on demand, dies when idle, catches up from last-seen cursor' lifecycle idea. Drop: src/discord/*, discord.js, gateway login budget logic, Discord-specific 👀/typing, tsukumo-archive.

**Why:** These are the 'wake the right session' brains the hub needs, and they are already separate from Discord: core.ts is tested without Discord, and message_chat proves the router can carry agent-to-agent traffic itself. Discord is only the input source and the UI. The hub's own channels/threads replace it, and the ledger/route/take/sweep logic carries over unchanged. Overlap to note: Claude Code's native local peer messaging (~/.claude/sessions/<pid>.json has messagingSocketPath /tmp/cc-socks/<pid>.sock, peerProtocol 1, peerFeatures notify_idle/reply_across_default_dirs) already does Claude-to-Claude wake on one machine. message_chat duplicates that locally. The hub's value is cross-machine, cross-agent (Grok/rock) and durable.

## suzuri — `fold-in`

IMPORTANT: the cross-machine workspace sync (Share/Join ticket, the suzuri-workspace-sync Rust crate with merge.rs/proto.rs/sync.rs/events.rs, and chrome/src/workspace_sync.rs) lives only on the non-main branches origin/archive/glass-chrome and feat/workspace-mcp-channels (commits c8e2691 on 2026-08-13 and 9bdd319). main, the 'classic' line from a0861f0, kept the Go wrapper internal/workspacesync, which shells out to a sidecar that main no longer builds, while docs/workspace.md still advertises Share/Join.

**What to take:** Take: (1) internal/workspace data model + semantics (channels/messages.jsonl, members w/ kind+availability+session_id identity rules incl. engine/engine-2 de-dup, tasks w/ exclusive claim, path leases w/ TTL, inbox/wait) as the seed of the hub's store schema; (2) internal/mcpsrv tool surface + workspace_guide 'paste-ready agent instructions' idea + notify.go channel push to grok; (3) libs/transfer hato-core/hato-code/hato-mailbox for device pairing (ticket/short-code handshake) and iroh transport between Mac and Windows; (4) recover workspace-sync merge/proto/sync logic (append-only jsonl with id dedup, v0 frames, two-root converge tests) from origin/archive/glass-chrome as the starting point of hub replication; (5) aicontrol's agent-state reporting (idle/busy/blocked per pane) + env-var discovery pattern; (6) internal/update darwin heal/resign lessons and the macOS signing/notarization half of release.yml (toru has only Windows). Suzuri the terminal itself stays its own product but becomes a hub client (panes report agent state to the hub; workspace modal becomes a hub view).

**Why:** Suzuri's workspace is the closest existing thing to the hub, built for this purpose: humans and agents in one room, presence, tasks, leases, and wake through MCP channel notifications. It also has the only cross-platform signed release and updater pipeline and the iroh P2P engine. Its own KB entry ('P2P conversation pairing after transfer handshake') says not to rebuild iroh pairing from scratch. The hub should pull the workspace and transfer out of the terminal so they don't stay stranded inside it, and suzuri should consume the hub.

## toru — `reuse-code-only`

**What it does:** Windows-only screenshot and screen-recording app (Wails v3 alpha.98 + Go + React 19 + shadcn 'new-york' (Radix) + Tailwind 4). Go packages: capture, shot, vid, replay (background footage that keeps the last N), overlay, hotkey, toast, export, history, upload, share and transfer. transfer uses psanford/wormhole-william magic-wormhole codes for 'Send Files'. internal/update/service.go is the updater. **What to take:** internal/update/service.go wholesale (phase machine idle→checking→downloading→ready→installing, SHA256SUMS verify, InstallOnExit, tray hook), frontend/src/updater/* (banner + hook), build/windows NSIS config and Taskfile, release.yml Windows job, tray.go and autostart_repair_windows.go patterns, settings_service.go Wails-service shape. Combine with suzuri's macOS sign/notarize + .app heal for the Mac half. Do NOT fork its React tree as the hub frontend (it's new-york/Radix; mokei needs base-nova/Base UI). Wormhole transfer is superseded by suzuri's iroh engine for the hub.

**Why:** The product has nothing to do with agents, but the packaging, install and background-update plumbing is exactly how Stephen wants the hub to ship. It is a copy-the-code template, not something to merge into the hub.

## Lessons from ai-office

1. Connect real agents; don't run fake ones. ai-office hosted its own local-LLM 'employees' (Ollama/llama-server/MLX) with prompts, reflection and meetings. That never touched the Claude Code and Grok sessions where the work actually happens. The hub should be a coordination layer that real external sessions join through adapters (the Claude Code mod with $.prompt.submit, Grok's notifications/claude/channel plus ACP, rock ACP/HTTP), not an agent runtime.
2. Don't build an orchestrator that drives turns. Most of its late commits fixed orchestration bugs: zombie meetings, stuck invitations, quorum failures, preemption between reflection and meetings, and 6 issues found in a 15-agent test. tsukumo's model works better: messages go to an owner, there is a per-message take lock, an engaged/defer state, a sweeper that reassigns only stalled new work, and the human has the final say.
3. Don't make the infrastructure need a server. SpacetimeDB plus a redis-backed Slack bridge needed services running. That conflicts with 'installable like Toru, works across Mac and Windows'. Use a local-first store per device and replicate P2P (suzuri's iroh engine and its workspace-sync prototype on origin/archive/glass-chrome), started on demand like tsukumo's router.
4. Chrome costs more than it earns. The 3D office (bloom, SSAO, an RTS camera, a minimap) was built and then deleted for a 2D HTML view. The hub UI should start as plain mokei panels: threads, presence and tasks.
5. Docs drifted from the code. The README stayed Tauri boilerplate and FEATURES.md still lists deleted 3D features. Keep the hub's agent guide generated from the live tool surface, the way suzuri's workspace_guide returns paste-ready instructions from code.
6. A related retrospective in the knowledge base (KB slack-dual-ai-pairing) adds hard requirements for the hub. An idle poll must never inject a turn into the human's session, so waking must be event-driven, only on a real mention or assignment, never a scheduled poll. 'Stop' must actually tear down the wake subscription. One writer per cursor or state file, or a lock, because the poll and the main session raced on last_ts. Claim-before-code plus disjoint work items worked, so keep tasks and path leases. Extra ACKs cause ping-pong, so rate-limit agent-to-agent traffic (tsukumo already allows 8 per pair per 10 minutes). Agents must never close or merge PRs on their own from an inbound message. The same GitHub user running two agents is ambiguous, so the hub needs its own per-session identity, not the git or GitHub author, and must disambiguate duplicate names (as suzuri does with engine/engine-2).
7. Keep the layers separate (KB p2p-conversation-pairing entry). Project 'what's lined up' belongs in the repo (NOW.md/AGENTS.md). Durable curated knowledge belongs in knowledge-base. Live agent-to-agent conversation is the hub's job. The hub should link to the other two layers, not swallow them.

### consolidate-mvp: fatal flaws found

- Too much for two weeks. Weeks 1-2 hold a new Wails app scaffold, a rewrite of suzuri internal/workspace (14 files, 3,495 lines of Go on main) from JSONL onto an HLC event log, a fork of the 900-plus-line tsukumo register.tsx, the aizuchi import, a KB git syncer, capture v1 with blob snapshots and commit matching, and signed and notarized Mac plus Windows releases. Porting the workspace onto an event log is a redesign, not a copy. Week 1 alone is plausible. Capture v1 and the Mac release will slip.
- Not as much consolidation as the summary says. It adds app N+1 (Yoriai) and a new Rust sidecar, keeps suzuri (terminal), aizuchi (meetings) and toru, and for weeks or months leaves two parallel agent-workspace systems running: suzuri's workspace_* MCP tools and pane next to the hub's tasks and leases. The plan never schedules removing suzuri's workspace ('a later suzuri PR'), so agents get two overlapping sets of claim and lease tools. That is exactly the stranded-systems problem Stephen wants gone. The suzuri retirement has to be a milestone in the MVP, not 'later'.
- The long-poll wake path is the load-bearing piece and is unproven. The mod API documents $.http.fetch as 'resolves once the body is read' and lists no timeout, abort or streaming option. Tsukumo never used it for long waits: it streams from a spawned Bun child ($.process.spawn) and uses fetch over a unix socket only for short acks. Whether a 25 s fetch held per session in a background loop survives mod reloads (PLUGIN_DIR_WATCH), session idle, and many concurrent sessions is unknown. This must be proven on day 1, with $.clock.every short polling or a spawned hub-CLI stream as the fallback.
- Windows wake is a coin flip that sits under the whole cross-device goal. Stephen's other machines are Windows PCs, and nothing in tsukumo or its README shows the mod running on Windows. If it doesn't run there, 'agents wake each other' falls back to no wake at all on Windows, because the MCP channels path works only for grok-fork, not Claude Code.

### deltadb: fatal flaws found

- Per-file LoroText shadow docs are the most expensive part of the design, and the CRDT's merge property is never used. The proposal itself says each worktree keeps its own shadow and the hub never writes the working tree, so every shadow has exactly one writer: the disk on one machine. Nothing ever merges concurrently. A replicated append-only log of edit events (structuredPatch plus before and after blob hashes, linked to promptId/toolUseId) gives the same 'which turn made this line' blame by replay, and costs much less on large repos. Character-level Loro shadows add memory and history growth, plus the reseed-on-checkout and shallow-snapshot complexity listed in the risks, for a capability the design never exercises. M4 (3-4 weeks, 'the hardest part') is built on this.
- Anchored comments are tied to one worktree's shadow doc. A comment made on the Mac clone cannot resolve in the Windows clone of the same repo, because those are separate Loro docs. Delta's comments are shared by everyone on the repo. Two more problems: shallow snapshots at each checkpoint can trim the history that older Cursors need to resolve, and a checkout or rebase that reseeds a shadow can orphan anchors. The fallback 'quotedText plus commitAtCreation' re-anchoring is what actually carries comments across machines and commits, and the proposal does not design it.
- 'No cloud' is contradicted by the pairing design. hato-code (suzuri libs/transfer/crates/hato-code) runs SPAKE2 over a WebSocket rendezvous mailbox (hato-mailbox). It has no iroh dependency, and its dev default is loopback, so a real mailbox server has to be hosted or chosen. Toru's codes use wormhole-william and the public magic-wormhole mailbox. Cross-device delivery also leans on n0's public relays. The proposal needs an explicit rendezvous plan, or a pairing method that needs no server, such as a QR code or a pasted iroh ticket.
- Waking a Claude Code session depends entirely on the private mod API ($.prompt.submit through CLAUDE_CODE_PLUGIN_DIRS). Meanwhile Claude Code 2.1.310 ships native peer messaging: ~/.claude/sessions entries carry peerProtocol:1, peerFeatures [notify_idle, reply_across_default_dirs, artifact_yield] and messagingSocketPath, and sessions have ListAgents/SendMessage tools. The proposal explicitly refuses to use these for same-machine delivery. So it rebuilds local messaging on an equally private, less official surface, when the native path could be the default local transport and the hub's own transport could be used only across machines and for Grok.
- Scope and process count are heavy for 'one great piece of software': a Go/Wails shell, a Rust core sidecar, a hook client, a TS mod, and a WASM Loro copy in the UI. That is two toolchains to sign and notarize, about 16 to 20 weeks of milestones, and a Delta-grade capture system before any payoff beyond messaging. A smaller first version (capture log plus messaging and waking plus cross-device sync, with no CRDT file shadows) would deliver what he actually asked for: no Discord, agents waking each other, and one app.

### agent-native: fatal flaws found

- Pairing with "no server Stephen has to run" is not real yet. hato-code SPAKE2 short codes go through hato-mailbox, a WebSocket rendezvous server. Its default is loopback (dev), and it refuses plaintext ws:// to a remote host. suzuri's docs/transfer.md still lists '[ ] Contacts / pair / listen (needs mailbox)' as unchecked. So M4 needs one of two things: Stephen hosts a mailbox (a server), or pairing falls back to pasting an iroh endpoint ticket by hand. The proposal treats code/QR pairing as a lift; it is new work plus infrastructure.
- Every Claude path carries two capture/wake surfaces: http hooks in settings.json AND a mod. The mod already sees prompt.submit, tool.call, turn.start, session.send/receive and Stop-equivalents, and it can register tools with $.tool.register (that is how tsukumo-discord exposes its tools today, not through a separate MCP server). Running http hooks, a mod, a stdio MCP server and a transcript tailer side by side means four integration points to keep version-compatible on every Claude Code update. For Claude the mod alone (with $.tool.register for hub_* tools) could carry capture, tools and wake. MCP should be kept for grok-build and other clients.
- The asUser trust rule fails across devices. Peer messages get the 'not the person's authority' fence, but replies 'typed in the hub GUI on a paired device' are submitted asUser:true, and the model then reads them bare as Stephen's own words. A paired device that is compromised, or simply buggy, can mint person-authority prompts on every other machine. That undoes the fencing the design relies on. Only the local device's GUI should be allowed to submit asUser. Remote 'Stephen' messages need a signed or user-confirmed path, or should go through fenced framing.
- Exactly-once wake depends on the target device holding the take-lock. Meanwhile kind=ask messages to a gone session fall to a 'front desk' after 3 minutes, and Stop-hook continuation, next-prompt additionalContext, the SSE submit path and native SendMessage are all possible deliveries of the same queued item. The proposal does not say which of these consume the item. Unless one delivery state machine owns all of them, the same message can arrive as context AND as a woken turn. tsukumo's core.ts has no tests for this (it never had multiple delivery channels per message).

### suzuri-hub: fatal flaws found

- The plan builds on the wrong GUI. On origin/main the default suzuri UI is 'classic ebiten + Charm' in Go (cmd/suzuri/main.go:70, chrome/HOST.md:89, internal/chromehost/prefer_test.go), and every recent commit is feat/fix(classic). The Rust winit/wgpu chrome is the secondary path. The proposal puts the presence strip, badges and toasts in 'the wgpu terminal chrome' and justifies the split UI with chrome/README.md. That means the in-terminal work, and part of the 'two surfaces' reasoning, targets a UI he is not using day to day.
- The cross-device starting point is described wrongly, so the M0 recovery plan is mis-scoped. Commit c8e2691 (the iroh two-root sync) was not 'deleted from HEAD'. It was never merged to main. A later, more complete version, 9bdd319 ('productize workspace Iroh P2P: suzuri-workspace-sync sidecar (--json NDJSON), Share/Join chrome, package the binary on macOS/Windows', +588 lines chrome/src/workspace_sync.rs, release.yml changes), sits on unmerged branches (archive/glass-chrome, feat/workspace-mcp-channels and others). The right first step is to triage those branches against classic, not to cherry-pick the older c8e2691 crate.
- It does not deliver the 'one great piece of software' he asked for. The hub UI is a localhost browser SPA, separate from the terminal app, and the wake path still depends on a separately installed Claude mod plus hand-edited settings.json. He still deals with three things (terminal, browser tab, mod install). Some split is forced by Claude Code, but the proposal never weighs a webview window (Wails, as in toru/mead) owned by the same install against 'open in default browser'.
- The mod update story breaks for Claude desktop Code-tab sessions, which the proposal itself names as a main reason for running hubd as a daemon. tsukumo's claude-mod/README.md says desktop sessions run the copy made at install time (~/.claude/plugins/cache/...), so neither CLAUDE_CODE_PLUGIN_DIR_WATCH nor a binary-versioned mod path updates them. They need a version bump plus `claude plugin update`. The 'hubd tells stale sessions to reload' handshake therefore does not cover those sessions.
- Everything in the wake path depends on undocumented Claude Code surfaces: the mod API ($.prompt.submit, turn.start/turn.complete) and the dev-gated channels flag. The three-adapter mitigation is reasonable, but the third adapter (PTY injection) only covers suzuri panes, so desktop and non-suzuri sessions have no fallback if the mod API changes.
