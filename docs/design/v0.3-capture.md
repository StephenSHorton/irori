# v0.3 "Capture": design

*2026-10-27. Builds on v0.2 (`main` @ bc83cd3). Inputs: research/01 §4 (Capture) and §7, research/03 (Capture mechanism, tiers 1–3), research/04 §2, §6 and §7, research/v02/router.md §11–§12 (the authorship ledger and PR refs), spike 01, and a survey of 40 real transcripts on this machine (2026-10-27). Where this doc and the research disagree, this doc wins.*

v0.3 records what every agent did: its turns, tool calls and edits, the commits those edits ended up in, the PRs it opened or reviewed, and the decisions it wrote down. You can then ask "what was this session doing", "which conversation wrote this line", or "why is it like this" and get an answer from the record instead of from terminal scrollback.

## 1. Scope

**In**
- A **transcript tailer** in the Core that incrementally reads every Claude Code transcript on this device (main sessions and their subagents, mod or no mod) and turns it into capture rows.
- **Timelines**: per session, turns with their prompt, reply, tool calls and edits, interleaved with Irori messages, commits and PRs.
- **Edits** as events: the patch (a blob), the git blob SHA before and after, the turn and the tool call that made it, and a fidelity of `exact` or `heuristic`.
- **Commit links**: watching each known repo's reflog and matching the commit's file blobs to recorded edits, so each commit links to the sessions and turns that produced it.
- **The PR ledger** (ported from tsukumo): `pr-link` rows, `gh pr create` and `gh pr review`. A message can be addressed to a PR.
- **Decisions**: `decision_record` with an optional code anchor that is re-checked when it is read, supersession, and "mark as decision" in the GUI.
- **`why`**: path (and optional line) → the edits, commits, sessions and decisions behind it.
- Secret scrubbing of everything capture stores.
- GUI: a Timeline tab, a History tab (commits and files), a Decisions tab, and fidelity badges on roster cards.

**Out (later)**
- Handoff cards, `thread_read` extraction, `fork`: these need an LLM call and a cost budget (research/04 §5), which come with v0.4's always-on node.
- File watching (fsnotify) for Grok or for human edits. A Grok member's capture is what it does through Irori tools; files a commit changes that no recorded edit explains are listed as **unattributed**.
- Replicating capture to other devices (v0.4). Rows are shaped for it: patches are blobs fetched on demand, and the turn index stays small.
- Pinned blocks, deliverable reports, the approval queue.

## 2. Where capture comes from

**Decision (14): the Core tails the transcript files; the mod stays as it is.** research/01 put capture in the mod (`session.append`, `tool.call`). Reading the JSONL in the Core is better for v0.3:
- It covers sessions that don't load the mod, which is every one of your sessions today, as well as desktop Code-tab sessions and sessions from before Irori started.
- It survives Core restarts with no loss, since each file's byte offset is kept, and the mod has no buffer to lose.
- It carries what the mod would have had to forward: the transcript's `toolUseResult` holds the `structuredPatch`, `originalFile` and `bashEditDiff` (spike 01 left open whether `session.append` exposes these, and the transcript certainly does).
- It keeps the mod thin, which research/03 names as the mitigation for mod API churn.

The cost is a few seconds of lag, since the roster already sees turn boundaries live, and a dependency on an undocumented format. The parser allow-lists the record types it reads and ignores everything else (the survey found 24 types; §3 uses 8).

**What is read**
- `~/.claude/projects/<slug>/<sessionId>.jsonl` (main), and `<slug>/<sessionId>/subagents/**/agent-<id>.jsonl` (subagents and workflow agents). The session id comes from the path. A subagent row carries `isSidechain: true` and `agentId`; its edits belong to the parent session, tagged with `agentId`.
- Files are scanned every 3 s. Read `[offset, size)` up to the last `\n`; a half-written line waits. A file that shrank resets to 0. Each file's offset is persisted in `<dataDir>/capture-cursors.json` (atomic write), not in the event log: offsets are local bookkeeping and never replicate. Cursors are saved after the rows they cover are appended. A crash between the two re-reads a little, so every capture row has a deterministic id (turn: session + turn id; edit: session + toolUseId + path; ledger: key + session + role), and the service skips ids it already holds, rebuilt from the log at start.
- **Backfill:** a file seen for the first time is read from the start if it was modified within `BackfillWindow` (default 72 h) and is at most `BackfillMaxBytes` (default 64 MiB). A file over the cap whose session is a live card is read from its last `compact_boundary` row (where the current context starts) or, if it has none in its last 64 MiB, from 64 MiB before the end at the next line start. Every other file starts at its current end. Older history stays readable in Claude Code itself; an "import older history" action can come later.
- The first scan can cover hundreds of MB. It runs in its own goroutine after `core.Start` returns, live sessions first, and lines starting `{"type":"api-request` (the largest rows, over half the line count) are skipped by a byte-prefix check before any JSON decoding.
- The tailer never reads `*.key` files, or anything outside `projects/`.

## 3. What the tailer turns rows into

| Transcript row | Becomes |
|---|---|
| `user`, not `isMeta`, no `toolUseResult`, not `isCompactSummary` | starts a **turn**. Its prompt is the text (string content, or text blocks joined). `origin.kind` (`human`, `plugin`, `peer`, `task-notification`, …) is kept. When it is missing (older versions), the origin is `sdk` if `promptSource` is `sdk`, `command` if the text starts with `<command-name>`, else `human`. `promptId` is the turn id when present, else the row `uuid`. A text of exactly `[Request interrupted by user]` (or `… for tool use]`) doesn't start a turn: it marks the current one `interrupted`. |
| `assistant` blocks | `text` → the turn's reply (the last text block wins); `tool_use` → a tool call `{id, name, target}`. `thinking` is dropped. |
| `user` with `toolUseResult` | completes its tool call (`is_error` from the `tool_result` block). For Edit, Write and NotebookEdit it becomes an **edit** (§4). For Bash it is checked for `bashEditDiff` (heuristic edits), a commit command (§5), `gitOperation.pr` with `action: "created"` and `gh pr review` (§6). |
| `system` `turn_duration` | closes the current turn. |
| `system` `away_summary`, `compact_boundary`; `user` with `isCompactSummary`; `ai-title`, `custom-title` | **summary** rows (kind and text), shown on the timeline. A compaction summary is stored as a blob, not inline (they run 12–17 KB). |
| `pr-link` | a PR ledger entry, role `touched` (§6). |
| everything else | ignored |

A turn is also closed when the next turn starts, or when the file has been quiet for 2 minutes and the session's presence status is not `busy`. The open turn of a live session is kept in memory and shown on the timeline as in progress; only closed turns are logged.

**`target`** is a short, scrubbed label for a tool call: the path for file tools (repo-relative when inside the session's repo), the first line of a Bash command (≤160 chars), the pattern for Grep and Glob, the URL for WebFetch, the description for Agent. Tool output is never stored, except the `stdout` lines §6 parses.

**Turn caps:** prompt excerpt 2000 chars, reply excerpt 1000, at most 200 tool calls per turn (the rest are counted, not listed).

## 4. Edits

One `capture.edit` row per file per tool call:

```
{ id, session, agentId?, turnId, toolUseId, rowUuid, tool,
  repoKey?, root?, path,            // repo-relative POSIX inside a repo, else absolute
  beforeBlob?, afterBlob?, afterBlobLF?,  // git blob SHA-1 (hex) of the whole file; LF = CRLF→LF form
  patch: "<sha256 of the patch blob>", adds, dels,
  fidelity: "exact" | "heuristic", at }
```

- **Write**: after = `content`; before = `originalFile` (null for a create). The patch is built from `structuredPatch`.
- **Edit**: before = `originalFile`; after = `originalFile` with `oldString` → `newString` (all occurrences when `replaceAll`, else the first). When `originalFile` is null (too large for Claude Code to include), or `oldString` isn't found in it, after is unknown: the edit keeps its patch, has no `afterBlob`, and its fidelity stays `exact` (the patch is still Claude Code's own).
- **NotebookEdit** keeps the patch only. (This Claude Code has no MultiEdit tool; a `toolUseResult` with an `edits` array is treated as successive Edits if one appears.)
- A result with `staged: true` (held for review, not written) is not an edit.
- **Bash** with `bashEditDiff.changedFiles`: one `heuristic` edit per file, with no blobs, and a patch only when `bashEditDiff.files` carries one.
- The patch blob is a unified diff (`--- a/<path>` / `+++ b/<path>` plus the hunks), scrubbed (§9) before it is hashed and stored.
- **Line endings:** each blob is hashed twice, over the bytes as given (`afterBlob`) and with every CRLF turned into LF (`afterBlobLF`, omitted when equal). A commit matches either, because on Windows `core.autocrlf` makes the committed blob the LF form. Without this nearly every link on this machine would be `partial`.

**Blob store** (`internal/blob`): content-addressed files at `<dataDir>/blobs/<aa>/<sha256>` (gzip), written once (temp file plus rename) and never changed. It holds patches and compaction summaries. Each blob is at most 4 MiB, and a patch over that is truncated with a marker. Blobs never go into the event log, and v0.4 will fetch them on demand.

## 5. Commits

**Which repos are watched:** every worktree root that an edit or a live card's cwd has shown (from `git rev-parse --show-toplevel`, resolved once and cached), for as long as Irori runs. The roots seen are kept in the log (`repo.seen` {repoKey, root}), so they are watched again after a restart.

**Watching:** every 5 s, stat `<gitdir>/logs/HEAD` (for a linked worktree, the gitdir comes from its `.git` file). When it grows, parse the new lines: `<old> <new> <name> <<email>> <unix> <tz>\t<message>`.

Any reflog line can bring in commits, not only `commit:` lines: a fast-forward merge, a pull, a rebase or a cherry-pick moves HEAD over commits this worktree's reflog never listed (your v0.2 flow commits in `worktree-wf_*` worktrees, then fast-forwards main, and the worktrees and their reflogs are deleted). So for every line whose `<new>` isn't already in `commit.seen` for this repo: `git rev-list --reverse --max-count=200 <old>..<new>` (just `<new>` when `<old>` is all zeros), and each commit not yet seen is processed. A checkout to a known commit adds nothing. A capped walk is logged with the count it skipped.

For each commit: `git show -s --format=%H%x00%P%x00%ct%x00%an%x00%s <sha>` for its own time (the committer-window match uses `%ct`, not the reflog line's time, which for a fast-forward is the merge time), and `git diff-tree -r --no-commit-id --no-renames --raw --no-abbrev --diff-merges=first-parent <sha>` (git 2.31+; `-m --first-parent` lists every parent's diff on newer git) for each changed path's new blob. `commit.seen`:

```
{ repoKey, root, sha, op, subject (≤200), author, at, branch?,
  files: [{path, blob, status}]  (≤500; more are counted) }
```

**Linking.** For each file in the commit:
- **exact:** an edit in the same repoKey and path, from **any** worktree root, whose `afterBlob` or `afterBlobLF` equals the committed blob. It and the earlier edits of that run (same root and path, back to the previous commit that touched the path from that root) are linked. Blob equality is what lets a fast-forwarded merge in main link back to edits made in a deleted agent worktree.
- **partial:** no blob matches, but there are edits to that path from the **commit's own root** since its previous commit there. They are linked, and the file was changed again afterwards (by a person, a formatter, or a tool that rewrote it).
- **heuristic:** only Bash (`bashEditDiff`) edits from the commit's root.
- **unattributed:** nothing.

Restricting partial and heuristic to the commit's own root keeps two workflow agents editing `foo.go` in different worktrees from being credited with each other's commits.

Who made the commit is recorded separately. The **committer** is a session whose Bash tool ran a commit command (`git commit`, `git merge`, `git cherry-pick`, `git revert`, `git rebase`, `gh pr merge`, matched on the command text, since `gitOperation` doesn't report commits) with a cwd in this root, within ±10 s of the commit's `%ct`.

`commit.linked`:

```
{ repoKey, sha, committer?: {key, turnId},
  files: [{path, link: "exact"|"partial"|"heuristic"|"unattributed", edits: [editId]}],
  sessions: [key], turns: [turnId] }
```

A commit seen before any of its edits were tailed (rare: backfill catching up) is linked again when the edits arrive; the newest `commit.linked` per sha wins.

## 6. PRs and the authorship ledger

Ported from tsukumo (research/v02/router.md §11 and §12), with Irori keys.

- **Entries:** `pr.ledger` `{key: "pr:<owner/repo lowercased>#<n>", repo, number, url?, session (agent key), role, source, at}`. Roles rank `author` first, then `touched`, then `reviewer`, with earliest `at` first within a rank (tsukumo's code order, not its comment). The same identity (key, session, role) keeps its earliest `at`. Entries older than 45 days drop out of the view; the rows stay in the log.
- **Producers:**
  - `pr-link` transcript rows → `touched`, source `pr-link`.
  - Bash `gh pr create`: the result's `gitOperation.pr` with `action: "created"` (number and URL, as Claude Code reports it) → `author`. If that is absent, the command matches `\bgh\s+pr\s+create\b`, and stdout has `github.com/<o>/<r>/pull/<n>`, that is used instead.
  - Bash `gh pr review <target>`: a URL, or a number with the repo from `-R/--repo`, else the session's repoKey when it is a `remote:github.com/...` key → `reviewer`.
- **PR refs** (`extractPrRefs`): the URL, `owner/repo#N`, `name#N` (with the default owner), and bare `#N` (needs a default repo), with code spans stripped first. RE2 has no lookbehind, so the preceding rune is checked by hand (router.md §12, Go port note).

**Addressing a PR.** `send` gains `to: "pr:<owner/repo>#<n>"` or a PR URL. Routing (`to.kind: "pr"`):
1. The best-ranked ledger owner whose session is live → that session.
2. Else that repo's front desk (the repoKey `remote:github.com/<owner>/<repo>`), and the delivery's note names the owner it would have gone to.
3. Else queued, unowned, shown in the GUI.

A message addressed to a repo or an agent is not parsed for PR refs (no hidden rerouting). Free-text parsing is for the GUI composer's suggestions only.

## 7. Decisions

`decision.recorded`:

```
{ id, by: {key, name, kind}, statement (≤500), why? (≤2000),
  anchor?: { repoKey, path, sha (HEAD when recorded), start, end,
             hash (sha256 of the lines), context: [2 lines before, 2 after] },
  supersedes?: [decisionId], source?: {messageId? | turnId?}, at }
```

- **Recording:** the `decision_record` tool (by the caller), or the GUI's "Mark as decision" on a message or a turn (by the user, with trust `user`). An anchor needs a path, and lines are optional. Without lines it anchors to the whole file, and its hash is the file's blob SHA.
- **Reading re-checks the anchor** against a working tree: the root it was recorded in if that still exists, else the root of any live card with the same repoKey, else the status is `unknown`. It reports `ok` (the hash matches at the same lines), `moved` (the same lines found elsewhere in the file, with the new range), `changed` (the file is there but the lines aren't), `gone` (the file is missing) or `unknown` (no working tree). The check is never written back into the log, since the working tree is per-device state.
- **Supersession:** a decision listing `supersedes` hides those decisions from default lists, and they remain visible in their history. Only the original author or the user can supersede a decision.

## 8. Tools (both front ends, as v0.2 §8)

| name | args | returns |
|---|---|---|
| `timeline` | `agent?` (default me), `limit?` (turns, default 10, max 50), `before?` | turns newest first: prompt and reply excerpts, tool counts, edited paths, commits and PRs |
| `why` | `path`, `line?`, `repo?` | for a line: `git blame` → commit → the linked sessions and turns. For uncommitted lines: the newest edits. Always: decisions anchored there. |
| `decision_record` | `statement`, `why?`, `path?`, `lines?` (`"40-52"`), `supersedes?` | the decision id |
| `decisions` | `repo?`, `path?`, `query?`, `all?` | decisions with their anchor status |
| `send` | `to` also accepts `pr:<owner/repo>#<n>` or a PR URL | (v0.2) |

The repo for `path` and `why` comes from the caller's cwd unless `repo` is given. Results stay text, capped at 8 KB, as in v0.2.

The mod's logic doesn't change: it lists the Core's tools at attach time, so the new ones appear by themselves. Its version constant and the `--mod-version` it passes move to 0.3.0, so `/irori` shows which copy is loaded.

**Capture row actors.** Capture rows are written with actor `agent:<device>/<session>` (the session whose transcript produced them), so the existing `events` tool filters work. Commit rows and ledger rows from `pr-link` are written with actor `irori`.

## 9. Secret scrubbing (`internal/scrub`)

This runs on every excerpt, target, summary and patch before it is stored or hashed. It replaces matches with `[redacted:<kind>]` and covers:
- Known token shapes: `sk-ant-…`, `sk-…`, `ghp_`/`gho_`/`ghu_`/`ghs_`/`github_pat_`, `xox[abpr]-`, `AKIA…`, `AIza…`, JWTs (`eyJ…​.…​.…`), `-----BEGIN … PRIVATE KEY-----` blocks.
- `key=value` and `key: value` where the key contains `token`, `secret`, `password`, `passwd`, `api_key`/`apikey` or `authorization`, with a value of 8 or more characters.
- `Authorization: Bearer …` headers.
- Irori's own lockfile token and attach and member secrets, whose exact current values the Core knows.

Patches against files named `.env*`, `*.pem`, `*.key`, `id_rsa*` or `credentials*` are not stored at all. The edit row keeps its counts and `patch: ""`. Scrub tests run on seeded fixtures (research/04 §8 Q5).

## 10. API (loopback, as v0.2)

```
GET  /v1/timeline?agent=<key>&before=<turnId>&limit=N    -> {turns: [...], open?: {...}}
GET  /v1/edits?repo=<repoKey>&path=<p>&limit=N           -> []Edit
GET  /v1/commits?repo=<repoKey>&limit=N                  -> []{commit, link}
GET  /v1/blobs/<sha256>                                   -> the blob (text/plain)
GET  /v1/decisions?repo=&path=&all=1                      -> []Decision (with anchor status)
GET  /v1/prs?repo=                                        -> ledger view
```

Decision and tool writes go through `POST /v1/tools/{name}` as in v0.2. The GUI calls the Go services directly through Wails.

## 11. GUI

- **Timeline** tab: pick an agent (live or gone; the default is the most recent). It shows turns newest first, each with its prompt, reply, tool chips and edited files. Messages, commits, PRs and summaries are interleaved by time. An edit opens its diff. A commit chip opens History at that commit. "Mark as decision" sits on each turn.
- **History** tab: pick a repo to see its commits, each with link chips (exact, partial, heuristic, unattributed) and the sessions and turns behind it. A file box answers "why" for a path, with an optional line.
- **Decisions** tab: a list filtered by repo, showing the anchor status badge and the supersede chain. A form lets the user add a decision.
- **Roster:** a fidelity badge per card. `mod` means attached and captured, `passive` means captured with no mod, `mcp` means a Grok member with self-reports only. A "Timeline" link sits on each card.

## 12. Tests that prove v0.3

- **Unit:**
  - Transcript parsing on fixtures cut from real record shapes: turn boundaries, prompt origins, sidechain attribution, a half-written line, a shrunk file, and unknown types ignored.
  - Edit reconstruction for Edit, Write, replaceAll, a null originalFile, an `oldString` that isn't found, `staged`, and Bash `bashEditDiff`.
  - Git blob SHA known vectors.
  - Reflog parsing (every op), plus the link classes on a temp git repo with real commits: exact, exact through the CRLF→LF hash, partial, unattributed, the committer window, a fast-forward merge from a deleted worktree that links by blob, and two worktrees editing the same path.
  - Ledger rank and merge, `extractPrRefs` (the tsukumo test table), and PR routing.
  - Anchor re-check (ok, moved, changed, gone).
  - Scrub fixtures (true and false positives).
- **Integration (in-process Core):** a fake `~/.claude` with a transcript written in pieces. Then a real `git commit` in a temp repo produces a timeline, edits, an exact commit link, and a `why` answer for a line.
- **Live (Windows):** a real `claude --bg` session edits a file in a scratch repo and commits it. The GUI timeline shows the turn and edit, History links the commit to that turn, and `why` on a changed line names the session.

## 13. Build order

- **Wave 1, pure logic, in parallel:**
  - `internal/capture/transcript`: the parser, which turns rows into turns, tool calls, edits, summaries and PR entries, with no I/O beyond `io.Reader`.
  - `internal/capture/gitlink`: reflog parsing, diff-tree, blob SHA and link classification.
  - `internal/scrub` and `internal/blob`.
  - `internal/ledger`: PR refs, rank and merge.
  - `internal/decision`: anchors and their re-check.
- **Wave 2, wiring:**
  - `internal/capture`, the service: the tailer loop, cursors, writing rows, repo watching and the in-memory views.
  - Core wiring.
  - The tools (`timeline`, `why`, `decision_record`, `decisions`, PR `send`) and inbox PR routing.
  - The API routes.
  - The GUI tabs.
  - The integration test.
- **Then:** the live test.
