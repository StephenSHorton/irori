# v0.2 "Talk": design

*2026-10-26. Builds on v0.1 (`main` @ a2fa74f). Inputs: research/01 §4 and §7, research/04 §2–§5 and §7, spike 01, and the port specs in [research/v02](../research/v02) (router, mod, suzuri). Where this doc and the port specs disagree, this doc wins.*

v0.2 makes agents on one device able to message each other, wake each other, and share tasks and leases, with nothing dropped. Cross-device delivery is v0.4; every row is already shaped for it.

## 1. Scope

**In**
- Messages and an inbox that never drops: addressed to a session, an agent name, a repo, or as a reply.
- One delivery state machine for every wake path: Claude Code through the Irori mod, Grok through a channel push on `irori mcp`, and a person through the GUI.
- The Irori Claude Code mod, which auto-attaches every session through `irori attach`.
- Wake policy: everyone or allowlist mode, block and allow lists, held items, a bypass-mode hold, a hop limit, a per-pair rate limit and a pause-all switch.
- Tasks and leases, with leases released automatically when their holder goes away.
- `repo_key` on agent cards (the normalized origin remote, else the git root commit).
- GUI: an inbox with held items, a composer, tasks and leases, and pause-all in the tray.
- Manual revive: a GUI button that runs `claude --bg --resume <session>` in the session's cwd.

**Out (later milestones)**
- Threads as first-class objects with claims, and PR addressing with the authorship ledger: v0.3, once capture sees `gh pr` commands.
- Auto-revive (decision 3 allows it; the policy gate in research/04 §5 lands with v0.4's cross-device wake).
- Cross-device anything: v0.4.

**Native SendMessage.** research/01 §8 says Claude↔Claude on one machine is native. Irori doesn't replace or intercept it. Irori messaging exists for what native can't do: Grok and other non-Claude agents, a person writing from the GUI, a durable inbox past native's limits, an audit trail, repo-addressed work, and (v0.4) other devices. That supersedes the "don't build" line for those cases only.

## 2. Identity

- An **agent** is a presence card, keyed `<deviceId>/<sessionId>` (v0.1).
- The **sender** of a message is set by the Core from the connection, never from what the agent claims:
  - mod tools → the attached session;
  - `irori mcp` → the member that process bound with `irori_join` (Grok); unbound calls can read but not send;
  - GUI → `user:<deviceId>`.
- **Names.** An agent is reachable by its card name (Claude Code's session name), lowercased, plus up to 10 aliases it sends under (max 60 chars each; newest wins). Exact key beats name; a name that matches two live agents is an error naming both; a key prefix of 8+ characters works if unique.
- Grok members get a synthetic card (`agent: "grok"`, key `<deviceId>/grok-<id>`), held while their `irori mcp` process is connected and for the reattach grace after. The id comes from the session: `_meta`, then `IRORI_SESSION_ID`, `GROK_SESSION_ID`, `XAI_SESSION_ID`, else a random id for that process. It is never derived from the join name (v0.4.2), so reusing a name can't take over another member's cards or inbox; a script that posts a card and updates it from a later process sets `IRORI_SESSION_ID` to a token of its own.

## 3. Messages and routing

`message.sent` payload:

```
{ id, from: {key, name, kind}, to: {kind: "agent"|"repo"|"reply", value},
  text, reason?, replyTo?, threadId?, hop, parentId?, trust: "untrusted"|"user" }
```

- `id` is minted by the Core: a ULID-style string, sortable.
- `trust` is `user` only for messages typed in the GUI.
- `text` max 8000 chars after trim.

Routing (on send, in the Core), producing exactly one recipient:

| `to.kind` | Recipient |
|---|---|
| `agent` | That agent (key, key prefix, or name/alias). Unknown → error; known but gone → queued for it (it may come back or be revived). |
| `reply` | The sender of `replyTo`. |
| `repo` | The repo's **front desk**: the live agent in that `repo_key` that attached first. When it goes, the next earliest takes over. No live agent in the repo → queued unowned and shown in the GUI. |

## 4. Deliveries

One `delivery` per (message, recipient). States:

```
queued ─► held ─► queued (person: Deliver)          held ─► dismissed
queued ─► delivered ─► engaged ─► answered
                  └──► deferred ─► (due) queued
any open ─► skipped | rejected | expired(never in v0.2) | moved (repo work reassigned)
```

- **queued**: waiting for a wake path to the recipient.
- **held**: policy stopped it; reason is one of `blocked`, `not_allowed`, `bypass_receiver`, `paused`, `hop_limit`.
- **delivered**: a wake path handed it over. For the mod: accepted into Claude Code's queue. A submit made during a running turn is queued and only resolves when its own turn starts, so the mod POSTs `delivered` when the submit resolves or after 3 s pending, whichever is first. A Grok channel push is **not** delivered until the agent calls `irori_ack`, replies, or reads its inbox.
- **engaged**: the recipient's turn that carries it started (mod `turn.start` matching the delivery token), or it deferred.
- **answered**: the recipient called `reply` for it. A turn ending without a reply leaves it engaged.
- Each transition is a `delivery.<state>` row `{deliveryId, messageId, to, via, reason?, note?, until?, by}`. The current state is a fold.
- **Consumed once.** The Core hands a delivery to at most one wake path at a time; delivering again (a reload) is idempotent on delivery id.
- **When a wake is submitted.** For a recipient with a mod attach: submit immediately if it has no outstanding wake (a wake whose token is delivered but not yet engaged). Otherwise keep accumulating, and flush on that session's next `engaged` or `turn-ended`. Presence busy/idle is a hint for the UI, never the gate. A recipient with no wake path (no attach, no bound Grok member) keeps its deliveries queued.
- **Batching.** Everything queued for one recipient at flush time goes out as one wake (one prompt), up to 16 KB of text (about 4k tokens); the rest waits for the next flush.
- **Tokens.** Each wake has a unique token (`[irori-wake:<id>]`) that the mod matches against `turn.start`. Reminder wakes use a different form (`[irori-reminder:<id>]`) and never mark anything engaged.

**Sweeper** (every 60 s; pure planning functions, table-tested, ported from tsukumo `planSweep`/`planReminders`):
- Repo-addressed work delivered but not engaged after **10 min** moves to the next desk candidate (`moved`), once.
- Recipient gone for **3 min** (debounce; presence `gone` or attach lost): repo-addressed work moves; agent-addressed work stays queued for that agent.
- Engaged, no reply, no deferral for **60 min**: one reminder wake offering defer/skip.
- Deferral clamped to **12 h**; when due it re-queues.
- A move clears engaged/deferred state; deferrals by an earlier holder don't count.

## 5. Policy and safety

- **Mode** `everyone` (default) or `allowlist`, plus block and allow lists of sender keys or names, per device. Changed only from the GUI or the mod's `/irori` command typed by a person (`origin.kind === "composer"`). `irori mcp` has no policy writes.
- **Bypass-mode receiver** (native Claude Code's rule). A message is held (`bypass_receiver`) when the receiver runs with bypassed permissions **and** the sender does not: the sender isn't also in bypass, isn't `user:*`, and isn't on the allow list. Grok members have no permission mode and count as non-bypass on both sides. Permission mode comes from presence (the newest `permission-mode` row or `permissionMode` on a user row, scanning back past the tail on first sight); unknown counts as non-bypass. On this machine every Claude session runs in bypass, so Claude↔Claude messages flow and a Grok→Claude message is held until allowed. **Amended by decision 34 (2026-10-28):** the person's own Claude agents skip this hold whatever their mode: a sender of kind `claude` (not a Grok card) whose key names this device or a device certified to the person and not revoked, and names the device that wrote the `message.sent` row. The mode test above now applies only to Grok members and to agents on unknown or removed devices (and, with Shared Boards, other people's agents).
- **Hop limit.** The Core tracks, per session, the wake whose turn is running (from `engaged` to `turn-ended`). A send or reply made in that window gets `parentId` = the newest message in that wake and `hop` = its hop + 1; anything else starts at hop 0. At **hop > 6** the delivery is held (`hop_limit`).
- **Rate limit.** 8 messages per unordered pair per 10 min (`DIRECT_LIMIT`); the 9th send fails with a clear error. GUI messages are exempt.
- **Pause all.** A tray/GUI switch: while on, every new delivery is held (`paused`) and nothing wakes; turning it off re-queues `paused` items.
- **Soft boundary.** These rules bind agents that go through Irori's tools. An agent with shell access can read `irori.json` and call the API directly, including the mod's policy route. That is accepted for a single-user mesh; v0.4's signed device events don't change it on one device.
- **Fencing.** Every woken prompt wraps each message in `<irori-message from="…" key="…" delivery="…" trust="untrusted">…</irori-message>`. Content occurrences of `</irori-message` are escaped as `<\/irori-message`. Exactly one real closing tag per message (tested).

## 6. Tasks and leases

- **Task** rows: `task.created {taskId, title, objective, doneCriteria?, repoKey?, scope[]?, by}`, `task.claimed {taskId, by}`, `task.assigned {taskId, to, by}`, `task.status {taskId, state, note?}` with states `submitted, working, input_required, completed, failed, canceled` (A2A subset). One writer: claiming a task someone else holds fails unless it's unassigned or its holder is gone.
- **Lease** rows: `lease.acquired {resource, holder, until, stolenFrom?}`, `lease.released {resource, holder, reason}`. Resources are `path:<repoKey>:<posix glob>` or a named resource such as `gpu/qwen` or `port:8799`. Advisory. Default TTL 30 min, max 4 h; renew by acquiring again as the holder. Expiry is computed on read. Released automatically (`reason: "holder_gone"`) when the holder's agent is gone past the 3 min debounce. Stealing an unexpired lease needs `steal: true` and records `stolenFrom`.
- Path leases conflict when globs overlap within one repoKey (`path.Match`-style; `**` allowed).

## 7. Wire: `irori attach` and the mod

`irori attach --session <id> --cwd <cwd> --mod-version <v>` dials the Core (lockfile), opens `GET /v1/attach?session=<id>` (NDJSON stream), and copies it to stdout one JSON object per line. It reconnects with backoff (1 s doubling to 16 s) and exits 0 on `superseded`.

Stream events:

| type | fields |
|---|---|
| `hello` | `v`, `session`, `agentKey`, `name`, `api: {url, token}`, `attachSecret` |
| `deliver` | `deliveryIds[]`, `token` (unique per wake), `prompt` (the full fenced text, built by the Core) |
| `held` | `deliveryId`, `from`, `why`, `preview` |
| `moved` | `deliveryId`, `to` |
| `inbox` | `unread`, `held` |
| `superseded` | none |
| `error` | `message` |

A newer attach for the same session supersedes the older one. A session with no attach for 2 min (reload grace) counts as unreachable by mod; its queue keeps.

Settled: `$.session.id()` equals `sessionId` in `~/.claude/sessions/<pid>.json` (spike 01 rerun: the mod logged `b886ef92-…`, the same id `claude agents --json` listed for the job).

The mod package checks live before relying on them:
- `$.prompt.submit` while a turn is running: does it queue or reject? The delivered/engaged split assumes it queues.
- `$.http.fetch` to `127.0.0.1`: does the host add an `Origin` header (the API refuses any Origin)? Pass the bearer token in `headers`, not `auth`, because `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` refuses plugin requests that carry `auth`.

Mod → Core control is `$.http.fetch` to `api.url` with the bearer token from `hello`:

```
POST /v1/deliveries/delivered   {token}            (submit resolved, or 3 s pending)
POST /v1/deliveries/engaged     {token, turnId}    (turn.start whose text contains the token)
POST /v1/deliveries/turn-ended  {token, turnId}
POST /v1/tools/<name>  {args}                     (mod tool calls, see §8; sender = attached session)
```

`hello` also carries `attachSecret`, random per attach. The mod sends it as `X-Irori-Attach: <secret>` alongside the bearer token, and the Core maps it to the attached session, so control and tool calls act as that session and no other. A superseded attach's secret stops working.

## 8. Tools

Same backend, two front ends. Claude Code sessions get them from the mod (`mcp__irori__<name>`); Grok gets them from `irori mcp` (`irori_<name>`). A Claude session shouldn't load both; `irori mcp`'s server instructions tell Claude Code users the mod already provides these tools.

| name | args | notes |
|---|---|---|
| `agents` | `status?`, `cwd?` | v0.1 roster, plus repoKey and permission mode |
| `events` | `kinds[]?`, `limit?` | v0.1 |
| `send` | `to`, `text`, `reason?`, `repo?` (`to` omitted + `repo` = repo-addressed) | returns message id |
| `reply` | `delivery_id`, `text` | marks answered, routes to the sender |
| `inbox` | `all?` | open deliveries for me; reading marks Grok pushes delivered |
| `ack` | `delivery_id` | Grok only (mod acks itself) |
| `defer` | `delivery_id`, `minutes` (≤720), `note?` | |
| `skip` | `delivery_id`, `note?` | |
| `task_create`, `task_list`, `task_claim`, `task_assign`, `task_status` | | §6 |
| `lease`, `leases`, `release` | `resource`, `ttl_minutes?`, `steal?` | §6 |
| `join` | `name` | Grok only: binds this `irori mcp` process to a member |

Results are text, capped at 8 KB, `Error: …` on failure.

## 9. Grok channel push

When a delivery is queued for a Grok member, its bound `irori mcp` process writes:

```json
{"jsonrpc":"2.0","method":"notifications/claude/channel","params":{"content":"<fenced prompt>","meta":{"delivery_id":"…","message_id":"…","from":"…","trust":"untrusted"}}}
```

Meta keys only `[A-Za-z_][A-Za-z0-9_]*`. The delivery row is written before the push. The push doesn't count as delivered (§4).

## 10. API additions (loopback, token as v0.1)

```
GET  /v1/attach?session=          NDJSON stream (§7)
POST /v1/deliveries/{delivered,engaged,turn-ended}
POST /v1/tools/{name}             body {args}; caller identity from X-Irori-Attach (mod) or X-Irori-Member (the secret irori_join returned to an `irori mcp` process); never from the body
GET  /v1/inbox?agent=&all=        deliveries for an agent
GET  /v1/policy                   read only over HTTP; writes are Wails-only plus the mod's person-gated route
POST /v1/policy                   requires X-Irori-Origin: composer from an attached mod
```

## 11. GUI

- **Inbox** tab: every message with its delivery state, filterable; held items with Deliver, Allow & deliver, Dismiss; a composer (to: agent or repo).
- **Work** tab: tasks and leases, release/cancel buttons for a person.
- **Roster**: repoKey grouping, "attached" dot (mod connected), unread/held counts, Revive button on gone sessions that still have a transcript (runs `claude --bg --resume <id>` in cwd after a confirm, warns if the folder isn't trusted).
- Tray: Pause all wakes toggle; status line shows unread/held.

## 12. Tests that prove v0.2

- Unit: routing table, state machine transitions (every edge, idempotency), sweeper plans (ported tsukumo table tests), policy (each hold reason), fence escaping, rate limit window, hop limit, lease overlap/expiry/auto-release, task single-writer.
- Integration (Go, in-process Core): two fake attached sessions message each other; a reload supersedes and nothing is lost or doubled; a Grok member over a real `irori mcp` stdio process receives a channel push and acks.
- Live (Windows): two real `claude --bg` sessions with the mod: A sends to B by name, B wakes, replies, A wakes with the reply; GUI shows the whole exchange.

## 13. Build order

- **Wave 1, pure logic:** `internal/inbox` (messages, routing, the delivery fold, wake planning, sweeper plans, policy, limits, fencing), `internal/coord` (tasks, leases), `internal/repo` (repo_key), and presence additions (repoKey, permission mode). Reviewed and merged before wave 2.
- **Wave 2, wiring:** api routes and `irori attach`, the mod, `irori mcp` tools and the Grok push, the GUI, and an in-process integration test package. All against real wave-1 code.
- **Then:** integration and the live two-session test.
