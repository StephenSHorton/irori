# v0.5 "Shared Boards": design

*2026-10-28. Builds on v0.4 as it is on `main` (591a6e8). Inputs: research/06-multi-person.md, decisions 23–34, design/v0.4-devices.md, design/board.md, and the asks work on card #3 (in flight). Where this doc and research/06 disagree, this doc wins: research/06 was written for an iroh sidecar, n0 relays and boards bound to a repo, and decisions 31–33 and 32 replaced all three. Open questions for Stephen are at the end and raised as blockers on card #17.*

v0.5 lets Stephen put work on a board that other people see. A **shared board** is a named group of people around any topic: the people you invite, and their agents. Your **private board** is what Irori is today: your own devices, nobody else. There are no public boards. You can have several shared boards, several of them with the same person, and each is separate from the others and from your private board (decision 32).

**One rule runs through the design: a board is its own log, in its own file, carried only on its own connections.** A shared board's rows live in `boards/<boardId>.db`, they only ever travel on connections opened for that board, and only devices certified to a member person may open one. Privacy comes from where rows live, not from filtering rows inside one log (research/06). The second rule is v0.4's: any device may ask, only the owner decides (v0.4 §6.0). It holds across people unchanged.

## 1. Scope

**What v0.4 already gives this design**
- **Identity:** a person key with a stable `personId`, device certs chained to a pinned root, revocation with a cut, and automatic rotation of the person key when a device is removed (v0.4 §2, §3, §5.5; decision 30).
- **Signed rows:** every row signed by its writing device; `Insert` verifies the cert, cut, HLC order and kind (v0.4 §5.3).
- **go-room:** pion data channels, signaling sealed with a room key, one `Signaler` per topic over every carrier (LAN, hubs), and `board/<boardId>` channel labels already reserved (v0.4 §4.3).
- **The home server:** the always-on PC runs a signaling hub, a TURN relay and port mapping, and publishes `node.addr` (decision 33, v0.4 §7.1).
- **The Board:** cards with steps, blockers with recommended answers, watchers, card threads, comments from the app, short refs, links and attachments (design/board.md).
- **Asks** (#3, in flight): a prompt from the window that reaches free agents, one claimer, a thread with the person, an outcome.

**In**
- Board logs, their kind allow-list and reference closure (§2).
- Identity across people: what another person trusts, and the one identity change that needs (§3).
- Invites, leaving, removal, lost devices and forgetting a board (§4).
- What crosses to other people and what never does; Share to board and Withdraw (§5).
- Transport and sync through the home servers (§6).
- Bridging board rows into the inbox, the receive setting (decision 24) and the autonomy setting (decisions 23, 26) (§7).
- The window: a board switcher and a Boards dialog, nothing else (§8).
- Asks on a board, and peer review requests (decision 29) (§9, §10).
- Tests and the build order (§11, §12).

**Out (later)**
- Encrypting board logs at rest or end to end beyond the transport. Dropped for now by B5 (§6.6): only if non-members ever carry boards.
- "Share this turn" extracts of capture (decision 32, 10b).
- Boards open to strangers, and any server outside the home (decisions 32, 33).
- Resuming another person's session, or any transcript crossing people.

## 2. Data model

### 2.1 One log per board

- **Your private log** stays `irori.db`, synced only among your own devices on the mesh topic, exactly as v0.4.
- **Each shared board** is `<dataDir>/boards/<boardId>.db`, opened by the existing `store` package with its own `Signer` and a board `Verifier` (§3). Same schema, same gapless per-device seq, same `Vector`, `Missing` and `Insert`. No change to the events primary key.
- **`boardId`** is 16 random bytes, hex, made by the device that creates the board. It names nothing.
- **One coord service per log.** coord already folds one store; the Core holds a map `boardId → coord` and a routing function from a taskId to its log (a task lives in exactly one log, and its id says nothing about which, so the Core keeps an index `taskId → boardId` built from each log's `task.created` rows). Tools and the window go through that one function. Table tests cover it, including a taskId that exists in no log.
- **The board's own rows** sit at the start of its log:

```
board.created        { boardId, name, tag, creator: { personId, personPub, rootDeviceId, personEpoch }, at, personSig }
board.renamed        { name, by, at, personEpoch, personSig }
board.member.added   { personId, personPub, rootDeviceId, personEpoch, name, role: "owner"|"member", by, at, personSig }
board.member.role    { personId, role, by, at, personEpoch, personSig }
board.member.removed { personId, by, reason, cut: { deviceId: boardSeq, ... }, at, personEpoch, personSig }
board.member.left    { personId, cut: { deviceId: boardSeq, ... }, at, personEpoch, personSig }
board.server         { deviceId, port, public: { ip, tcp, udp } | null, at }   // §6.2; owner-only: the server's device
```

`personSig` on board rows is the acting person's key, for the epoch named in `personEpoch`, over the canonical object (v0.4 §2's `canonical()`), so another person can check who did it (§3). `by` must be the writing device's person. `tag` is the short board handle used in refs (§2.5, and decision B3). Cuts on a board are seqs in **the board log's** stream for each device, never private-log seqs.

**The creator is the board's root.** `board.created` is self-signed by the creator's person key and pins the creator's identity, as v0.4 pins the root device. Every later `board.member.*` row counts only when its `by` was an owner at that point in the fold, so membership chains back to `board.created`. An invitee pins `board.created` from the bundle and checks, before joining, that the inviter's person key (proven in the SAS, §4.1) is an owner in that chain.

### 2.2 The kind allow-list

A board store accepts only these kinds, in `Append` and in `Insert`. Anything else is refused and counted, so a bug can't push capture, presence, inbox or policy rows into a board.

| Board log accepts | Never in a board log |
|---|---|
| `board.*` (above) | `message.sent`, `delivery.*`, `wake.issued`, `turn.*` (the inbox stays private; §7 bridges) |
| `member.profile`, `member.device.added`, `member.device.revoked`, `member.key.rotated`, written by each member's own devices (§3) | `agent.seen/status/gone`, `agent.alias`, `agent.name` (full cards: cwd, permission mode) |
| | `person.*` rows of the private log (a board gets its own `member.*` objects, §3) |
| `agent.card` (reduced, §2.4) | `capture.*`, `commit.*`, `repo.seen`, `pr.ledger`, `decision.recorded` |
| `task.created/claimed/assigned/status/joined/left/linked/comment/steps/step/watched` | `policy.set`, `member.joined`, `local.moved`, and every device-local kind |
| `blocker.closed/option/resolved` | `node.addr` (the board gets `board.server` instead, §6.2) |
| `lease.acquired/released/refused/stolen` on mirrored leases only (§5.4) | `ask.*` of the private log, `revive.requested`, `delivery.decided` |
| `attach.offered` | `task.shared` (it names a private task; Share writes a fresh `task.created`, §5.2) |
| `board.ask.*`, `review.*` (§9, §10) | |

The registry in `store/kinds.go` gains a third column, `Board`, so the existing table test that lists every kind also says, for each, whether a board log accepts it. A new kind can't ship unclassified for boards either. New kinds this design adds: the `board.*` and `member.*` rows above, `agent.card`, `board.ask.*` and `review.*` (board logs only); `board.joined`, `board.forgot`, `receive.set`, `autonomy.set`, and `board_cards` and `shared_copies` as the rows `board.cardof` and `board.sharedcopy` (private log, replicated among your own devices); and the device-local forgotten-board marker and the board's `board.pin` anchor (§12 step 4 notes).

### 2.3 Reference closure

A row in a board may reference only ids that exist in that board: taskIds, commentIds, blocker ids, lease ids, cardIds and attachment hashes offered in it. Commit SHAs and PR URLs are allowed, because git already makes them public. `Append` refuses a board row whose references point outside the board, with the reason, so an agent learns why. `Insert` doesn't check closure (a forwarder can't fix another device's rows, and the referenced row may still be on its way). The fold sets such a row aside as unresolved, re-checks it whenever a row that could resolve it arrives, and never applies it until then; the count of unresolved rows shows in `?detail=1`. Closure is about meaning, not authority: it never makes a device serve anything (§5.5).

### 2.4 Actors and agent cards

- **Board rows never carry `user`.** A person's own row on a board is actor `person:<personId>`, written only by the GUI (Wails bindings, as v0.4 §2 does for `user`). An agent's row is actor `agent:<cardId>`. `isOwner` is untouched: it accepts only `user:<deviceId>` for a device certified to *my* person, and no board row is ever `user:`. A test feeds a board row with actor `user:<anything>` and checks `Append` and `Insert` both refuse it.
- **Every actor is tied to the writing device.** The board Verifier resolves the writing device to its member person (§3) and refuses a row whose actor doesn't match: a `person:<id>` actor must be that person; an `agent:<cardId>` actor must name a card whose `agent.card` was written by a device of the same person; an `agent.card`'s `personId` must be the writer's person. So Blake's devices can't write as Stephen or mint a card that claims to be Stephen's agent.
- **The owner rule on a board means "a device of the owning person".** `owner.DeviceOf` can't place `agent:` or `person:` actors on a device (cardIds hide which device an agent runs on), so on a board log an owner-only kind (v0.4 §6.0) counts only when the writing device belongs to the owning person: a lease's holder's person for `lease.released/refused`, the asking person for an ask's take, the server's device for `board.server`. Within one person, the device rules of v0.4 still apply on the private side.
- **`agent.card {cardId, name, kind, personId, status}`** is the only trace of an agent in a board log. No cwd, path, deviceId, sessionId, permission mode, title or last text. `cardId` is random per (agent, board): the same session on two boards gets two cardIds, so boards can't be joined on it. Only the person's own devices know which session a card is, in `board_cards (boardId, cardId, agentKey)`: a private `board.cardof` row replicated among them, never on a board, so any of them can put any of the person's agents on a board and route a notice about its card (stage 1 is one person on several devices). Two devices that mint a card for one agent while apart settle on the lower cardId; both map back to the agent.
- A card is written the first time an agent touches a shared task (comments, joins, is assigned, takes a mirrored lease), and its `status` row (`active`, `idle`, `gone`) only when it changes. On the board it shows as "blake's agent `mlg-lead`".

### 2.5 Short refs on a board

board.md's short refs are derived per log: `task.created.num` is one more than the highest number the writing device has folded *in that log*. So on a shared board, Stephen's and Blake's devices share one count, and clashes settle by the same letters rule. A board's `#12` and the private board's `#12` are different cards, so refs need the board in them. Decided (B3, Stephen, 2026-10-28): the private board keeps bare `#12`; a shared board's card is `<tag>#12` (`mlg#12`), printed that way by every tool and the window, and accepted with or without the tag only where it is unambiguous across every log this device holds (an ambiguous bare number is refused naming each card, as a clash is today).

## 3. Identity across people

Inside your own mesh the person signature proves nothing the device signature doesn't (v0.4 §2), because every one of your devices holds the person secret. **Across people it is the whole trust.** Blake has no way to check your device chain except through your person key, and the reverse.

**What a board pins.** `board.created` pins the creator, and `board.member.added` pins each invitee's `{personId, personPub, rootDeviceId, personEpoch}` as proven in the SAS-confirmed invite (§4.1). **A member's board root is the device that proved itself, not the person's v0.4 root:** the creating device for the creator, and the device that ran the invite SAS for an invitee (the SAS binds its `devicePub`). So a person whose original v0.4 root was revoked and re-paired can still join boards. From then on, each member's identity in that board is a separate chain, seeded from that row.

**A board's own identity rows.** Private-log `person.*` rows can't simply be copied: their cuts are private-log seqs, which mean nothing in a board log, and v0.4's chain rule checks the row's *writer*, which for a copy would be the copying device. So each member's devices write board-scoped objects, signed by the person key, into each board:

```
member.device.added   { cert: { personId, deviceId, devicePub, role, personEpoch, at }, personSig }   // no label
member.device.revoked { revoke: { personId, deviceId, boardCut, boardCutHash, personEpoch, at }, personSig }
member.key.rotated    { personId, personEpoch, personPub, by: deviceId, at, prevSig }
member.profile        { personId, name, personEpoch, personSig }
```

The board Verifier runs v0.4's rules on them, inside the board log:
- **Chain to the pinned root.** A `member.device.added` counts only when its writing device holds a counted cert of the same person, or it is the root device's self-cert from the pin. A device can't certify itself.
- **Epochs.** A person-signed object counts only when `personSig` verifies against that member's key for the `personEpoch` it names, and either that epoch is the member's newest accepted one, or the row's HLC is below the HLC of the accepted rotation that ended that epoch. Rows signed before the rotation stay valid; a new object signed with an older key does not (HLCs are signed and only move forward per device, and a row more than two minutes ahead waits, v0.4 §5.6).
- **Revokes and cuts.** `boardCut` is the highest seq of the revoked device's stream **in this board log** that the revoking device holds. The min-cut rule, `refused_events` and the cut-capped `Vector` work exactly as v0.4 §5.5, per board. A revoke counts if its writer was ever validly certified in the board, so a mutual revoke removes both, as in v0.4.
- **Rotation.** `member.key.rotated` must carry `prevSig`, the previous epoch's key over `canonical({personId, personEpoch, personPub, by, at})`, and must be written by the device named in `by`. Two rotations to one epoch take the one whose `by` is the lower device id. A rotation whose `by` device is revoked in the board is discarded wherever it sits, so a thief that rotates first and is then revoked doesn't win the key. If a thief and your device revoke each other, both rotations are discarded and that person's devices can write nothing new on the board until an owner removes and re-invites them (v0.4's "make a new person" case, on a board).
- Everything else in v0.4 §5.3 applies unchanged: row signatures against the cert's `devicePub`, per-device HLC order, two minutes ahead, forks.

**Your private mesh needs the same fields.** `person.key.rotated` carries only the new public key today (`identity.KeyRotated`), and certs carry no epoch (`identity.Cert`). A device can only write a board's `prevSig` and `personEpoch` if it knew them when the rotation happened, so the private rows gain `prevSig`, `by` and `personEpoch` too (the own mesh ignores them in its checks). This touches `internal/identity`, which card #18 has open; the requirement is passed to its holder rather than changed here.

**Keeping boards current.** Whenever one of your devices adds, revokes or rotates in the private log, the Core writes the matching `member.*` object into every board your person is in, with a cut over that board's stream. When a new device joins your mesh, a device of yours that already holds a counted cert in each board (normally the one that paired it) writes its cert there, so Blake's boards learn your new laptop through one cert, and a revoked laptop is cut from every board at once (research/06).

**What the other person sees of your devices.** Each board cert carries a `deviceId`, a `devicePub` and a role, with no label. Members can count your devices and see when one is added or removed. That is the price of them checking your rows (raised under B1).

**A stolen device.** It holds the person secret, so until you revoke it, it can sign certs and membership rows on every board you are in. The controls are v0.4's: one-click revoke from another device, the per-board cut honoured by every member, rotation with `prevSig` that a revoked device can't win, and each member's device count on the member panel.

## 4. Invites, leaving and removal

### 4.1 Invite

The inviter is an owner (decision 32, 7b). Invite is GUI-only, like Add a device.

1. **Stephen: Boards → a board → Invite.** The Core opens an invite window (one use, at most 1 hour, so it fits a call), makes a code with go-room's `NewCode()`, derives an invite room from it (`room.SecretFromCode("irori-invite-v1", code)`), registers that room as a guest topic on his home server, and shows an **invite link**: `irori-invite:<code>@<server host:port>#<person fingerprint>`. The fingerprint is a short hash of Stephen's current person public key. This changes the hub's guest-topic rule (v0.4 §4.2): an invite topic may live up to 1 hour, at most 2 invite topics per member beside the 2 pairing topics. Decided (B4, Stephen, 2026-10-28): the link is pasted, and step 5's words and fingerprints are read aloud on a voice call.
2. **Stephen sends it to Blake** over Discord or anything else. Agents that read the chat can see it; the steps below are what make that harmless.
3. **Blake: Boards → Join with an invite.** He pastes it. His Core dials Stephen's hub as a guest at that address and opens the invite room, and the two connect through go-room's handshake. Stephen's side takes the first device that proves the code; a second one closes the window (v0.4 §3, step 5).
4. **Both prove their person keys.** Each side signs the invite room's SAS info (v0.4 §3's HKDF, with both person keys added to `info`) with its person key. Blake's Core checks that the proven key matches the fingerprint in the link, and that it is an owner in the bundle's membership chain (§2.1). Both screens show both names and both person fingerprints. If either person is already pinned on another board this device holds, and the key differs, the screen says so in red and the join can't continue.
5. **They confirm each other.** Blake reads the five words to Stephen, who types them, as pairing does; and each reads out the other's fingerprint from their own screen. Done over a voice call, this is what stops someone who controls the chat from posing as Stephen with a forged link of their own: the forged link's fingerprint and words won't match what Stephen says.
6. **Stephen's device writes `board.member.added`** for Blake with `role: member`, signed with Stephen's person key, and sends Blake the board bundle: the board's whole log so far (membership, each member's `member.*` rows, `board.server` rows, cards) and the board secret for its epoch (§6.1). Blake's Core creates `boards/<boardId>.db`, inserts the bundle, writes Blake's own `member.*` rows (§3), and joins the board topic. Both close the invite room.
7. **Blake's other devices** learn the board from Blake's private log: the Core writes a private `board.joined {boardId, name, tag}` row (replicated kind, own mesh only) and hands the board secret to Blake's other devices in a `board.secret` frame on the own-mesh sync channel, as `person.secret` travels (v0.4 §5.2). They then join the board topic themselves.

The invitee's receive setting starts at Open and the board's autonomy at Trusted (decisions 24, 26). Who joins is the inviter's call; Irori adds no warning (decision 24).

### 4.2 Owners

- Any owner invites, removes and changes roles. There may be several owners, so a board isn't orphaned when one person loses their devices (decision 32, 7b).
- `board.member.role` makes someone an owner or takes it away. The last owner can't demote themselves.
- **Removal is sticky.** The membership fold runs in `(hlc, device, seq)` order, except that once a person is removed (or has left), every role row and every membership row by them is ignored until a `board.member.added` for them with a higher HLC, by an owner. So when one owner removes Carol and another promotes her while apart, the removal stands in every arrival order. An ignored role row shows to the owners as one conflict line in the Boards dialog (research/01 §5), so the owner who promoted her sees it didn't take.

### 4.3 Removal

- **An owner removes a member** (GUI only): `board.member.removed {personId, by, reason, cut}`, where `cut` holds, for each of that person's certified devices, the highest seq of its stream in this board log that the remover holds. The remover's own view decides; every member then refuses exactly the same rows whenever they hear of it, so folds agree (research/06; same mechanism as v0.4 §5.5).
- Rows above the cut that a member already holds move to `refused_events` and show as "N rows after removal". Nothing folds them.
- **Cleanup**, by the remover's Core: the removed person's agents are unassigned, their mirrored leases are released with `reason: member_removed`, and any bridged deliveries from them still waiting (§7.1) move to held.
- **The board secret rotates** (§6.1), so the removed person's devices can't follow the board's signaling, and every member's hub drops them.
- **The dialog says plainly:** "Blake keeps everything already on his devices. Removing him stops him syncing and writing anything this board accepts."

### 4.4 Leaving

`board.member.left` is written by the leaving person's own device, with a cut over their own devices' streams in the board. Its effect on everyone else is a removal. The board shows "Leaving…" until some other member's vector covers the `left` row (or the person picks "Forget now", which says the others may not hear of it), and only then forgets the board (§4.6), so the row isn't lost with the file.

### 4.5 Lost or stolen device

Revoking a device in Settings → Devices (v0.4 §3) writes the revoke to the private log, and §3 writes a `member.device.revoked` with a per-board cut into every board log. Rows from that device above the cut are refused on every board, by every member, and the board secret rotates (§6.1).

### 4.6 Forgetting a board

Forgetting deletes `boards/<boardId>.db` and the board's secrets on this device, and records the boardId in a device-local forgotten list, so a later `board.joined` row arriving from another of your devices doesn't bring it back. It doesn't make the board forget you: other members still see you until you leave or are removed. Leave forgets on every one of your devices, through a private `board.forgot` row that each of them applies. Re-joining needs a new invite.

## 5. What crosses and what never does

### 5.1 The three columns

| Private (your log, your devices only) | Shared (only by being written to a board log) | Never leaves the device |
|---|---|---|
| Presence and full agent cards (cwd, permission mode, title) | `board.*` membership and `board.server` | Raw transcripts, Tier 2 bodies |
| Every inbox message and delivery, including bridged ones (§7.1) | `member.*` profile, device certs (no labels) and revokes, rotations | Person and device secret keys; board secrets are never in a row and go only to member devices in frames (§6.1) |
| Capture Tier 0 and 1: turns, edits, commits, PR ledger, ai-titles | Tasks created on or shared to the board, their comments, steps, blockers, watchers and links | Policy rows and allow-lists, Pause all |
| Your receive and autonomy settings (`receive.set`, `autonomy.set`) | | |
| Private tasks, private leases | Reduced `agent.card`s of agents that touched a shared task | `irori.json` and its token, attach and member secrets, `turn.key` |
| `node.addr` (your server's full address row) | Mirrored leases (§5.4) | Patch blobs, `capture-cursors.json` |
| The private `board.joined`/`board.forgot` rows, and `board_cards`/`shared_copies` (`board.cardof`, `board.sharedcopy`) | Commit SHAs and PR URLs that shared cards cite | Petnames |
| | Attachments put on a shared card or comment | |

Nothing moves from the left column to the middle except through a write to a board log, and every such write is either a person in the GUI or an agent under its person's autonomy setting (§7.3).

### 5.2 Share to board

"Share to board" is on a private card in the window (GUI), or requested by an agent (§7.3).
1. Irori re-runs `internal/scrub` and a stricter pass that drops absolute paths and home directories from the title, objective, done-when, steps and links.
2. It shows exactly what will be written, with "Visible to: Stephen, Blake", and the person confirms.
3. It writes a fresh `task.created` in the board log with the scrubbed fields and its steps. The private history (comments, status notes, blockers) stays private. A link `shared_copies (privateTaskId, boardId, taskId)`, a private `board.sharedcopy` row replicated among your own devices, lets the private card show "Shared to mlg as mlg#4" and the window show them as one card, on every one of your devices.
4. The private card is closed with a note pointing at the shared copy, and its holders are told at their next turn. **Writes to the private id are refused, never rerouted:** the error names the shared card (`mlg#4`) and who it is visible to, so an agent re-sends deliberately and a private status note can't be published by accident.

### 5.3 Withdraw

On a shared card the creator or an owner can Withdraw: `task.status canceled, withdrawn: true`. The fold accepts a cancel on a shared card (withdrawn or not) only from a device of the creator's person or of an owner, so another member can't cancel your card. Other members hide the card, and its holders on your side carry on in a new private card. The dialog says: "Blake's devices already have what was shared." Nothing can be recalled.

### 5.4 Leases across people

Decision 32 (6a): only leases of agents working shared tasks are mirrored. With boards no longer bound to a repo, "the board's repos" becomes **the shared task's repo**:
- when an agent that holds (or has joined) a shared task acquires a lease on a resource in that task's repo, its Core writes the same `lease.acquired` into the board log, with the holder shown as its `agent.card`;
- a shared task without a repo mirrors no leases;
- release and expiry mirror the same way. On the board, `lease.released` and `lease.refused` count only from a device of the holder's person (§2.4); on the holder's own side, v0.4's device rule decides;
- **nobody steals another person's lease.** `lease.stolen` in a board log counts only when its actor is a person whose agent holds the lease. Another person's "close" on a lease card sends the holder a next-turn release request through §7.1;
- two people's agents taking overlapping leases while apart both succeed locally; when the rows meet, the lease of the lower device id stands and the other holder's Core writes `lease.refused` and tells its agent (v0.4 §6.4's rule, not research/06's HLC rule, so a clock can't win it);
- a refused or conflicting lease shows as a lease card on the board, as it does privately.

Git conflicts stay the last line of defence. A lease never says what private work runs in a shared repo, because only shared-task holders' leases cross (decision 32 rejected mirroring all leases).

### 5.5 Attachments

Files on shared cards and comments use v0.4 §6.6 unchanged, with a board-scoped fetch: on a board connection, a device serves a hash only when **one of its own person's devices** wrote the `attach.offered` for it in that board, or it fetched that hash for that board itself. A reference written by someone else never makes your device serve a file, so a member who knows or guesses a private file's hash can't pull it. The 256 MiB cap holds. The never-leave rules on the source path (data dir, `.env*`, private keys, credential stores) apply before anything is copied.

## 6. Transport and sync

### 6.1 The board topic and its secret

Each board has a **board secret**, 32 random bytes made at `board.created`, per epoch:

```
boardSecret(boardEpoch)   random 32 bytes; held by every member device; never in a row
topicKey             = HKDF-SHA256(ikm = boardSecret, salt = "irori/board/1", info = boardId || boardEpoch)
                     → 32-byte sealing key || 16-byte topic suffix
topic                = "irori/board/1/" + hex(suffix)
```

- It is the board's go-room room key: it seals the board's signaling envelopes on every carrier, exactly as the person secret seals the mesh topic (v0.4 §4.2).
- It travels only inside connections whose peer is already authenticated: in the invite bundle (§4.1), to your own other devices in a `board.secret` frame on the own-mesh sync channel, and after a rotation in a `board.secret` frame on each board connection, only to current members' devices.
- **It rotates on every removal, every leave, and every revoke of a member's device.** A device of an owner, or of the person whose device was revoked, that folds one of those rows makes the next `boardEpoch`'s secret and sends it to every remaining member device. Two devices rotating to one `boardEpoch` while apart take the lower device id's secret. Devices keep the previous epoch's topic open until every member device has said `hello` with the new one, as v0.4 does for the person epoch. Until then a removed person or a stolen device that is on the same LAN as a member can still read that member's sealed signaling (its candidate addresses), the same residual v0.4 §4.2 accepts.
- It is not a log key. Board rows are not encrypted beyond DTLS (decision 32, 11a); §6.6 says what changes for a third person.

### 6.2 Which hubs a board uses

Decision 33's hub admits only your own certified devices and pairing guests. A shared board needs at least one hub that admits another person's devices; otherwise Stephen at home and Blake at his home have no way to exchange an offer. Decided (B1, Stephen, 2026-10-28): every member's server admits that board's members, for that board only, with limited relay:

- **Every member's home server serves that board's topic to that board's members.** Its hub's `Authorize(id, pub)` answers yes for a device with a counted, unrevoked cert from a current member of any board the server's Core holds, and `AllowTopic` for such a client is only the topics (current and previous epoch) of the boards its person is a member of. It can't subscribe to your mesh topic, open guest topics, or see any other board.
- **Each server announces itself to its boards** with `board.server {deviceId, port, public}`: the public address and mapped ports only, never the LAN addresses or v6 list in `node.addr`. It is written by the server device into each board its person is in, only when it changes, and `{public: null}` when the server is off or outside reach is off. A member's devices dial every `board.server` of the boards they are in, in parallel, keep the first handshake per server, and back off as the hub client does today.
- **One Signaler per board topic,** with every carrier the device has for it: the LAN carrier (two members' devices on one network find each other with no server), its own home server's hub, and every other member's server from `board.server`. Envelopes are de-duplicated as they are today.
- **TURN for other people is narrow.** A member of a board gets `turn.creds` with guest-scoped rights (v0.4 §4.4): its allocation may send only to the server's own relayed addresses, never to the home LAN. Your own devices reach it through their own relayed candidates on the same server, relay to relay inside the PC. Limits per remote person: 4 allocations, inside the server's total. (On iroh there are no allocations, one relay client per device, so this limit is not carried over; see boards2-transport.md §6.)
- **The always-on node stores and forwards** every board its person is in (decision 32, 9a). Signatures mean it can't forge Blake's rows; it carries them to your Mac and yours to Blake while either is offline.

What other people learn: your home server's public address and port, from `board.server`; your devices' current addresses (public, and LAN host candidates), from the board's signaling; and, on your hub, the source addresses their devices connect from. That is the exposure decision B1 asks about. Host candidates could be left out of board offers, at the cost of two members on one LAN relaying through a server; this design keeps them.

### 6.3 Connections

- **One go-room `Mesh` per board topic,** so one `PeerConnection` per (device, device, board). A connection opened on board A's topic opens only a `board/<boardId>` sync channel for A, and its `Accept` checks the peer's `devicePub` against a counted cert of a current member of A. It can never serve your private log or another board.
- **Your own devices meet on each board topic too** (they are member devices), and sync that board's log with each other there. One rule, "a board's rows move only on its own connections", is easier to check than a board channel riding the private mesh connection.
- **What several boards with one person cost:** with three boards shared with Blake, each pair of your device and his device that are both up holds three connections, one per board. Each is idle until a row moves, keeps a 15 s ping, and goes through the same ICE path. Removing Blake from one board closes exactly that board's connections and touches nothing else.
- **Who offers:** the lower device id, as in v0.4 §4.2, compared across people the same way (device ids are random).
- **Version:** each board connection's `hello` carries `coreVersion` and a board protocol version. A mismatch is refused with `peer.down reason: "version"`, and the board's member panel says whose Irori to update (research/06 version skew).

### 6.4 The sync protocol on a board

The frames are v0.4 §5.2's, against the board store: `hello {v, deviceId, personId, boardId, boardEpoch, coreVersion, schema, vector, wallMs}`, `rows`, `vector`, `ping/pong`, and `board.secret {boardEpoch, sealed}` in place of `person.secret`.
- **`board.*` and `member.*` rows go first** on catch-up, since the Verifier needs membership and certs before a member's other rows.
- A row held for "no cert yet" waits per peer under the same cap (2,000 rows or 8 MiB).
- **Any member device may forward any member's rows.** The Verifier checks the writing device, not the sender.
- **A stalled forwarder** (a peer whose vector stops advancing for one member's stream while that member's other devices are ahead) is flagged on the member panel (research/06).

### 6.5 With the servers off

- Two members' devices on one network sync over the LAN carrier with every server off.
- A device away from home reaches a board when any member's server is reachable and admits it (B1). With every member's server unreachable, it can't, and the board's line in the Boards dialog says so ("Can't reach any home server for mlg").
- Connections already up survive a server going away, as in v0.4.

### 6.6 When a board gets a third person

Decision 32 (11a) says board logs get encryption beyond the transport once a board has a third person. research/06's reason was forwarders that aren't trusted. In this design no non-member ever forwards or stores a board's rows: a hub admits only members, and a connection carries a board only between members. With three people, what a board key that rotates on removal would add is narrow: rows written after a removal are unreadable by the removed person even if a member's device leaked them, and a board file copied off a member's disk is unreadable without the key. Decided (B5, Stephen, 2026-10-28): the rule is dropped. Boards of any size carry no row encryption beyond DTLS; encryption comes back only if machines that aren't members ever carry boards. The board secret (§6.1) stays separate from any future log key.

## 7. How work reaches other people

### 7.1 The bridge into the inbox

Board rows wake nothing on their own. When a comment, assignment, blocker change or ask arrives on a board for a task one of your local agents holds, watches or is assigned, **the device that hosts that agent** writes an ordinary private `message.sent` plus a delivery to it:
- **the sender key is its own kind:** `board:<boardId>/<cardId>` for another person's agent and `board:<boardId>/person:<personId>` for another person. It is never `user:`, never `<deviceId>/<session>`, so `isOwner` and decision 34's own-agent skip can never match it, whichever device wrote the bridged row. Each policy check (bypass hold, block list, rate limit) sees it as another person;
- it shows as `blake` or `blake's agent mlg-lead`, fenced `<irori-message from="blake" trust="untrusted" board="mlg">`. Other people's text is always untrusted to your agents; your own agents' rows on the board arrive as they do today;
- the message carries `ref: {boardId, deviceId, seq}` and `Ref: task:<id>`, so it lands on the card's thread like any message about a card (board.md "Card threads");
- **only the hosting device bridges,** and the bridge is idempotent on `ref`. Your Mac and your node both hold the board log and never deliver one row twice;
- your own agents' writes on a board task go through the same path to your other agents, so there is one delivery route.

**The hop limit crosses the bridge.** Board rows that agents write (`task.comment`, `task.assigned`, blocker rows, board asks) carry `hop`: the hop of the delivery the writing agent's current turn is running on, plus one, as `send` sets it today from the agent's running wake. The bridge gives its private message that hop. So two people's agents waking each other stop at the hop limit (50 since decision 37; it was 6), as decision 24 requires, and the per-pair rate limit also counts per (remote person, board).

**Replies go back on the board.** An agent's `reply` to a bridged message, or a `send` naming a `board:` key, becomes a `task.comment` on that card in the board log (or the ask's thread), with scrub, the stricter pass and the "Visible to" line. Nothing an agent sends to another person travels as a private message.

Every v0.2 §5 and v0.4 §6.3 rule then applies on the host: block list, Pause all, the hop limit (50, a runaway-loop guard), the per-pair rate limit, and the host deciding holds. Reviving a closed session because of another person's row always asks the person first (an approval notification, decision 26).

### 7.2 Your receive setting (decision 24)

Per board and per person, set only in the app. Rows: `receive.set {boardId?, personId?, preset?, switches}` in your private log, actor `user` only, **replicated among your own devices** so the PC and the Mac apply one setting (decisions 23 and 24 describe one setting per person; v0.4's `policy.set` stays device-local, and Pause all stays per device). Each host reads it when it decides a hold.

| From other people on the board… | Closed | Ask me | Members wake | **Open (default)** |
|---|---|---|---|---|
| Their comments, blocker changes, assignments | Next turn | Next turn | Next turn | Next turn |
| A request to wake one of your agents | Next turn, marked "asked to wake" | Held for you | Wakes it (people you pick) | **Wakes it** |
| Their agents asking to wake yours | Next turn | Held | Wakes it (picked people's agents) | **Wakes it** |
| Rows to your bypass sessions | Held | Held | Through, for picked people | **Through** (B2, decided) |
| Their agents assigning work to yours | Next turn | Held | Next turn, or a wake if asked | **Next turn, or a wake if asked** |

- **"Held"** uses the hold reasons research/06 named: `member_wake`, `cross_person`, `member_lease`. A held row reaches you as a notification card (one per sender, decision 34's coalescing), with Release and Dismiss.
- **Bypass sessions on Open** (B2, Stephen, 2026-10-28): Open lets other people's rows through to your bypass sessions; Ask me and Closed hold them. This settles decision 34's "the hold stays for other people's agents": it is the hold under Ask me and Closed, not under Open (decision 35).
- The guards stay on under every setting: hop limit, rate limit, Pause all. There is no token budget (decision 24).
- Assignments follow the receive setting (decision 32), so on Open they arrive like comments.

### 7.3 Your agents' autonomy (decisions 23, 26)

Per board, set only in the app. Rows: `autonomy.set {boardId?, preset?, switches}` in your private log, actor `user` only, replicated among your own devices like `receive.set`.

| Your agents may… | Ask me | **Trusted (default for new boards)** | Autonomous |
|---|---|---|---|
| Comment, raise and close blockers, tick steps, work shared tasks | Yes | Yes | Yes |
| Create new cards on the board | Request (notification) | **Yes** | Yes |
| Share one of your private cards to the board | No | **Request (notification: Share / Review / No)** | Yes, after scrub; you get a notice with Withdraw |
| Assign work to other people's agents | Yes | **Yes** | Yes |
| Mirror all their leases in shared tasks' repos (not only shared-task holders') | No | **No** | Yes |
| Ask to wake another person's agents | Asks; their receive setting decides | Same | Same |

- **A request is a notification, not chat** (decision 26): in front of other programs, on every device you are on, with its buttons, cleared everywhere once answered. The requesting agent doesn't wait; the answer reaches it at its next turn. It is written as the existing `ask.posted` in your private log, so it already shows and clears on every device (v0.4 §6.7).
- **What the setting can't change:** what others may do to your agents (that is your receive setting, and Blake's autonomy never overrides it); who changes it (the app only, never a tool); and what never leaves the device (§5.1 right column, under every preset).
- **Where an agent's new card goes.** `board_create` gains `board` (a tag or boardId). Without it the card is private, always. The board tool lists the boards the agent may post on, with their members. A card created on a shared board, and every tool result that wrote to one, ends with "Visible to: Stephen, Blake". If scrub or the stricter pass blocks a write, the result names the pattern that matched, so the agent can rephrase.
- **Text caps** as today: title 200, objective and comment 4000.

### 7.4 Who can do what on a board

| Action | A person (in their own app) | Their agents | Another person's agents |
|---|---|---|---|
| Create a card on the board | Yes | Per their autonomy | Per their own person's autonomy |
| Share a private card | Yes, with preview | Per autonomy (request by default) | No |
| Comment, raise or close a blocker, tick steps | Yes | Yes | Yes (decision 19) |
| Join and work a shared card | Yes | Yes | Yes, guarded by mirrored leases |
| Assign a card to an agent | Yes, to any card on the board | Yes | Yes; delivered per the receiver's setting |
| Wake an agent now | Own agents; others' per their receive setting | Same | Same |
| Steal a lease | Own agents' only | No | No (a release request instead) |
| Withdraw or cancel a shared card | Its creator or an owner | Its creator's agents, if the creator is their person | No |
| Invite, remove, change roles, rename | Owners only | No | No |
| Change receive or autonomy settings | Own only | No | No |
| Read capture, transcripts, rosters, inbox | No; only what is on the board | No | No |

A removal or leave is honoured past its writer's cut only when that cut came from its person's removal or leave, never from a device its own person revoked, and never stamped before its writer's last row.

Encryption for boards with a third person.** *Decided 2026-10-28: (a).* Decision 32 (11a) says encrypt board logs once a board has a third person, because research/06 expected forwarders that aren't members. This design never lets a non-member forward or store a board. A board key would only protect rows after a removal if a member leaks them, and board files copied off a member's disk. Recommended: (a) drop the rule; encrypt only if non-member forwarders ever appear. (b) Build a board key that rotates on removal before any board takes a third person. (c) Cap boards at two people until (b) is built.
