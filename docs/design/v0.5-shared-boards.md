# v0.5 "Shared Boards": design

*2026-10-28. Builds on v0.4 as it is on `main` (591a6e8). Inputs: research/06-multi-person.md, decisions 23–34, design/v0.4-devices.md, design/board.md, and the asks work on card #3 (in flight). Where this doc and research/06 disagree, this doc wins: research/06 was written for an iroh sidecar, n0 relays and boards bound to a repo, and decisions 31–33 and 32 replaced all three. Open questions for Stephen are at the end and raised as blockers on card #17.*

v0.5 lets Stephen put work on a board that other people see. A **shared board** is a named group of people around any topic: the people you invite, and their agents. Your **private board** is what Irori is today: your own devices, nobody else. There are no public boards. You can have several shared boards, several of them with the same person, and each is separate from the others and from your private board (decision 32).

**One rule runs through the design: a board is its own log, in its own file, carried only on its own connections.** A shared board's rows live in `boards/<boardId>.db`, they only ever travel on connections opened for that board, and only devices certified to a member person may open one. Privacy comes from where rows live, not from filtering rows inside one log (research/06). The second rule is v0.4's: any device may ask, only the owner decides (v0.4 §6.0). It holds across people unchanged.

## 1. Scope

**What v0.4 already gives this design**
- **Identity:** a person key with a stable `personId`, device certs chained to a pinned root, revocation with a cut, and automatic rotation of the person key when a device is removed (v0.4 §2, §3, §5.5; decision 30).
- **Signed rows:** every row signed by its writing device; `Insert` verifies the cert, cut, HLC order and kind (v0.4 §5.3).
- **go-room:** pion data channels, signaling sealed with a room key, one `Signaler` per topic over every carrier (LAN, hubs), and `board/<boardId>` channel labels already reserved (v0.4 §4.3).
- **The home server:** the always-on PC runs a signaling hub, a TURN relay and port mapping, and publishes `node.addr` (decision 33, v0.4 §7.1).
- **The Board:** cards with steps, blockers with recommended answers, watchers, card threads, comments from the app, short refs, links and attachments (design/board.md).
- **Asks** (#3, in flight): a prompt from the window that reaches free agents, one claimer, a thread with the person, an outcome.

**In**
- Board logs, their kind allow-list and reference closure (§2).
- Identity across people: what another person trusts, and the one identity change that needs (§3).
- Invites, leaving, removal, lost devices and forgetting a board (§4).
- What crosses to other people and what never does; Share to board and Withdraw (§5).
- Transport and sync through the home servers (§6).
- Bridging board rows into the inbox, the receive setting (decision 24) and the autonomy setting (decisions 23, 26) (§7).
- The window: a board switcher and a Boards dialog, nothing else (§8).
- Asks on a board, and peer review requests (decision 29) (§9, §10).
- Tests and the build order (§11, §12).

**Out (later)**
- Encrypting board logs at rest or end to end beyond the transport. Decision 32 (11a) defers it until a board has a third person; §6.6 says what changes then.
- "Share this turn" extracts of capture (decision 32, 10b).
- Boards open to strangers, and any server outside the home (decisions 32, 33).
- Resuming another person's session, or any transcript crossing people.

## 2. Data model

### 2.1 One log per board

- **Your private log** stays `irori.db`, synced only among your own devices on the mesh topic, exactly as v0.4.
- **Each shared board** is `<dataDir>/boards/<boardId>.db`, opened by the existing `store` package with its own `Signer` and a board `Verifier` (§3). Same schema, same gapless per-device seq, same `Vector`, `Missing` and `Insert`. No change to the events primary key.
- **`boardId`** is 16 random bytes, hex, made by the device that creates the board. It names nothing.
- **One coord service per log.** coord already folds one store; the Core holds a map `boardId → coord` and a routing function from a taskId to its log (a task lives in exactly one log, and its id says nothing about which, so the Core keeps an index `taskId → boardId` built from each log's `task.created` rows). Tools and the window go through that one function. Table tests cover it, including a taskId that exists in no log.
- **The board's own rows** sit at the start of its log:

```
board.created        { boardId, name, tag, createdBy: personId, at }
board.renamed        { name, by, at }
board.member.added   { personId, personPub, rootDeviceId, epoch, name, role: "owner"|"member", by, at, personSig }
board.member.role    { personId, role, by, at, personSig }
board.member.removed { personId, by, reason, cut: { deviceId: seq, ... }, at, personSig }
board.member.left    { personId, cut: { deviceId: seq, ... }, at, personSig }
board.server         { deviceId, port, public: { ip, tcp, udp } | null, at }   // §6.2
```

`personSig` on membership rows is the acting person's key over the canonical object (v0.4 §2's `canonical()`), so another person can check who did it (§3). `tag` is the short board handle used in refs (§2.5, and decision B3).

### 2.2 The kind allow-list

A board store accepts only these kinds, in `Append` and in `Insert`. Anything else is refused and counted, so a bug can't push capture, presence, inbox or policy rows into a board.

| Board log accepts | Never in a board log |
|---|---|
| `board.*` (above) | `message.sent`, `delivery.*`, `wake.issued`, `turn.*` (the inbox stays private; §7 bridges) |
| `person.profile`, `person.device.added`, `person.device.revoked`, `person.key.rotated`, copied in by each member's own devices (§3) | `agent.seen/status/gone`, `agent.alias`, `agent.name` (full cards: cwd, permission mode) |
| `agent.card` (reduced, §2.4) | `capture.*`, `commit.*`, `repo.seen`, `pr.ledger`, `decision.recorded` |
| `task.created/claimed/assigned/status/joined/left/linked/comment/steps/step/watched` | `policy.set`, `member.joined`, `local.moved`, and every device-local kind |
| `blocker.closed/option/resolved` | `node.addr` (the board gets `board.server` instead, §6.2) |
| `lease.acquired/released/refused/stolen` on mirrored leases only (§5.4) | `ask.*` of the private log, `revive.requested`, `delivery.decided` |
| `attach.offered` | `task.shared` (it names a private task; Share writes a fresh `task.created`, §5.2) |
| `board.ask.*`, `review.*` (§9, §10) | |

The registry in `store/kinds.go` gains a third column, `Board`, so the existing table test that lists every kind also says, for each, whether a board log accepts it. A new kind can't ship unclassified for boards either.

### 2.3 Reference closure

A row in a board may reference only ids that exist in that board: taskIds, commentIds, blocker ids, lease ids, cardIds and attachment hashes offered in it. Commit SHAs and PR URLs are allowed, because git already makes them public. `Append` refuses a board row whose references point outside the board, with the reason, so an agent learns why. `Insert` doesn't check closure (a forwarder can't fix another device's rows), but the fold ignores and counts a row whose reference it can't resolve after catch-up.

### 2.4 Actors and agent cards

- **Board rows never carry `user`.** A person's own row on a board is actor `person:<personId>`, written only by the GUI (Wails bindings, as v0.4 §2 does for `user`). An agent's row is actor `agent:<cardId>`. `isOwner` is untouched: it accepts only `user:<deviceId>` for a device certified to *my* person, and no board row is ever `user:`. A test feeds a board row with actor `user:<anything>` and checks `Append` and `Insert` both refuse it.
- **`agent.card {cardId, name, kind, personId, status}`** is the only trace of an agent in a board log. No cwd, path, deviceId, sessionId, permission mode, title or last text. `cardId` is random per (agent, board): the same session on two boards gets two cardIds, so boards can't be joined on it. Only the agent's own Core knows which local session a card is, in a device-local table `board_cards (boardId, cardId, agentKey)`.
- A card is written the first time an agent touches a shared task (comments, joins, is assigned, takes a mirrored lease), and its `status` row (`active`, `idle`, `gone`) only when it changes. On the board it shows as "blake's agent `mlg-lead`".

### 2.5 Short refs on a board

board.md's short refs are derived per log: `task.created.num` is one more than the highest number the writing device has folded *in that log*. So on a shared board, Stephen's and Blake's devices share one count, and clashes settle by the same letters rule. A board's `#12` and the private board's `#12` are different cards, so refs need the board in them. How they look is decision B3. The recommended form: the private board keeps bare `#12`; a shared board's card is `<tag>#12` (`mlg#12`), printed that way by every tool and the window, and accepted with or without the tag only where it is unambiguous across every log this device holds (an ambiguous bare number is refused naming each card, as a clash is today).

## 3. Identity across people

Inside your own mesh the person signature proves nothing the device signature doesn't (v0.4 §2), because every one of your devices holds the person secret. **Across people it is the whole trust.** Blake has no way to check your device chain except through your person key, and the reverse.

**What a board pins.** `board.member.added` records the invitee's `{personId, personPub, rootDeviceId, epoch}` as seen in the SAS-confirmed invite (§4.1). From then on, each member's identity in that board is a separate chain, seeded from that row.

**How a member's devices become valid in the board.** Each member's own devices copy that member's `person.*` rows into the board log: `person.profile`, every `person.device.added` and `person.device.revoked`, and every `person.key.rotated`. The rows are written (and row-signed) by the copying device, but what the board trusts is the person-signed object inside:
- a `person.device.added` cert counts when its `personSig` verifies against that member's person key **for the cert's epoch**;
- a revoke counts on the same test, and its cut works exactly as v0.4 §5.5 (min cut, `refused_events`, cut-capped `Vector`);
- the board Verifier then accepts a row from a device when it holds a counted, unrevoked cert from a current member, the row signature matches the cert's `devicePub`, and the row is under any cut. Everything else in v0.4 §5.3 applies unchanged (HLC order, two minutes ahead, forks).

**Rotation needs one new field.** `person.key.rotated` carries only the new public key today (`identity.KeyRotated`; `internal/identity/rotate.go`), which is fine inside your mesh where the device chain vouches for it. Another person can't check that. So it gains `prevSig`: the previous epoch's person key signing `canonical({personId, epoch, personPub, at})`. A board accepts a rotation only with a valid `prevSig` from the epoch it already trusts, then trusts the new key. Your own mesh ignores the field. Two rotations to one epoch (two of your devices revoking while apart, v0.4 §3) are both signed by the previous key, and the board takes the same winner your mesh does (the row from the lower device id, then the lower seq). This touches `internal/identity`, which card #18 has open; the requirement is passed to its holder rather than changed here.

**Copies stay current.** Whenever one of your devices appends a `person.*` row to the private log, the Core appends the same signed object to every board log your person is a member of. A device that joins your mesh later copies its cert into each board on its first start, so Blake's boards learn your new laptop through one cert and a revoked laptop is cut from every board at once (research/06).

**What the other person sees of your devices.** Each copied cert carries `deviceId`, `devicePub` and `label` ("Stephen's MacBook"). That much is the price of them being able to check your rows. Labels are yours to edit in Settings → Devices before you join a board.

**A stolen device.** It holds the person secret, so until you revoke it, it can sign certs and membership rows on every board you are in. The controls are v0.4's: one-click revoke from another device, the cut honoured everywhere, rotation with `prevSig`, and every certified device listed (on each board's member panel too, as a count per person).

## 4. Invites, leaving and removal

### 4.1 Invite

The inviter is an owner (decision 32, 7b). Invite is GUI-only, like Add a device.

1. **Stephen: Boards → a board → Invite.** The Core opens an invite window (24 hours, one use), makes a code with go-room's `NewCode()`, derives an invite room from it (`room.SecretFromCode("irori-invite-v1", code)`), registers that room as a guest topic on his home server (v0.4 §4.2, `guest.open`, with the longer window this needs), and shows an **invite link**: `irori-invite:<code>@<server host:port>#<person fingerprint>`. The fingerprint is a short hash of Stephen's current person public key. How the invite travels is decision B4.
2. **Stephen sends it to Blake** over Discord or anything else.
3. **Blake: Boards → Join with an invite.** He pastes it. His Core dials Stephen's hub as a guest at that address and opens the invite room, and the two connect through go-room's handshake. Stephen's side takes the first device that proves the code; a second one closes the window (v0.4 §3, step 5).
4. **Both prove their person keys.** Each side signs the invite room's SAS info (v0.4 §3's HKDF, with both person keys added to `info`) with its person key. Blake's Core checks that Stephen's person key matches the fingerprint in the link, so someone else holding the code can't pose as Stephen. Stephen's Core shows Blake's name and person fingerprint.
5. **Blake reads the five words to Stephen, who types them** (on a call, or in the chat). Stephen proceeds only when they match, as pairing does.
6. **Stephen's device writes `board.member.added`** for Blake with `role: member`, signed with Stephen's person key, and sends Blake the board bundle: `board.created`, the board secret for its epoch (§6.1), the member rows, every member's copied `person.*` rows, and the `board.server` rows. Blake's Core creates `boards/<boardId>.db`, inserts the bundle, copies Blake's own `person.*` rows in (§3), and joins the board topic. Both close the invite room.
7. **Blake's other devices** learn the board from Blake's private log: the Core writes a private `board.joined {boardId, name, tag}` row (replicated kind, own mesh only) and hands the board secret to Blake's other devices in a `board.secret` frame on the own-mesh sync channel, as `person.secret` travels (v0.4 §5.2). They then join the board topic themselves.

The invitee's receive setting starts at Open and the board's autonomy at Trusted (decisions 24, 26). Who joins is the inviter's call; Irori adds no warning (decision 24).

### 4.2 Owners

- Any owner invites, removes and changes roles. There may be several owners, so a board isn't orphaned when one person loses their devices (decision 32, 7b).
- `board.member.role` makes someone an owner or takes it away. The last owner can't demote themselves.
- Two owners making conflicting changes while apart (one removes Carol, the other promotes her) are shown to the owners as a conflict line on the Boards dialog, not resolved silently (research/01 §5). The fold's rule while unresolved: a removal beats any concurrent change to the same person, so the safe outcome stands until an owner acts.

### 4.3 Removal

- **An owner removes a member** (GUI only): `board.member.removed {personId, by, reason, cut}`, where `cut` holds, for each of that person's certified devices, the highest seq the remover holds. The remover's own view decides; every member then refuses exactly the same rows whenever they hear of it, so folds agree (research/06; same mechanism as v0.4 §5.5).
- Rows above the cut that a member already holds move to `refused_events` and show as "N rows after removal". Nothing folds them.
- **Cleanup**, by the remover's Core: the removed person's agents are unassigned, their mirrored leases are released with `reason: member_removed`, and any bridged deliveries from them still waiting (§7.1) move to held.
- **The board secret rotates** (§6.1), so the removed person's devices can't follow the board's signaling, and every member's hub drops them.
- **The dialog says plainly:** "Blake keeps everything already on his devices. Removing him stops him syncing and writing anything this board accepts."

### 4.4 Leaving

`board.member.left` is written by the leaving person's own device, with a cut over their own devices. Its effect on everyone else is a removal. The leaving Core then forgets the board (§4.6).

### 4.5 Lost or stolen device

Revoking a device in Settings → Devices (v0.4 §3) writes the revoke to the private log, and §3's copy rule writes it into every board log. Rows from that device above the cut are refused on every board, by every member.

### 4.6 Forgetting a board

Deleting `boards/<boardId>.db` locally removes the board from this device at once. It is a local action, never a row, and it doesn't make the board forget you: other members still see you until you leave or are removed. Leave forgets on every one of your devices (through a private `board.forgot` row).

## 5. What crosses and what never does

### 5.1 The three columns

| Private (your log, your devices only) | Shared (only by being written to a board log) | Never leaves the device |
|---|---|---|
| Presence and full agent cards (cwd, permission mode, title) | `board.*` membership and `board.server` | Raw transcripts, Tier 2 bodies |
| Every inbox message and delivery, including bridged ones (§7.1) | `person.profile`, device certs and revokes, rotations | Person and device secret keys, board secrets |
| Capture Tier 0 and 1: turns, edits, commits, PR ledger, ai-titles | Tasks created on or shared to the board, their comments, steps, blockers, watchers and links | Policy rows, allow-lists, receive and autonomy settings |
| Private tasks, private leases | Reduced `agent.card`s of agents that touched a shared task | `irori.json` and its token, attach and member secrets, `turn.key` |
| `node.addr` (your server's full address row) | Mirrored leases (§5.4) | Patch blobs, `capture-cursors.json`, `board_cards` |
| The private `board.joined`/`board.forgot` rows | Commit SHAs and PR URLs that shared cards cite | Petnames |
| | Attachments put on a shared card or comment | |

Nothing moves from the left column to the middle except through a write to a board log, and every such write is either a person in the GUI or an agent under its person's autonomy setting (§7.3).

### 5.2 Share to board

"Share to board" is on a private card in the window (GUI), or requested by an agent (§7.3).
1. Irori re-runs `internal/scrub` and a stricter pass that drops absolute paths and home directories from the title, objective, done-when, steps and links.
2. It shows exactly what will be written, with "Visible to: Stephen, Blake", and the person confirms.
3. It writes a fresh `task.created` in the board log with the scrubbed fields and its steps. The private history (comments, status notes, blockers) stays private. A device-local link `shared_copies (privateTaskId, boardId, taskId)` lets the private card show "Shared to mlg as mlg#4" and the window show them as one card.
4. The private agents holding the card are told at their next turn that it now lives on the board, and their later writes go to the shared copy (the routing function follows `shared_copies`).

### 5.3 Withdraw

On a shared card the creator or an owner can Withdraw: `task.status canceled, withdrawn: true`. Other members hide the card, and its holders on your side carry on in a new private card. The dialog says: "Blake's devices already have what was shared." Nothing can be recalled.

### 5.4 Leases across people

Decision 32 (6a): only leases of agents working shared tasks are mirrored. With boards no longer bound to a repo, "the board's repos" becomes **the shared task's repo**:
- when an agent that holds (or has joined) a shared task acquires a lease on a resource in that task's repo, its Core writes the same `lease.acquired` into the board log, with the holder shown as its `agent.card`;
- a shared task without a repo mirrors no leases;
- release and expiry mirror the same way. The holder's device is the owner (v0.4 §6.0), across people as across devices;
- **nobody steals another person's lease.** `lease.stolen` in a board log counts only when its actor is a person whose agent holds the lease. Another person's "close" on a lease card sends the holder a next-turn release request through §7.1;
- two people's agents taking overlapping leases while apart both succeed locally; when the rows meet, the lease of the lower device id stands and the other holder's Core writes `lease.refused` and tells its agent (v0.4 §6.4's rule, not research/06's HLC rule, so a clock can't win it);
- a refused or conflicting lease shows as a lease card on the board, as it does privately.

Git conflicts stay the last line of defence. A lease never says what private work runs in a shared repo, because only shared-task holders' leases cross (decision 32 rejected mirroring all leases).

### 5.5 Attachments

Files on shared cards and comments use v0.4 §6.6 unchanged, with a board-scoped fetch: a device serves a hash to another person's device only when that board's log references it, and only on that board's connection. The 256 MiB cap holds. The never-leave rules on the source path (data dir, `.env*`, private keys, credential stores) apply before anything is copied.

## 6. Transport and sync

### 6.1 The board topic and its secret

Each board has a **board secret**, 32 random bytes made at `board.created`, per epoch:

```
boardSecret(epoch)   random 32 bytes; held by every member device; never in a row
topicKey             = HKDF-SHA256(ikm = boardSecret, salt = "irori/board/1", info = boardId || epoch)
                     → 32-byte sealing key || 16-byte topic suffix
topic                = "irori/board/1/" + hex(suffix)
```

- It is the board's go-room room key: it seals the board's signaling envelopes on every carrier, exactly as the person secret seals the mesh topic (v0.4 §4.2).
- It travels only inside connections whose peer is already authenticated: in the invite bundle (§4.1), to your own other devices in a `board.secret` frame on the own-mesh sync channel, and after a rotation in a `board.secret` frame on each board connection, only to current members' devices.
- **It rotates on every removal or leave.** The removing owner's device makes the next epoch's secret and sends it to every remaining member device. Devices keep the previous epoch's topic open until every member device has said `hello` with the new epoch, as v0.4 does for the person epoch. Two owners rotating while apart take the lower device id's secret for that epoch.
- It is not a log key. Board rows are not encrypted beyond DTLS (decision 32, 11a); §6.6 says what changes for a third person.

### 6.2 Which hubs a board uses

Decision 33's hub admits only your own certified devices and pairing guests. A shared board needs at least one hub that admits another person's devices; otherwise Stephen at home and Blake at his home have no way to exchange an offer. Whether your home server does this is decision B1. The recommended design:

- **Every member's home server serves that board's topic to that board's members.** Its hub's `Authorize(id, pub)` answers yes for a device with a counted, unrevoked cert from a current member of any board the server's Core holds, and `AllowTopic` for such a client is only the topics (current and previous epoch) of the boards its person is a member of. It can't subscribe to your mesh topic, open guest topics, or see any other board.
- **Each server announces itself to its boards** with `board.server {deviceId, port, public}`: the public address and mapped ports only, never the LAN addresses or v6 list in `node.addr`. It is written by the server device into each board its person is in, only when it changes, and `{public: null}` when the server is off or outside reach is off. A member's devices dial every `board.server` of the boards they are in, in parallel, keep the first handshake per server, and back off as the hub client does today.
- **One Signaler per board topic,** with every carrier the device has for it: the LAN carrier (two members' devices on one network find each other with no server), its own home server's hub, and every other member's server from `board.server`. Envelopes are de-duplicated as they are today.
- **TURN for other people is narrow.** A member of a board gets `turn.creds` with guest-scoped rights (v0.4 §4.4): its allocation may send only to the server's own relayed addresses, never to the home LAN. Your own devices reach it through their own relayed candidates on the same server, relay to relay inside the PC. Limits per remote person: 4 allocations, inside the server's total.
- **The always-on node stores and forwards** every board its person is in (decision 32, 9a). Signatures mean it can't forge Blake's rows; it carries them to your Mac and yours to Blake while either is offline.

What other people learn: your home server's public address and port, from `board.server`. That is the exposure decision B1 asks about.

### 6.3 Connections

- **One go-room `Mesh` per board topic,** so one `PeerConnection` per (device, device, board). A connection opened on board A's topic opens only a `board/<boardId>` sync channel for A, and its `Accept` checks the peer's `devicePub` against a counted cert of a current member of A. It can never serve your private log or another board.
- **Your own devices meet on each board topic too** (they are member devices), and sync that board's log with each other there. One rule, "a board's rows move only on its own connections", is easier to check than a board channel riding the private mesh connection.
- **What several boards with one person cost:** with three boards shared with Blake, each pair of your device and his device that are both up holds three connections, one per board. Each is idle until a row moves, keeps a 15 s ping, and goes through the same ICE path. Removing Blake from one board closes exactly that board's connections and touches nothing else.
- **Who offers:** the lower device id, as in v0.4 §4.2, compared across people the same way (device ids are random).
- **Version:** each board connection's `hello` carries `coreVersion` and a board protocol version. A mismatch is refused with `peer.down reason: "version"`, and the board's member panel says whose Irori to update (research/06 version skew).

### 6.4 The sync protocol on a board

The frames are v0.4 §5.2's, against the board store: `hello {v, deviceId, personId, boardId, epoch, coreVersion, schema, vector, wallMs}`, `rows`, `vector`, `ping/pong`, and `board.secret {epoch, sealed}` in place of `person.secret`.
- **`board.*` and `person.*` rows go first** on catch-up, since the Verifier needs membership and certs before a member's other rows.
- A row held for "no cert yet" waits per peer under the same cap (2,000 rows or 8 MiB).
- **Any member device may forward any member's rows.** The Verifier checks the writing device, not the sender.
- **A stalled forwarder** (a peer whose vector stops advancing for one member's stream while that member's other devices are ahead) is flagged on the member panel (research/06).

### 6.5 With the servers off

- Two members' devices on one network sync over the LAN carrier with every server off.
- A device away from home reaches a board when any member's server is reachable and admits it (B1). With every member's server unreachable, it can't, and the board's line in the Boards dialog says so ("Can't reach any home server for mlg").
- Connections already up survive a server going away, as in v0.4.

### 6.6 When a board gets a third person

Decision 32 (11a) defers log encryption until then. With three people, Carol's always-on node forwards rows between Stephen and Blake, and stores them. Today that is fine (they are all members and see everything anyway). The step that would matter is a forwarder that isn't a member, which this design never allows: a server admits only members, and a connection carries a board only between members. So the third person changes nothing in this design by itself. Encrypting rows under a board key that rotates on removal stays the plan for when untrusted forwarders exist, and is out of v0.5.

## 7. How work reaches other people

### 7.1 The bridge into the inbox

Board rows wake nothing on their own. When a comment, assignment, blocker change or ask arrives on a board for a task one of your local agents holds, watches or is assigned, **the device that hosts that agent** writes an ordinary private `message.sent` plus a delivery to it:
- the sender shows as `blake` or `blake's agent mlg-lead`, fenced `<irori-message from="blake" trust="untrusted" board="mlg">`. Other people's text is always untrusted to your agents; your own agents' rows on the board arrive as they do today;
- the message carries `ref: {boardId, deviceId, seq}` and `Ref: task:<id>`, so it lands on the card's thread like any message about a card (board.md "Card threads");
- **only the hosting device bridges,** and the bridge is idempotent on `ref`. Your Mac and your node both hold the board log and never deliver one row twice;
- your own agents' writes on a board task go through the same path to your other agents, so there is one delivery route.

Every v0.2 §5 and v0.4 §6.3 rule then applies on the host: block list, Pause all, the hop limit (6), the per-pair rate limit (also counted per remote person and board), and the host deciding holds. Reviving a closed session because of another person's row always asks the person first (an approval notification, decision 26).

### 7.2 Your receive setting (decision 24)

Per board and per person, set only in the app. Rows: `receive.set {boardId?, personId?, preset?, switches}`, device-local (it is policy, v0.4 §5.1).

| From other people on the board… | Closed | Ask me | Members wake | **Open (default)** |
|---|---|---|---|---|
| Their comments, blocker changes, assignments | Next turn | Next turn | Next turn | Next turn |
| A request to wake one of your agents | Next turn, marked "asked to wake" | Held for you | Wakes it (people you pick) | **Wakes it** |
| Their agents asking to wake yours | Next turn | Held | Wakes it (picked people's agents) | **Wakes it** |
| Rows to your bypass sessions | Held | Held | Through, for picked people | **Through** (decision B2) |
| Their agents assigning work to yours | Next turn | Held | Next turn, or a wake if asked | **Next turn, or a wake if asked** |

- **"Held"** uses the hold reasons research/06 named: `member_wake`, `cross_person`, `member_lease`. A held row reaches you as a notification card (one per sender, decision 34's coalescing), with Release and Dismiss.
- **The last column's bypass row conflicts with decision 34's text** ("the hold stays for other people's agents"). Every Claude session here runs in bypass, so under that reading Open would never wake one of them. This doc follows decision 24 and marks it as decision B2.
- The guards stay on under every setting: hop limit, rate limit, Pause all. There is no token budget (decision 24).
- Assignments follow the receive setting (decision 32), so on Open they arrive like comments.

### 7.3 Your agents' autonomy (decisions 23, 26)

Per board, set only in the app. Rows: `autonomy.set {boardId?, preset?, switches}`, device-local.

| Your agents may… | Ask me | **Trusted (default for new boards)** | Autonomous |
|---|---|---|---|
| Comment, raise and close blockers, tick steps, work shared tasks | Yes | Yes | Yes |
| Create new cards on the board | Request (notification) | **Yes** | Yes |
| Share one of your private cards to the board | No | **Request (notification: Share / Review / No)** | Yes, after scrub; you get a notice with Withdraw |
| Assign work to other people's agents | Yes | **Yes** | Yes |
| Mirror all their leases in shared tasks' repos (not only shared-task holders') | No | **No** | Yes |
| Ask to wake another person's agents | Asks; their receive setting decides | Same | Same |

- **A request is a notification, not chat** (decision 26): in front of other programs, on every device you are on, with its buttons, cleared everywhere once answered. The requesting agent doesn't wait; the answer reaches it at its next turn. It is written as the existing `ask.posted` in your private log, so it already shows and clears on every device (v0.4 §6.7).
- **What the setting can't change:** what others may do to your agents (that is your receive setting, and Blake's autonomy never overrides it); who changes it (the app only, never a tool); and what never leaves the device (§5.1 right column, under every preset).
- **Where an agent's new card goes.** `board_create` gains `board` (a tag or boardId). Without it the card is private, always. The board tool lists the boards the agent may post on, with their members. A card created on a shared board, and every tool result that wrote to one, ends with "Visible to: Stephen, Blake". If scrub or the stricter pass blocks a write, the result names the pattern that matched, so the agent can rephrase.
- **Text caps** as today: title 200, objective and comment 4000.

### 7.4 Who can do what on a board

| Action | A person (in their own app) | Their agents | Another person's agents |
|---|---|---|---|
| Create a card on the board | Yes | Per their autonomy | Per their own person's autonomy |
| Share a private card | Yes, with preview | Per autonomy (request by default) | No |
| Comment, raise or close a blocker, tick steps | Yes | Yes | Yes (decision 19) |
| Join and work a shared card | Yes | Yes | Yes, guarded by mirrored leases |

| Wake an agent now | Own agents; others' per their receive setting | Same | Same |
| Steal a lease | Own agents' only | No | No (a release request instead) |

## 8. The window

Stephen's rule for the window stands: cards of shared work, nothing he won't look at (v0.4 §9).

- **The board switcher is the filter row v0.4 §9 already has:** All, Needs a decision, My devices, and one chip per shared board (its name). "All" includes every board. Nothing else is added to the grid.
- **A card on a shared board** shows the board's name as its "where it lives" line ("mlg · with Blake"), its ref with the tag (`mlg#4`), and other people's agents with a person chip on their faces. Its detail adds, under the goal, one line: "Visible to: Stephen, Blake".
- **On a private card's detail:** Share to board (pick a board, then the preview, §5.2). **On a shared card's detail:** Withdraw (creator or owner).
- **Asks and new cards** pick their board in one dropdown beside the prompt box, defaulting to My devices.
- **Settings → Boards** (a dialog from the settings popover, like Devices): each board with its name and one status dot; New board; Join with an invite. A board opens to:
  - **Members:** name, person fingerprint, owner badge, device count; Invite (owners); Remove (owners); Leave;
  - **What reaches my agents:** the receive preset, with Members wake's people picker;
  - **What my agents may do:** the autonomy preset;
  - **One warning line, only when something is wrong:** can't reach any home server for the board, a member's Irori out of date, rows refused after removal, a stalled forwarder, an owner conflict.
- **Notifications:** share requests (Share / Review / No), held rows from other people (Release / Dismiss), and revive approvals, all cleared on every device once answered.

Fingerprints beyond the members list, paths, hubs and counters stay in `GET /v1/boards?detail=1`.

## 9. Asks on a board

#3 is building asks for the private board: a prompt from the window goes to free agents, one claims it, the claimer may talk it through with Stephen in a thread, and it ends as a new card, a change to a card, or nothing. This design gives asks one hook and leaves the rest to #3. **Re-check this section against design/board.md once #3 lands.**

- **An ask can target a board.** It is written to that board's log as `board.ask.*` rows (the kinds #3 settles, under a `board.` prefix so the allow-list can name them), and its thread is that ask's comments in the board log.
- **It reaches free agents of every member**, through each host's bridge (§7.1) and each person's receive setting: on Open, a free agent hears it at its next turn, or is woken if the asker asked for a wake.
- **The claim stays owner-decided.** Whatever row #3 uses to claim, the claim is a request, and the take is written only by the asking device (v0.4 §6.0's ask entity). Two people's agents claiming at once get one winner, decided on the asker's device, and the loser hears at its next turn.
- **The outcome card** is created on the same board.

## 10. Peer review across people (decision 29)

Lands with Shared Boards; the details can follow in their own doc.
- `review.requested {taskId, pr, from: cardId, to?: cardId}` on a board asks another person's agents to review a PR a shared card links. Without `to` it goes to the member's dedicated reviewer, if they set one.
- `review.reviewer {cardId, repo?}` (written by that person's GUI) dedicates one of their agents as the reviewer for the board or a repo.
- The review is posted by the reviewer's own `gh`, under its owner's GitHub account. Irori shows the state (asked, reviewing, approved, changes requested) from the PR ledger of the device that sees it, never posts reviews or merges. Your own agents can comment but aren't offered as approvers.

## 11. Tests

All on 127.0.0.1 and in-process, failing rather than skipping when peers can't connect (v0.4 §10).

**Unit**
- The kind allow-list: every kind in the registry has a Board column; a board store refuses each excluded kind in `Append` and `Insert`.
- Reference closure: a board row naming a private taskId, a commentId from another board or an unoffered attachment hash is refused by `Append`; a forwarded one the fold can't resolve is ignored and counted.
- Actors: `user:*` refused in a board log; `person:` rows only from Wails bindings.
- The board Verifier: a cert counts only with a valid `personSig` for its epoch; a rotation counts only with a valid `prevSig`; two rotations to one epoch take the lower device id's in every order; a revoked device's rows above the cut are refused.
- Membership fold: added, role, removed and left with cuts; several owners; the last owner can't demote; concurrent remove and promote surface as a conflict and the removal stands.
- The board topic: a new epoch gives a new topic; the previous stays open until every member device has the new epoch.
- Short refs per log, and the tagged/bare resolution rules (B3).
- The routing function `taskId → log`, including an unknown id and a shared copy.
- Scrub's stricter pass drops absolute paths and home directories.

**Multi-Core (`internal/mesh` harness with the fake transport)**
Five Cores: Stephen's PC (his server), Mac and node; Blake's PC (his server) and laptop. Real stores and keys. They must show:
- private rows never cross: a board connection never carries a private-log row, and Blake's devices never reach Stephen's mesh topic;
- a forged kind, a forged actor and an uncertified device are refused;
- a row Blake writes reaches Stephen's Mac through Stephen's node with Blake offline;
- removal with a cut gives the same fold on every member in every arrival order, the board secret rotates, and the removed person's devices can't connect on the new topic;
- revoking Stephen's Mac cuts its rows on every board;
- each board row is bridged exactly once, by the hosting device;
- every receive preset: a wake request from Blake wakes on Open, is held on Ask me, is next-turn on Closed;
- a bypass session receives Blake's row on Open (or holds it, per B2);
- autonomy: on Trusted an agent creates a board card; a share request raises one `ask.posted` and clears on every device after one answer;
- a mirrored lease blocks Blake's agent and shows as a lease card; partitioned lease grabs keep the lower device id's lease; Blake can't steal Stephen's lease;
- three boards with Blake: removing him from one leaves the other two connected and syncing;
- an attachment on a shared card is fetched by Blake's laptop, and a hash only the private log references is refused;
- a board ask claimed by agents of both people gets one winner, decided on the asking device.

**go-room and the hub**
- The hub admits a board member's device only for that board's topics; it can't subscribe to the mesh topic, open a guest topic, or see a board its person isn't in; it is dropped when its person is removed or its device revoked.

## 13. Decisions for Stephen

Raised as blockers on card #17, one each.

**B1. Your home server admits board members' devices.** Decision 33's hub admits only your devices. Shared boards need at least one hub that admits the other person's, or two people at two homes can't connect. Recommended: (a) every member's server admits that board's members, for that board's topic only, with TURN that reaches only the server's relayed addresses; members learn your home public address and port. (b) Only owners' servers do. (c) No server admits other people; boards sync only on a shared LAN or through an advanced relay you rent.

**B2. Other people's rows to your bypass sessions on Open.** Decision 24's Open lets them through; decision 34's text says the hold stays for other people's agents. Every Claude session here runs in bypass, so holding them means Open never wakes a Claude session. Recommended: (a) Open lets them through; Ask me and Closed hold them. (b) Always hold them, whatever the receive preset; you release each sender once.

**B3. How short refs look on shared boards.** Each board numbers its own cards, so `#12` exists on several boards. Recommended: (a) private stays `#12`; shared cards are `mlg#12` with a short tag picked at board creation; a bare number works only when it is unique across every board. (b) Every ref carries a board tag, private too (`me#12`). (c) Bare numbers everywhere, refused whenever ambiguous.

**B4. How an invite travels.** Pairing has you type a code to keep it off the clipboard; an invite crosses Discord anyway. Recommended: (a) a pasted invite link holding the code, your server's address and your person fingerprint; the invitee reads five words back to you, which you type. (b) Type a code, the server address and the fingerprint separately, as pairing does.
