# v0.4 "Devices": design

*2026-10-27, revised the same day after two reviews, again for decision 31 (the transport is go-room, not an iroh sidecar), and on 2026-10-28 for decision 33 (the home server). Builds on v0.3 (`main` @ f3de30e). Inputs: research/01 §5 (Data, Transport) and §6, research/04 §4 (tiers) and §5 (security), research/06 "People and devices" and build order steps 4–6, decisions 2–4, 8, 10, 22–28, 31 and 33, design/board.md and waits-signals.md, and three code readings done for this doc: Toru's rooms and ICE (`internal/stream/room.go`, `ice.go`, `wire.go`, `broadcast.go`, `lan.go` and their tests on Toru's origin/main), Toru's LAN and relay for decision 33 (`internal/lan`, `docs/lan.md`, `cmd/toru-relay`), and every place in Irori that assumes one device. Where this doc and the research disagree, this doc wins.*

v0.4 joins your own devices (the Windows PC, the Mac and the always-on Windows node) into one Irori. Each device keeps its own event log, and the logs replicate between your devices over WebRTC data channels (go-room, §4), directly or through a TURN relay, which stores nothing. **The always-on PC is Irori's server for your devices** (decision 33): it hosts the signaling hub that carries the sealed offers and answers, the TURN relay, and the port mapping that makes both reachable from outside the home. Devices on one network also find each other directly, with no server at all. Nothing goes through a third party: there are no public brokers and no public STUN servers. The rows themselves still flow over a mesh of direct connections (decision 30); the server only introduces devices and relays packets for the ones that can't reach each other. Every device then shows every device's agents in one inbox and one Board. A message to an agent on another machine wakes it there, approvals show and clear on every device, and files can travel with messages.

v0.4 also lays down the identity that Shared Boards (research/06, "v0.4 People") builds on: a person key, device certs, and signed rows. People other than you are not in this doc.

**One rule runs through the whole design: any device may ask, only the owner decides.** Every entity that grants something (a delivery, a wake, a lease, an ask) has exactly one owning device. Other devices write *request* rows; only the owner writes the row that takes effect, and every fold ignores (and counts) an authoritative row from the wrong device. That is what makes the mesh safe without a server and without trusting clocks (§6.0).

## 1. Scope

**In**
- **Identity:** a person key, device certs and revocation, all as signed rows (§2).
- **Pairing:** a pairing code shown on one device and entered on the other, the SAS words typed back on the first, the first's key typed on the second, and one-click revoke. No server of our own (§3).
- **go-room:** the shared pure-Go module extracted from Toru (pion data channels, sealed signaling, ICE), running inside the Core and started only once you have another device (§4). For Irori it gains a LAN carrier, a signaling hub, a TURN server and port mapping (§4.2, §4.4, §4.8).
- **Replication:** vector sync of the event log between your devices, with signed rows, device-local kinds kept out, fork detection, and revocation cuts (§5).
- **One mesh:** one inbox and one Board across devices, wakes to sessions on other devices, capture per device, and approvals on every device (§6).
- **Attachments** (decision 28): files on messages and Board cards, fetched from the device that holds them (§6.6).
- **The always-on node** as a full peer that stores and forwards, and as the home server: hub, TURN relay and port mapping (§7).
- **The cards window:** only cards of shared work (progress, who is on it, blockers with recommended answers, PRs), shipped first and on its own as v0.3.3 (§9, §11).
- **Signing and notarizing the macOS release**, because the Mac is one of the three devices (§4.7; see decision D4).

**Out (later)**
- Other people, shared board logs and `irori/board/1` (research/06 steps 7–16, "v0.4 People"), including peer review requests to other people's agents (decision 29) and attachments to other people. This doc reserves the channel label and the identity they use.
- Resuming a session on a different machine (research/04 §4, `--resume <path> --fork-session`). It stays experimental. In v0.4, "wake on another machine" means the host device wakes its own session.
- Tier 1 FTS of other devices' turns beyond what capture already stores, Tier 2 mirroring on the node, and handoff cards.
- A server outside the home, and dynamic DNS. With the home server off, a device away from home can't connect (§7). A TURN relay you run or rent elsewhere stays an advanced setting (§4.4).
- Fetching full transcripts across devices. Patch blobs are fetchable (§6.5); transcripts never leave their device.
- Encrypting the log at rest, and LLM-based extraction on the node.

## 2. Identity

There are three layers, all ed25519 and all set by the Core. Rows and agents never get to claim one (research/06).

**Person.** `<dataDir>/person.json` holds `{personId, name, secretKey, epoch, rootDeviceId}`, mode 0600. `personId` is the first 16 bytes of sha256 over the *first* person public key, hex; it names the person and never changes, even when the key rotates (§3, Revoke). `rootDeviceId` is the device that created the person. It is created on first v0.4 start. Pairing replaces it on the joining device (§3). The default name is the OS user name, and you can change it in Settings.

**Device.** `device.json` keeps `id`, `name` and `os` (`internal/device/device.go:20`) and gains `personId` and `devicePub` (the device's ed25519 public key, hex). The device secret is a separate 32-byte ed25519 seed, `<dataDir>/device.key` (0600), written by Go with `crypto/rand`. **One key is both the transport identity and the row-signing key:** it signs every row (§5.3) and signs the DTLS fingerprints in each connection's `auth` message, the first on it (§4.3). go-room never reads key files; the Core hands it a `Sign` function, so the key stays in `internal/identity` if it moves to DPAPI or the Keychain (decision D2).

**Certs.** A device belongs to the person once a `person.device.added` row holds a cert for it:

```
person.device.added   { cert: { personId, deviceId, devicePub, label, role: "desktop"|"node", at },
                        personPub, personSig }            // personSig = ed25519(person key, canonical(cert))
person.device.revoked { revoke: { personId, deviceId, cut, cutHash, at, reason }, personSig }
person.key.rotated    { personId, epoch, personPub, at }  // the new public key only; never the secret
person.profile        { personId, name, rootDeviceId, personPub, personSig }
```

- The person key signs the cert or revoke. The device that writes the row signs the row, like every row (§5.3).
- **The root is pinned.** The first device certifies itself with a self-written row on first v0.4 start. That self-cert is valid only when its `deviceId` equals `rootDeviceId` from `person.json` (carried to every device in the pairing exchange, §3). Any other self-cert is refused, even with a valid `personSig`, so a revoked device that still holds the person secret can't mint a fresh "root".
- **Every other cert row is accepted only when its writing device holds a valid cert** (the chain leads back to the root), or when it arrives inside the pairing exchange (§3). A device can't certify itself.
- `canonical()` is the JSON encoding with the keys sorted and no spaces. It is used only for these person-signed objects. Rows are signed over bytes (§5.3).

**What the person signature does and doesn't buy in v0.4.** Every one of your devices holds the person secret (research/06 decision 8, recommendation (a)). So inside your own mesh the `personSig` proves nothing the device signature on the row doesn't already prove: any certified device, a stolen one included, can produce both. In v0.4 trust comes from the cert chain to the pinned root and from the revocation rules (§5.5), not from the person signature. The person key is laid down now because Shared Boards will hand it to other people as the thing they trust, which is why it rotates on revoke (§3, decision D8).

**Owner identity.** The person at the GUI keeps the sender key `user:<deviceId>` (`core/core.go:263`, `api/board.go:70`). Ownership is resolved through certs instead of by rewriting the key: `isOwner(key)` is true **only when the key is exactly `user:<deviceId>` for a device ever certified to my person**. Revoked devices still count, because every row of theirs that is stored is at or below their cut (§5.5). This handles three cases with one rule, and none of them needs a row rewritten:
- rows from before v0.4;
- rows a device wrote under its own first-run person before it joined;
- rows from your other devices.

`person:<personId>` actors are for board logs (research/06) and are not written in v0.4.

**Where `isOwner` goes.** Two kinds of check assume one device today.
- **Exact matches against this device's own key** are the ones that break across devices. A Mac agent writing to "you" (`user:<mac>`) raises no card on the PC today. These get an owner set:
  - `notify/watch.go` (`waitingFor` at `:146`, and the matches near `:306`, `:316`, `:320`, `:345`): `notify.Sources` gains an `IsOwner func(string) bool` in place of the single `User` string;
  - `coord/board_impl.go:713-715` (`bb.Ref == viewer`, `isHolder(t, viewer)`): `BoardFilter` gains `ForAny []string` (or the same `IsOwner` func);
  - `api/board.go:70` and `board_service.go:112` (`For: user:<thisDevice>`) pass the owner set.
- **Prefix checks** (`inbox/state.go:287` `isUserKey`, called from `:365,671`, `route.go:90`, `search.go:169,273`, `sweep.go:156`; `coord/impl.go:53` `IsPerson`; `tools/set.go:215,232`; `tools/board.go:262,332`) already accept every device's `user:*` key, but they would also accept a made-up one (`user:anything`). They move to `isOwner` too, so the prefix test stops being the rule anywhere.

**Each site gets a test** (bypass hold, rate limit, `asUser`, policy, lease steal, Revive, blocker close, Needs-you on another device's owner key, a made-up `user:` key refused). `isOwner` needs the cert fold from identity, so it lands with identity, not before it (§11).

**Only the GUI makes `user` rows.** `actorFor` turns any `user:` prefix in `by` into actor `user` (`inbox/state.go:276`, `coord/impl.go:583`), and the loopback API mints such keys today (`api/v02.go:268`, `user:composer@…`). In v0.4 that matters on every device, because a `user` row approves a revive or answers an ask (§6.3, §6.7). So:
- the loopback API never accepts a caller-supplied `by` or key that starts with `user:`, and `v02.go:268` moves to its own actor (`api:<sender>`);
- actor `user` is minted only by Wails bindings.

**Person-actor rows record their device.** A row whose actor is `user` gains `at_device: <deviceId>` in its payload when the GUI writes it. The writing device is already in the row key; the field makes the origin plain in history and in the `events` tool.

**Agents.** Keys stay `<deviceId>/<sessionId>` (v0.2 §2). Grok members get a reduced `agent.seen` card, `{key, agent: "grok", name, status}`, with no secret, so other devices can see and address them (today only `member.joined`, `core/members.go:151`).

**What a card row carries.** `agent.seen` writes the whole `presence.AgentCard` today (`core/core.go:205`), unscrubbed: `LastText` (the last assistant prose), `Title`, `Cwd` and `Transcript` (a local path) (`presence/presence.go:29-47`). Once rows replicate, that text is copied to every device for good. So in v0.4:
- `Transcript` and `PID` leave the row (local paths and pids mean nothing on another machine);
- `LastText` leaves the row and stays in this device's memory (decision D9);
- `Title` runs through the capture scrubber before `Append`.

## 3. Pairing

You always pair from a device that is already in the mesh ("A") to a new one ("B"). The first device is in the mesh on its own.

**The pairing code is a secret.** Whoever has it can reach A's pairing room first. Treat it like a one-use password: the GUI says so next to it.

1. **A: Settings → Devices → Add a device.** A opens a pairing window (10 minutes, one use), makes a code with go-room's `NewCode()` (16 symbols, about 79 bits, `XXXX-XXXX-XXXX-XXXX`), opens the pairing room derived from it (§4.2) on its LAN carrier and on every home server it is connected to (registering it there as a guest topic for the window, §4.2), and shows the code as text. The code carries nothing else: no address and no name (why: below). There is no QR code: every device is a computer, with no camera to scan one (Stephen, 2026-10-28). Typing the code keeps it off the clipboard, where any agent on either machine could read it; copying it shows a one-line warning.
2. **B: Settings → Devices → Join with a code.** B types the code (any case, with or without dashes) and, only when it is away from home, the home server's address (below). It opens the same pairing room and sends `pair.hello {deviceId, name, os}`. A takes the first `pair.hello` from a device id that is neither its own nor revoked, and makes the offer (in the pairing room A always offers). The connection comes up through go-room's handshake (§4.3). Its `Accept` takes any key here and records B's `devicePub`, because nothing is certified yet. On each side it takes only the first key it sees for the other device id in this window and refuses a different one, so a code holder can't swap in its own key once the connection is up (go-room would otherwise let a newer, fully authenticated connection replace it, §4.3). `Accept` runs inside go-room's 10 s handshake and gets no fingerprints, so the SAS below runs after `OnPeer`, over `Messages()`.
3. **Both Cores compute the SAS in Go:**
   ```
   HKDF-SHA256(ikm = the pairing room key, salt = "irori/pair/1",
               info = A.devicePub || B.devicePub || fp(A's DTLS cert) || fp(B's DTLS cert) || A.deviceId || B.deviceId)
   ```
   That gives 5 words from hato-code's wordlist, ported to Go as a table. The room key is the scrypt of the code (§4.2). Each side first proves it holds the code, by an HMAC over the info with the room key, compared in constant time. The fingerprints are the ones the DTLS transport saw, not the SDP's (§4.3). So the words bind both device keys and this one DTLS session: someone in the middle who knew the code would be running two DTLS sessions, and A and B would see different words. Until the words match, both Cores treat the peer as unconfirmed: they send nothing on it but the SAS exchange.
4. **B shows the words. You type them into A.** A shows the joiner's device name, OS and device fingerprint (a short hash of its `devicePub`) above the input, and has no Confirm button: A proceeds only when the typed words match. Typing instead of clicking is what stops a code thief: if someone else used the code first, A answers B with `pair.busy`, B shows "code used" and never reaches the words step, so there is nothing to type.
   **B also types A's key.** A shows its own device fingerprint beside the code (and again once the words match), and B asks for it under the words, with Cancel. B takes A's grant (step 6) only from the device whose handshake proved that key, and tells A (`pair.key`) once it matches; A certifies B only when both the words and that are in, so a pairing that fails on B leaves no cert behind. The second wrong key closes the window ("That isn't the key the other device shows"). Without this, anyone else holding the code (an agent that read it off the clipboard or shell history) could reach B first posing as A, prove the code, and hand B a person of its own: only A checks the words, so B would show "Paired" with a person the thief made. The thief can't prove A's key, so the key B is given never matches.
5. **Failure closes the window.** An HMAC failure, a `pair.hello` from a second device id, or wrong words typed twice closes the pairing window and leaves the pairing room, and A shows "Someone else tried to use this code. Make a new one." Pairing also refuses a peer whose `deviceId` equals A's own, or that is already certified under a different `devicePub` (a copied data dir or restored backup, §5.2).
6. **After the words match, A sends B,** over the pairing connection (the same `*Peer` the words were computed on; if it went down or was replaced, pairing starts over), the person secret and its `epoch`, `rootDeviceId`, its `person.profile`, every `person.*` row A holds, and the `node.addr` rows it holds (so B can find the home server at once, §4.2). A then writes `person.device.added` for B (`role` picked on A's screen: desktop or node) and adds B to the set its `Accept` lets in. B replaces its own `person.json` with A's person, rewrites `device.json`'s `personId` and adopts the certs. Both then close the pairing connection and the pairing room, open the mesh topic (§4.2), connect again there, with the handshake now checked against B's cert, and start normal sync (§5). Reconnecting proves at once that B can find the mesh without the code.
7. **B's earlier history replicates.** B's rows from before pairing are signed by B's device key (§5.4). They become valid once B is certified, so B's past work joins the mesh, and `isOwner` accepts B's `user:<B.deviceId>` rows through B's new cert. B's first-run self-cert and `person.profile` for its old person also replicate; they are stored and inert, because cert and profile folds consider only rows whose `personId` is the local person.

**How B finds A** (decision 33; there are no brokers):
- **At home** (the usual case), B needs nothing but the code. Its LAN carrier broadcasts the sealed `pair.hello` on the local network (§4.2). A hears it directly if A is on the same network. If A is away (pairing the PC at home from the Mac on a trip), the home server hears it: the pairing room is a guest topic A registered there, so the server bridges that topic between its LAN and its hub, and A, connected to the hub from outside, gets B's envelopes.
- **Away from home,** B also needs the home server's address. A's Add screen shows it under the code when the server is reachable from outside ("Joining from outside your home? Server address 203.0.113.7:24817"). B's Join screen has an optional "Home server address" field; B connects to that hub as a guest (§4.2), which admits it only to a pairing room a certified device registered, for that window.
- A manual address stays in B's dial list for that server until a `node.addr` row for it arrives (with the pairing bundle, step 6, or by sync); from then on B dials the row's addresses like every device. Right after pairing the server's hub may refuse B until A's cert row for B has reached the server; the hub client's backoff covers that, and at home the LAN carrier connects without waiting.

**Why the code carries no address.** The code is typed, and an IPv4 address and port would add about ten symbols to sixteen. Most pairing happens on one network, where no address is needed. The public address also changes whenever the ISP reassigns it, so a code that embeds it could be stale before it is typed, and a leaked code would also say where your PC is. The optional field costs one more box, only on the rare remote join.

**A device that is already in a mesh can't join another.** B's Join is refused when B holds a cert written by any device other than itself (its own first-run self-cert doesn't count); you revoke or reset B first. **Reset** means wiping the log, `device.json` and `device.key` (a new device id and device key), keeping only `settings`. As built, nothing is deleted: the Reset button (on a removed or forked device's warning line) marks it and quits, and the next start moves the log, `device.json`, `device.key`, `person.json` and the per-device files into `reset-<time>/` in the data dir; `irori pair reset` does the same from a shell when Irori isn't running. A reset device can't replay another mesh's rows, because it has none.

**Revoke** (Settings → Devices → a device → Remove, GUI only). Revoking writes `person.device.revoked {deviceId, cut, cutHash}`, where `cut` is the highest seq of that device this device holds and `cutHash` is the hash of that row's signed bytes. Its effects:
- every device drops the revoked device from the set its `Accept` lets in and closes any open connection to it (§4.3), and the home server drops its hub connection, closes the guest topics it registered, and refuses its next TURN request (§4.2, §4.4);
- rows from that device above the cut are refused everywhere (§5.5);
- its agents' cards, deliveries and leases are retired the way a `device.started` retires a crashed host's (§6.1);
- **the person key rotates** (decision D8): the revoking device makes a new person key, writes `person.key.rotated {epoch+1, personPub}`, and sends the new secret to each remaining device in a `person.secret` frame on the sync channel (§5.2). The secret is never in a row. The new epoch moves the mesh topic; a device that is offline gets the secret when it next connects to any device that has it, through the topic of the epoch it last said `hello` with, which stays open until then (§4.2). Each Core keeps every older epoch's key until every remaining device has the current one, so a device that missed several rotations jumps straight to the current key. Two devices that revoke while they can't reach each other both rotate to the same epoch with different keys: every device takes the `person.key.rotated` row written by the lower device id (then the lower seq) as that epoch's key, and the other side adopts it in a `person.secret` frame over the last epoch they shared, so they meet on one topic again.

The dialog says plainly: "This device keeps everything it already has. Removing it stops it from syncing and from writing anything new that your other devices will accept." Until every other device has seen the revoke, the device's row in Devices says "Removal pending: seen by 1 of 3 devices". A revoke made while offline takes effect nowhere else until this device syncs.

**Revokes don't depend on arrival order.** A revoke is honoured if its writer was ever validly certified, whether or not the writer is itself revoked. So if a stolen laptop and your PC revoke each other, **both are revoked everywhere**, whichever row a device hears first. You then re-pair the PC from a third device (the node or the Mac); re-pairing a revoked device is a reset of it plus a normal join, so it comes back with a new device id, and its rows written above the cut stay only on that machine. If a thief revokes every device, the mesh can't certify anyone: you make a new person on one device and pair the rest to it. Every device's own rows become valid again under the new person through the same rule as step 7. The thief's rows never do.

**A device that sees its own revocation** stops syncing and shows "Removed from your devices by <device>", with a Reset button.

**Pairing is GUI-only.** Add, Join, typing the words and Remove go through Wails bindings and are not on the loopback API, so an agent with a shell can't pair a device (v0.2 §5's soft boundary). The one CLI path is `irori pair join` for a headless machine: it can only join, it reads the code from a prompt rather than argv, and it still needs the words typed into the other device's app. Typing the SAS also means an agent that read the code off the clipboard can't finish a pairing without you typing words only the real B shows. The always-on node's path is in §7.

## 4. Transport: go-room

Decision 31 replaces the iroh sidecar with `github.com/StephenSHorton/go-room`, a public pure-Go module extracted from Toru that both apps use (as with go-toast). It is pion WebRTC data channels, with signaling sealed with a key only your devices hold. Toru carries that signaling over public MQTT brokers; Irori doesn't (decision 33): its envelopes go over the local network and through a hub on the home server, and ICE uses the home server's STUN and TURN (§4.2, §4.4). It runs inside `irori.exe`: there is no helper process, no second toolchain and no second binary to sign.

### 4.1 What is reused from Toru, what is new

Toru's `internal/stream` (origin/main) has the rendezvous and the ICE list Irori needs, but no data channels: Toru's streams use media tracks, its LAN runs WireGuard over raw `pion/ice`, and its call window does WebRTC in WebView2. So go-room lifts Toru's signaling and ICE code and adds a data-channel peer layer that Toru doesn't have yet.

| Lifted from Toru into go-room | New in go-room |
|---|---|
| `room.go`: the code alphabet and `NewCode`/`NormalizeCode` (16 symbols of 31, about 79 bits), scrypt key and topic derivation, the sealed `Envelope` (`secretbox`, 24-byte nonce), publish to all and de-duplicate by id, auto-reconnect and resubscribe, the message-age check; the two broker sets (EMQX, HiveMQ) stay in go-room's `mqtt` package for Toru, and Irori never imports it | **Parameters for what is Toru-specific today:** the app's scrypt salt and topic prefix (`toru-stream-room-v1`, `toru/v1/`), the client-id prefix, the broker list and `maxMessageAge` (2 minutes) |
| `ice.go`: the public STUN list (Toru's; Irori doesn't use it, §4.4), the TURN REST credential loop (fetch from `CredentialURL`, refresh at 80% of the ttl, backoff, keep working credentials until they expire, https required except on loopback), `RelayStatus` (none, pending, ok, error) | A secret from a high-entropy key (HKDF) as well as from a typed code, for the per-person topic (§4.2) |
| `broadcast.go`'s offer flow: one `PeerConnection` per peer, gather with a 4 s cap, then send the SDP | **The peer layer:** offer/answer over the room with a fixed offerer, one reliable ordered message channel per peer, and on-demand byte streams, each its own data channel with flow control (§4.3) |
| The `tuneICE` test hook and `loopbackOnly` (`SetIncludeLoopbackCandidate(true)` plus a loopback `SetIPFilter`) from `e2e_windows_test.go` | **The signed-fingerprint handshake** that binds each connection to an ed25519 identity (§4.3) |
| pion's mDNS candidates off, as Toru's LAN agent has it (no browser here; LAN discovery is go-room's own sealed beacon, §4.2) | An in-memory signaler for tests, so two real pion peers connect on 127.0.0.1 with no broker |
| Toru's `cmd/toru-relay` ideas: TURN REST credentials on `pion/turn`, allocation caps | **The home server pieces (decision 33):** carriers under one Signaler, the LAN carrier, the hub server and client, the TURN server, and port mapping (§4.2, §4.4, §4.8) |

Toru then moves onto go-room for its rooms and relay; that migration is Toru's own change and not part of Irori's plan.

### 4.2 Rendezvous: the pairing room, the mesh topic, and how envelopes travel

Signaling carries only small envelopes (presence, offers, answers). Rows, blobs and attachments never touch it. Each envelope is sealed with the room key, so the hub, the LAN and anyone listening on either see random bytes. Envelope `From` and `To` are Irori device ids.

**The pairing room** (§3) is derived from the pairing code: `room.SecretFromCode("irori-pair-v1", code)`, which is scrypt over the code as in Toru. It is open only on A while a pairing window is open, and on B while it is joining. It closes when pairing ends, fails or times out.

**The mesh topic** is how your devices find each other after pairing. It is derived from the person secret, which every certified device holds (§2):
```
meshSecret = room.SecretFromKey("irori/mesh/1", ikm = person secretKey, info = personId || epoch)
           = HKDF-SHA256(ikm, salt = "irori/mesh/1", info) → 32-byte sealing key || 16-byte topic suffix
topic      = "irori/mesh/1/" + hex(suffix)
```
No pairing code is ever reused, and the topic doesn't name you: it is a hash of a secret.

#### Carriers: one Signaler per topic, envelopes over every path

A room is one go-room `Signaler` (one sealing key, one de-duplication set, one `Mesh`) that sends each envelope over every **carrier** it has and takes the first copy that arrives. A carrier moves sealed payloads for a topic and never holds a key. This is the shape the brokers had (publish to every broker set, de-duplicate by id), with the brokers replaced by:

- **The LAN carrier**, on every device: sealed datagrams on the local network (below). It is what lets two devices on one network connect with the home server off.
- **One hub carrier per home server** the device knows of (normally one): a TLS connection to the server's hub (below). The server's own rooms use the hub in process.

One Signaler with several carriers matters: go-room allows one `Mesh` per `Signaler`, so a LAN room and a hub room as two Signalers on one topic would make two `PeerConnection`s to the same device. `Connected()` counts carriers that are up, and presence is announced each time any carrier (re)connects.

#### The LAN carrier

**Mechanism: sealed UDP datagrams, directed broadcast to each local subnet, then unicast; not mDNS.**
- **Port:** UDP 38419 on every device, fixed (a device has to know where to send before it has heard anyone). The socket binds the wildcard address with `SO_BROADCAST`, because broadcast is delivered only to a wildcard bind on Windows. If the port is taken, the LAN carrier is off and Devices says why; the hub still works.
- **Sending to everyone** (`To == ""`, presence, `pair.hello`): one datagram to the directed broadcast address of each up IPv4 interface with a private address (192.168.1.255 for 192.168.1.20/24), not 255.255.255.255, which Windows sends out of one interface only (Toru hit this with Radmin's adapter). On Windows, an interface whose network is on the Public profile gets no datagrams (the Network List Manager reading Toru's `nlm_windows.go` does), so a laptop on café Wi-Fi sends nothing there.
- **Sending to one device** (offers, answers, byes): unicast to the address that device's last authentic envelope came from, or broadcast if none is known yet.
- **The datagram:** `"GR1" || tag(8) || nonce(24) || secretbox(room key, envelope)`, at most 8 KiB (an SDP with every candidate fits; the LAN fragments it if it must). `tag = first 8 bytes of SHA-256("go-room/lan/1" || topic || u64(unixSeconds / 300))`: it lets a receiver pick the room without trying every key, and it changes every 5 minutes, so a listener on the network can't follow one device's datagrams from one network to the next by a fixed value. Receivers accept the current and the previous window's tag. A datagram whose tag matches no open room is dropped unopened.
- **Limits:** at most 200 datagrams opened per second per socket, the rest dropped; the same age check and de-duplication as every carrier.
- **IPv4 only.** IPv6 has no broadcast, and every home LAN still has IPv4; an IPv6-only network falls back to the hub.

**Why not mDNS.** Port 5353 is owned by the OS responders (Windows' DNS client, macOS's mDNSResponder), so sharing it means contending with them; a service record names the service in clear text to everyone on the network (`_irori._tcp` on café Wi-Fi says an Irori laptop is here); and after discovery Irori would still need a path for offers and answers. Toru turned pion's mDNS off for the same listener reason. The sealed datagram is discovery and signaling at once, reveals nothing but its size and timing, and reuses go-room's sealing.

**macOS:** the Local Network prompt covers broadcast as well as host candidates (`NSLocalNetworkUsageDescription`, §4.7). No Bonjour entry is needed, because nothing uses Bonjour.

#### The hub

**Wire: TLS 1.3 over TCP with length-prefixed frames, not WebSocket.** The only thing WebSocket adds is passing through HTTP proxies, and the hub is reached directly: at home on the LAN, away through the port the router maps (§7). TLS 1.3 is in the Go standard library, and its exporter gives the channel binding the handshake below needs. Plain TCP without TLS would let anyone on the path see topics and timing and inject frames into an authenticated connection; TLS costs nothing extra in code.

- **Port:** the home server's one port number N, on TCP (the hub, and TURN over TCP) and UDP (STUN and TURN over UDP), §7. A TCP connection is told apart by its first byte: `0x16` (a TLS handshake record) goes to the hub, `0x00` or `0x01` (a STUN request, indication or response) to TURN, anything else is closed. TURN's ChannelData (`0x40`–`0x7F`) only follows on a connection already handed to TURN.
- **TLS:** the server certificate is self-signed, ECDSA P-256, made fresh at every server start, with no names in it and a random serial. ALPN `go-room-hub/1` is required; a client that doesn't offer it gets a handshake alert. **Nothing pins the certificate:** the client skips certificate verification (`InsecureSkipVerify`) and both ends instead sign the TLS session itself with their device keys (below), so the certificate needs no replicated fingerprint, and a scanner sees no certificate that stays the same from one start to the next.
- **Frames:** `u32 big-endian length || u8 type || body`, at most 64 KiB. Control bodies are JSON; `pub` and `msg` bodies are `u8 len || topic || sealed payload` (the same sealed bytes a broker carried).

| type | from | body |
|---|---|---|
| `hello` | client, first, within 5 s | member: `{v:1, id, pub, sig}`; guest: `{v:1, guest:true, topic}` |
| `welcome` | hub | `{v:1, id, pub, sig}` (the hub's device signs too) |
| `sub` / `unsub` | client | topic |
| `pub` | client | topic, sealed payload; the hub sends it to every other subscriber of the topic |
| `msg` | hub | topic, sealed payload |
| `guest.open` / `guest.close` | member | `{topic, ttlMs}` / `{topic}`: admit guests to this topic for the window (pairing) |
| `turn.get` / `turn.creds` | member or guest / hub | `{}` / `{username, credential, ttlS}` (§4.4; a guest's are narrower) |
| `ping` / `pong` | either | every 15 s; 45 s of silence closes |
| `err` | hub | `{reason}` before a close, only to an authenticated member |

**The authorization handshake.**
```
x      = TLS exporter(label "EXPORTER-go-room-hub", context empty, 32 bytes)    // TLS 1.3 only
client = ed25519(device key, "go-room/hub/client/1" || 0x00 || x || len(id) || id)
server = ed25519(device key, "go-room/hub/server/1" || 0x00 || x || len(id) || id)
```
1. The client sends `hello`. **A member** signs `x`. The hub calls `Authorize(id, pub)`; Irori's answer is yes only for a device with a valid, unrevoked cert for this person whose `devicePub` is `pub` (§2). **A guest** names one topic; the hub admits it only if a member registered that topic with `guest.open` and the window hasn't closed.
2. Anything else (a bad signature, an unknown key, a guest topic that isn't open, a malformed or late `hello`) closes the connection **without a reply**, so a stranger can't tell a wrong key from a closed window.
3. The hub answers `welcome`, signed with its own device key over the same `x`. A member's client calls `Expect(id, pub)`; Irori's answer is yes for a certified, unrevoked device whose key matches its cert. A `node.addr` row (below) is how a device finds a hub, not whether it trusts one. A guest records the hub's key and checks it once pairing has given it the certs.

`x` is unique to the TLS session, so a signature can't be replayed or relayed: a man in the middle runs two TLS sessions with two different exporters, and can produce neither side's signature for the other. TLS 1.3 is required because the 1.2 exporter isn't bound to the handshake without extended master secret.

**What each client may subscribe to.** The hub asks `AllowTopic(client, topic)`:
- **a member:** the mesh topics this server's own Core has open (the current epoch, and the previous one during a rotation, below), and guest topics that are open. The server's Core holds the person secret, so it computes those topics itself; a member can't make it carry anything else;
- **a guest:** only the topic its `hello` named, and only while that topic is open.

**Guest topics (pairing).** A device that opens a pairing window sends `guest.open {topic, ttlMs}` to each hub it is connected to; the server's own pairing windows open locally. A guest topic lasts at most 10 minutes, at most 2 are open per member, and it closes on `guest.close`, when its window ends, when its member disconnects or is revoked, or when it expires. Closing it drops its guests. Any certified device may open one, not only the server itself, because A can be the Mac while the server stays at home (§3); a guest still reaches nothing but the one pairing room it has the code for.

**The LAN bridge.** The server forwards open guest topics between its LAN carrier and its hub, both ways, so B at home with only the code reaches A away from home (§3). Mesh topics aren't bridged: every device that can reach the hub connects to it itself.

**Limits** (it is Stephen's desktop): 64 member and 8 guest connections, 4 handshakes in flight per remote IP and a backoff after a failed one, 8 topics per connection, 50 `pub` per second per connection (burst 100), 64 KiB frames. The hub keeps nothing: no retained messages, no log of envelopes.

**The hub client** dials every address it has for a server in parallel (the LAN address the server's datagrams come from, the LAN and public addresses in its `node.addr` row, the last address that worked, a manual address) and keeps the first that completes the handshake, so at home the LAN address wins and a router without NAT loopback doesn't matter. It reconnects by itself, 1 s, 2 s, 4 s ... up to 60 s, re-reading the list each time.

#### The address row

The server publishes where it can be reached as a replicated row, so every paired device learns it, through any device, even with the server off:
```
node.addr { v:1, port, lan: ["192.168.1.20"], v6: ["2001:db8::20"],
            public: { ip, tcp, udp } | null,     // the router's external address and mapped ports
            via: "upnp" | "natpmp" | "manual" | "",
            reach: "ok" | "cgnat" | "unmapped" | "off", at }
```
- Only the device itself writes its `node.addr` (an owner-only kind, §6.0); the fold keeps each device's newest by seq and ignores one from a revoked device.
- It is written **only when something in it changes** (a new DHCP lease, a new public address, a mapping gained or lost), never on a timer, so the log doesn't grow with each renewal.
- `reach: "off"` with no addresses is written when the server is switched off, so devices stop dialing it.
- Devices keep the last address that completed a handshake per server in `hub-addrs.json` (device-local, beside the addresses a pairing handed them until the server's row arrives), and dial it next time.
- A device that is certified but stolen can write a `node.addr` for itself and run a hub with its own key. It passes `Expect` until it is revoked; all it gains is the sealed envelopes it was already entitled to, and it can drop them, which costs only the connections that went through it.

#### Presence, who offers, rotation, message age

- **Presence.** Every running Core announces `presence {deviceId, epoch, coreVersion}` on the mesh topic when any carrier connects and every 30 s, and `leave` when it shuts down. Presence never logs a row. It feeds device liveness (§6.2) together with the sync channel's `ping`.
- **Who offers.** For each pair of devices, the lower device id always makes the offer. The higher one, on seeing the lower's presence, calls `Connect`, which sends `rtc.want`. So two offers never cross, which is the rule the iroh design had as "the connection dialed by the lower node id stays".
- **Who is answered.** A Core makes or answers an offer only for a device id with a valid, unrevoked cert for your person. Anything else on the topic is ignored and counted. The topic is sealed with the person secret, so only devices that hold it can be there at all, and the handshake (§4.3) still has to pass.
- **Rotation.** When the person key rotates on a revoke (§3, D8), `epoch` moves and so does the topic. Each remaining Core **keeps the previous epoch's topic open too, until every certified, unrevoked device has said `hello` with the new epoch** (§5.2). That way a device that was offline during the rotation still finds a peer, connects, and gets the new secret in a `person.secret` frame. During rotation a Core runs two Signalers and two `Mesh`es, one per topic (go-room: one `Mesh` per `Signaler`), each on every carrier. The server's hub allows both topics to members for the same window. Two devices that both have the new epoch connect on the new mesh only: the old mesh's `Allow` refuses a device whose `hello` already carried the new epoch, so the old topic carries only connections to devices still behind.
- **What an old-topic key holder can still do.** The revoked device keeps the old secret. **On the hub it can do nothing:** its hub connection is dropped at the revoke and `Authorize` refuses it from then on. **On a LAN it shares with your devices**, until the old topic closes, it is a room-key holder, and so is anyone who has a pairing code while that window is open. It can read presence and the SDP of devices on that network, and so their candidate addresses. It can spoil connection attempts that haven't finished the handshake (a forged `rtc.answer` that wins the race, or an `rtc.bye` naming the attempt's session), which costs that attempt and a backoff. It can't take down a connection that is up, and it can't pass the handshake, because its cert is revoked. go-room guarantees that: a newer `rtc.offer` is answered beside the live connection and replaces it only after passing the handshake, an offer that isn't newer on the offerer's clock is dropped, `rtc.want` closes an up connection only when ICE has stopped hearing the peer, and `rtc.bye` closes one only when it carries a token that travelled inside DTLS. This is why the old topic closes as soon as every device has the new epoch.
- **Message age.** go-room drops envelopes more than 2 minutes old or ahead, on every carrier. So a device whose clock is more than 2 minutes off can't signal at all. Devices shows this as the same clock warning as §5.6 ("Mac's clock is off by 7 minutes: it can't connect"). Irori keeps 2 minutes: with the hub keeping nothing it bounds replays of captured LAN datagrams.

**Envelope types** (`Type`; bodies are JSON):

| type | to | body |
|---|---|---|
| `presence` | everyone | `deviceId, epoch, coreVersion` |
| `leave` | everyone | |
| `rtc.want` | the lower device | `{}`: please offer to me |
| `rtc.offer` / `rtc.answer` | one device | `session, sdp` (all candidates gathered, 4 s cap) |
| `rtc.bye` | one device | `session, token, reason` (the token is from the receiver's `auth`, §4.3) |
| `pair.hello` / `pair.busy` | pairing room only | `deviceId, name, os` / A is already pairing with someone |

### 4.3 Connections and channels

**One `PeerConnection` per peer**, with a fresh DTLS certificate per connection (pion's default). Data channels are pion data channels over one SCTP association. go-room uses `SettingEngine.DetachDataChannels()` and wraps each channel in its own type. SCTP keeps its streams independent, so a large blob never blocks the sync channel's live rows, although they share the path's congestion control.

**The handshake binds the connection to a device key.** The SDP, and so the DTLS fingerprints in it, crossed the hub or the LAN. So nothing is trusted until each side has signed what it actually sees:
```
auth { v:1, deviceId, devicePub, sig, token }
sig = ed25519(device key, "go-room/auth/1" || 0x00 || role ('O' offerer | 'A' answerer)
              || sha256(offerer's DTLS cert) || sha256(answerer's DTLS cert)
              || sha256(topic) || len(deviceId) || deviceId)
```
- The fingerprints are read from the connected DTLS transport (the local certificate and `GetRemoteCertificate()`), not from the SDP.
- `auth` is the first message on the message channel, in both directions. Each side then sends its verdict `{v:1, ok}`; go-room surfaces a peer as up (`OnPeer`) only after both `auth`s verify and both sides' `Accept(deviceId, devicePub)` returned nil. So Irori's first frame is the third message on the channel, and go-room has already consumed the two before it.
- `token` is random per connection. It travels only inside DTLS, and an `rtc.bye` to an up peer must carry it, so a room-key holder can't close a live connection with a forged bye (§4.2).
- `Accept` runs inside go-room's 10 s handshake timeout and is given no fingerprints. Anything slow or interactive (the pairing SAS, §3) runs after `OnPeer`.
- **After pairing**, `Accept` checks `devicePub` against the device's cert (§2), and refuses an uncertified or revoked device. So the hub, or someone who got hold of signaling, can't impersonate one of your devices, because they can't sign with its key. A relayed signature is useless as well: it names both fingerprints, and the DTLS session can't be completed without the private key of the certificate it names. That key is fresh for every connection.
- **During pairing**, neither side knows the other's key yet, so `Accept` takes any key, and the SAS words do the authenticating (§3): they cover both device keys and both fingerprints, so a man in the middle who knew the code gets different words on A and B.

**Channels:**
- **`sync`: one reliable, ordered message channel per peer.** It carries `auth`, then the frames of §5.2. go-room's `Channel` sends whole messages of up to a cap Irori sets at 8 MiB (Go itself sends at most 1 MiB, §5.2). Each message is cut into SCTP messages of at most 16 KiB and joined again on arrival, because pion's default SCTP message cap is 64 KiB (`sctp` v1.12.0 `defaultMaxMessageSize`). `Send` blocks while the channel's buffered amount is above a high-water mark (1 MiB) and resumes below a low-water mark (256 KiB), so a backfill can't queue without bound.
- **`blob/<reqId>`: one channel per fetch.** A go-room `Stream` is raw bytes with no message boundaries, so Irori frames the request itself: the fetching Core opens the stream, writes a 4-byte big-endian length and then the JSON request `{id, sha256, offset, len}` (at most 4 KiB), and reads raw bytes until the other side closes. The serving Core reads the length-prefixed request, then reads from the file and writes in 16 KiB chunks under the same high and low water marks. It is resumable by offset, and Go checks the length and hash and moves the file into place, as before (a stream cut by a dying connection can look like a clean EOF). At most 4 concurrent blob channels per peer that this side opens (`MaxStreams = 4`); `OpenStream` waits for a slot. The receiving side takes up to 8, because it frees a slot only when its handler closes the stream, so a fetch that is cancelled and replaced doesn't find the server still counting the old one. A cancelled fetch closes its stream; `Stream.Close` also unblocks the server's `Write` if it was blocked.
- `board/<boardId>` labels are reserved for Shared Boards and refused in v0.4 (where the iroh design reserved the `irori/board/1` ALPN).

**Revoke closes the connection.** Revoking a device (§3) drops it from the accept set and calls `Peer.Close`, which closes the `PeerConnection` and every channel on it, and go-room doesn't reconnect after a local close. It also leaves the old mesh topic once rotation completes (§4.2).

### 4.4 ICE: the home server's STUN and TURN

**The ICE list for each new connection** (go-room reads `Config.ICE` per connection, so a change applies to the next one and ones already up keep their path):
- for each home server whose hub is connected: `stun:H:U`, `turn:H:U?transport=udp` and `turn:H:T?transport=tcp`, with that server's credentials, where `H` is the address the hub connection went through. At home that is the LAN address and `U = T = N`; away it is the public address with the mapped ports from `node.addr` (§4.2);
- the advanced TURN relay, if one is set (below);
- **no public STUN.** The server's TURN port answers STUN Binding, which gives away devices their public address for hole punching. With the server off, a device away from home can't signal at all, and on one network host candidates are enough, so public STUN would never make a connection that otherwise fails. go-room's `DefaultSTUN` stays for Toru.
- On the server itself, the list names its own LAN address, with credentials it issues locally.

**The TURN server** runs on the home server, on `pion/turn/v5` (MIT, already in go-room's module graph), as Toru's `cmd/toru-relay` does:
- **Sockets:** UDP N, and TURN over TCP on N behind the hub's first-byte split (§4.2). No TLS TURN (`turns:`): what TURN carries is already DTLS, so `turns:` would add nothing but a certificate problem (pion/ice's `InsecureSkipVerify` for a self-signed one isn't exposed through pion/webrtc's `SettingEngine`).
- **Relayed addresses** are allocated on the server's LAN IPv4 address. Those sockets are never mapped on the router. They don't need to be: every packet to or from them is between the server and a device on its own LAN, or another relayed address on the same server. Two away devices that both relay through the server meet relay-to-relay, inside the PC.
- **Credentials:** the TURN REST scheme, as toru-relay: `username = "<expiry unix seconds>:<deviceId>"`, `credential = base64(HMAC-SHA1(turnKey, username))`, realm `relay`. `turnKey` is 32 random bytes made on the server, kept only there (`turn.key`, stored like the device key under D2), and never sent anywhere. Credentials last 12 hours, as toru-relay's do: a relayed connection lasts only as long as the credentials it was made with, because pion's allocation refreshes reuse them. go-room's credential loop renews them at 80% of the lifetime, so new connections always get fresh ones.
- **Issued only over the hub:** a member's `turn.get` on its authenticated hub connection gets a `turn.creds` answer for its own device id. There is no HTTP credential endpoint on the home server.
- **Guests get narrower credentials,** so a remote pairing works on networks that block direct paths: a guest's `turn.get` gets `username = "<expiry>:guest-<random>"`, valid until its guest topic closes, whose allocation may send only to the server's own relayed addresses. A code holder can reach A's relayed candidate and nothing on the LAN.
- **Revocation doesn't wait for expiry.** The TURN auth handler is Irori's own function: on every authenticated request, including the allocation refreshes pion makes at most every 10 minutes, it checks that the username's device id is still certified and unrevoked. A revoked device loses its relayed paths at its next refresh.
- **Which peers it relays to.** For a member, the permission handler admits only peer addresses inside the server's own interface subnets. It refuses loopback, link-local, multicast, unspecified and public addresses. So the server is never a proxy to the internet, but an authenticated device can send UDP to any host on the home LAN through it. That is said plainly in §8: it is the price of relaying to LAN devices, and only your certified devices hold credentials.
- **Limits** (from toru-relay's `limit.go`): 8 allocations per device and 32 in total.

**The advanced relay setting.** Settings → Devices → Advanced keeps today's TURN setting: a TURN REST credential URL, and optionally TURN URLs, for a relay you run or rent elsewhere. It is added to the list beside the home server's, never instead of it. The credential URL's query (often the provider's key) is cut from every log line, status detail and the dialog, as before.

**What remains impossible**, and Devices says which one applies:
- **the server is off or unreachable and the device is away from home:** no signaling, so no new connection (accepted, decision 33). Connections already up survive, because their traffic never touches the hub;
- **the home ISP uses CGNAT:** the router's own external address is shared (100.64.0.0/10, or private space for a router behind another router), so a mapping succeeds and still reaches nobody. Devices away from home can't reach the server, and no port forward helps; only the advanced relay setting does;
- **the server's network is on the Public firewall profile** (Windows): the "private networks" allow from the firewall dialog doesn't cover it, so nothing reaches the server, even on the LAN. Devices says so on the server; Irori doesn't change the profile of a physical network (Toru does that only for its own virtual adapter).

The path (direct or relay) and the RTT are in `GET /v1/devices?detail=1`, not in the dialog. A relayed connection stays relayed until it next reconnects; Toru's make-before-break upgrade to a direct path (its LAN agent) is a later improvement. Relaying through the home server costs its upload bandwidth, which is the home connection's.

### 4.5 Process model

- **In-process.** The net layer (`internal/mesh` over go-room) is goroutines in the Core, desktop and headless alike. There is nothing to spawn, supervise, kill on exit or version-match.
- **Started only when needed.** It starts once the store opens **and** there is at least one peer cert or an open pairing window. A device on its own dials no hub and binds no socket. Any failure in it (no hub reachable, the LAN port taken, ICE errors) leaves a working single-device app, with Devices saying "Can't reach your home server" or why. The home server's own pieces start by the same rule (§7): once it has a peer cert, at every start.
- **Reconnects.** go-room's hub client reconnects by itself, and the LAN carrier has nothing to reconnect. A peer connection that fails (ICE `failed`, the transport closes, no bye) is dropped, and go-room's `Mesh` reconnects it by itself: the lower id re-offers and the higher one re-sends `rtc.want`, 1 s, 2 s, 4 s ... apart for about a minute, so a Wi-Fi blip costs seconds, not a presence interval. It doesn't reconnect after a local `Close`, an `rtc.bye` or a refusal. After that minute, the Core's `Connect` on each presence takes over, with go-room's backoff from 1 s up to 60 s. When the lower id re-offers while the higher one still holds the old connection, the new one comes up beside it and replaces it: `OnPeerDown(ErrReplaced)` for the old `*Peer`, then `OnPeer` for the new one, so the Core keys its per-peer state on the `*Peer`, not only the device id.
- **Windows Firewall.** pion's UDP sockets now belong to `irori.exe`. A user-scope install (`WAILS_INSTALL_SCOPE=user`) can't add a firewall rule, so the first ICE gather raises Defender's "allow access" dialog for Irori. Starting lazily puts that dialog at pairing time, where the pairing screen says what it is for. Settings explains that denying it blocks inbound paths: paths that start outbound (hole punching, and TURN) usually still work, but the LAN carrier hears nothing. **On the home server denying it blocks the server itself** (the hub, TURN and the LAN carrier all listen), so its pairing screen says Windows asks once to allow `irori.exe` on private networks and that the server needs it (§7). Defender's dialog makes a program rule, so the one answer covers every port Irori uses.
- **LAN without the internet or the server.** Two devices on one network find each other through the LAN carrier and connect on host candidates, with the home server off and with no internet at all (§4.2).
- **The updater** needs nothing extra: there is no second exe to lock or wait for. The Core closes peer connections and leaves the rooms on shutdown, before `InstallOnExit` runs.

### 4.6 Topology

**Mesh, not a hub.** With three devices every device keeps up to two connections. Vector exchange gives transitive catch-up for free: a Mac row the node holds reaches the PC when the PC reconnects, even with the Mac asleep, because `Insert` already accepts any non-self device in seq order. The always-on node is just the peer most often up (§7). A hub would add a special role and a single point of failure for nothing at this size (decision D1). The home server (§4.2, §4.4) doesn't change this: its hub only introduces devices, and its TURN relay carries DTLS bytes it doesn't read for connections that can't go direct. The rows still travel device to device.

### 4.7 Build and release

- **One Go build.** go-room is pure Go (pion, `pion/turn`, `x/crypto`, and `huin/goupnp` in its `portmap` package). Irori doesn't import go-room's `mqtt` package, so paho isn't linked into `irori.exe`. The Windows build stays `CGO_ENABLED=0`. The macOS build (`release.yml`'s `macos` job, from b8729b0, unsigned today) is unchanged in shape: no Rust toolchain, no extra binary in the zip, the NSIS script or `Contents/MacOS`, and no second binary to sign.
- **Signing and notarizing the `.app`** is still in scope (D4): it covers `irori` alone. The Apple signing and notarization secrets are copied into the irori repo's Actions secrets.
- `Info.plist` gains `NSLocalNetworkUsageDescription`. Without it, macOS Local Network privacy silently blocks the LAN host candidates and the LAN carrier's broadcasts.
- The Mac's mod and attach paths (`presence/*_other.go`) have never run live, so a Mac smoke run (attach, wake, capture on the Mac alone) comes before the three-device run (§10).
- `go.mod` pins an exact go-room version, which pins pion and goupnp through it. A change in go-room is a go-room release and a bump here, never a `replace` on `main`.
- **Checks:** anything that touches networking is also cross-compiled with `GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 go build $(go list ./internal/...)` from Windows before it merges, since there is no CI. The root package can't build for darwin from Windows (wails needs cgo there), so the macOS release job's build is its check.

### 4.8 What go-room must offer Irori

The API Irori builds on (module `github.com/StephenSHorton/go-room`, package `room`): what go-room v0.1.0 has, with the home server additions of decision 33 (go-room v0.2.0) folded in and listed after the code.

```go
// Codes and secrets (topic = app + "/" + hex)
func NewCode() string                                   // XXXX-XXXX-XXXX-XXXX, ~79 bits
func NormalizeCode(in string) (string, bool)
type Secret struct { Key [32]byte; Topic string }
func SecretFromCode(app, code string) (Secret, error)   // scrypt(code, salt = app), as Toru
func SecretFromKey(app string, ikm, info []byte) Secret // HKDF, for high-entropy keys (the mesh topic)

// Signaling: one Signaler per room, over any number of carriers (§4.2)
type Envelope struct { V int; ID, From, To, Type string; At int64; Body json.RawMessage }
func Decode[T any](env Envelope) (T, error)
type Signaler interface {
    Send(to, typ string, body any) error  // sealed once, published on every carrier; to "" = everyone
    Connected() int                       // carriers up
    Self() string; Topic() string
    Close()
    // plus an unexported method: only Open builds one, so sealing,
    // de-duplication and the age check are always go-room's.
}
type SignalOptions struct {
    MaxAge time.Duration                  // default 2 min
```

### 5.2 The sync protocol (Core ↔ Core frames on the `sync` channel)

```
hello   { v:1, deviceId, personId, epoch, coreVersion, schema, vector, wallMs }
rows    { events: [ {d, s, h, a, k, p: base64(payload), sig: base64} ] }   // ≤ 1 MiB, ≤ 500 rows, (device, seq) order
vector  { vector }                                                     // after each applied batch, and every 30 s
ping    { t }  /  pong { t }                                            // every 15 s; liveness only, never logged
person.secret { epoch, sealed }                                         // after a rotation (§3); only to certified, unrevoked devices
```

Each frame is one `Channel` message (§4.3). Blob fetches don't use these frames; each has its own `blob/<reqId>` data channel (§4.3). The request is `{id, sha256, offset, len}` and the reply is the raw bytes.

- **On connect,** each side sends `hello`, checks the other's `personId`, `schema` and protocol version, and that the `devicePub` the handshake verified (§4.3) matches the cert for its `deviceId` (a mismatch is refused and shown). Then it streams `Missing(peer.vector)` in batches. It sends the next batch when the peer's `vector` shows the last one applied.
- **`person.*` rows go first.** Catch-up sends every `person.*` row the peer lacks before anything else, because `Insert` needs a device's cert before it accepts that device's rows, and `(device, seq)` order would otherwise put a device's rows ahead of the cert another device wrote for it.
- **A row refused only for "no cert yet"** is held in memory for that peer's stream and retried when a cert arrives. It is not counted as a forgery, and only that device's stream waits. **Held rows are capped per peer** (2,000 rows or 8 MiB, whichever comes first). Past the cap they are dropped and asked for again by vector later, so a peer sending rows for device ids that will never be certified costs bounded memory.
- **Live:** every committed `Append` or `Insert` is offered to each connected peer whose last-known vector lacks it. Rows relay: a Mac row inserted on the node is pushed on to the PC.
- **The same (device, seq) twice.** Today `Insert` returns nil for a seq it already holds without looking (`sqlite.go:253`, "already held; rows never change"). In v0.4 it compares the incoming row's signed bytes with the stored row's. Equal is a harmless duplicate. **Different is proof that the device signed two rows for one seq**: by theft, or by accident when a data dir or VM is restored from backup or cloned. Both rows are kept in a `forks` table, that device's stream stops on this device, it is marked "signed two different histories" in Devices with Remove, and the fork row is offered to peers so every device learns of it.
- **My own rows coming back.** If a peer's `hello` vector holds more of my own seqs than I do, my data dir was restored or copied. Today `Insert` refuses them (`ErrOwnDevice`, `sqlite.go:220`). In v0.4 the Core accepts its own rows back when they verify against its own key, and **blocks `Append` until it has caught up**, so it can't reuse a seq it already sent. Devices shows "Restoring this device's rows from <peer>". If it had already written different rows at those seqs, that is a fork (above), and the fix is Reset (§3).
- **The payload travels as base64 of the stored bytes,** so the bytes the signature covers survive the trip (§5.3) and no JSON re-encoding can change them.
- **Insert in batches:** `Store.InsertBatch(events)` takes one transaction per batch. The first catch-up after pairing can carry a whole capture backfill.
- **A gap** (`ErrGap`) means a batch arrived out of order. The receiver sends its `vector` and the sender restarts from there.
- **Schema:** a peer with a newer `schema` or a newer kind version still syncs. Unknown kinds are stored and ignored by folds, because "payloads only gain fields" is already the rule. A peer older than this Core's minimum gets `peer.down reason: "version"`, and Devices says which device to update.

### 5.3 Signed rows

- **A store migration adds `sig BLOB`** to `events`. `store.Event` (`store.go:23`) gains `Sig` with `json:"-"`, so `/v1/events` output doesn't change.
- **What is signed:** `sig = ed25519(device key, "irori/row/1" || device_id || seq || hlc || actor || kind || sha256(payload))`, with length-prefixed fields.
  - **`actor` is covered.** research/06 left it out, but `isOwner` reads the actor, so a forwarder could otherwise turn an agent's row into a `user:` row.
  - `payload` is the exact stored bytes. The column is already `BLOB` (`sqlite.go:67`) and `Insert` stores what it was given, so verification uses what is on disk.
- **`Append` signs every row.**
- **`Insert` verifies before storing:**
  - the row's device has a valid cert for my person (chain to the pinned root, §2), in the log or earlier in the same batch;
  - the signature matches the cert's `devicePub`;
  - the row is not above that device's effective cut (§5.5);
  - its kind isn't local;
  - **its HLC is above that device's previous row's HLC** (each device's clock only moves forward, and the signed rows prove it);
  - its HLC is not more than 2 minutes ahead of local wall time (§5.6).

  A signature, cert, cut or kind failure is refused and counted per peer in Devices, and the stream from that peer pauses for that device. An HLC that goes backwards is treated like a fork: that device's stream stops and it is flagged.
- **Writer rules are checked by the folds, not by `Insert`** (§6.0), because they need folded state (who owns a delivery, who holds a lease).
- **Store stays crypto-agnostic.** It takes a `Signer` and a `Verifier` at `Open` (interfaces implemented by a new `internal/identity` package). The fake transport tests run real keys.

### 5.4 The one-time migration

v0.4's first start runs a migration before the net layer could start.

- **It copies `irori.db` to `irori.db.v0.3` first.** `migrate` refuses a schema newer than the build (`sqlite.go:148`), so v0.3.2 can't open a migrated database. The copy is the way back.
- **It back-signs every existing row** that this device wrote.
- **It moves `policy.set` and `member.joined` rows** into `local_events`, leaving each original seq in `events` as kind `local.moved` with payload `{}`. That way seqs stay gapless and no policy history ever replicates. Every replay (inbox, coord, capture, notify) skips `local.moved`.
- **It is a Go migration step.** The framework runs only SQL strings today (`sqlite.go:57`). Back-signing and moving rows need a step that runs Go code with the `Signer`; §5.7 adds that kind of step.

**This is the only time Irori rewrites rows.** It is safe because nothing has left the device as a peer: v0.1–v0.3 had no transport, and the migration runs before the net layer first starts. Two caveats, stated plainly:
- a v0.3 export or a `/v1/events` consumer that cached rows holds the old, unsigned copies. They can never be inserted into a v0.4 mesh (they fail verification) and they differ from the migrated rows (`local.moved`), so any such cache must be rebuilt, not trusted;
- once a device has synced, rows never change again.

The migration is idempotent: it is marked done in `schema_migrations`, and an unsigned own row on a later start is a startup error, not something to fix silently.

### 5.5 Revocation cuts

- **Which revokes count.** A revoke is honoured if its writer was ever validly certified (§3). This doesn't depend on which rows a device has already folded, so every device reaches the same set of revoked devices from the same rows.
- **The effective cut** of a device is the lowest `cut` among all honoured revokes of it. A device that holds a different row at the cut than `cutHash` names has found a fork (§5.2) and flags it.
- **A revoked device's rows above the effective cut are refused by `Insert`.** Rows above it that a device already holds (heard before the revoke, or before a lower cut arrived) are moved to a `refused_events` table. Devices shows them as "N rows after removal" and nothing folds them.
- **Moving rows out re-folds what they touched.** A moved row may already have marked a delivery delivered, taken a lease or closed a task. Each service re-folds every entity that a moved row touched from the remaining log (§6.1). The fold-order tests cover it (§10).
- `refused_events` rather than kept-but-hidden (research/06) because then every reader, including `List`, `Subscribe`, the API and the tools, is correct with no filter to forget. The table is the record that they existed.
- **`Vector` reports `min(max, cut)` for a revoked device,** and `Missing` never sends past it. Otherwise one device that heard extra rows and one that didn't would ask each other for them forever.
- The result: every device refuses exactly the same rows once it holds the same revoke rows, so the folds agree (research/06 "Removal").

### 5.6 Clocks

`hlc.Observe` (`hlc.go:43`) takes any value up to 2^62. Bounding the local clock alone isn't enough: a stored row keeps its HLC, so a year-3000 row would win every fold that orders by HLC, for good. Three rules together close it:
- **Each device's HLCs only increase** (§5.3). A device can't write behind its own last row.
- **A row more than 2 minutes ahead of local wall time isn't stored yet.** That device's stream pauses on this device until local wall time is within 2 minutes of the row's HLC, then continues. Every device applies the same wait against its own clock, so all of them settle the same way. `Insert` also calls `ObserveBounded(remote, wall + 2 min)`, so the local clock never jumps.
  - A device whose clock is slightly fast just syncs a little late. A row stamped far in the future blocks that device's stream for good, because rows are never re-stamped and the stream is gapless. Devices shows "Mac's clock is ahead: its rows are waiting", and the fix is to correct the clock and Reset that device (§3).
  - Each Core compares its wall clock with each peer's `hello.wallMs` and shows the same warning line on the device whose clock is off, before it writes far-ahead rows.
- **Nothing that grants authority is decided by HLC order** (§6.0). HLC orders display and snapshots of an entity's owner-written rows; who holds a lease, which answer counts and where a delivery goes are decided by the owning device.

Rows are never re-stamped.

5. **A paging cursor:** `Filter.After` becomes a `(hlc, device_id, seq)` cursor. Today `inbox/state.go:228-245` and `capture/service.go:187` page with `AfterHLC` (strictly after), so rows that two devices wrote at the same HLC are dropped at a page boundary. coord already works around this (`coord/impl.go:217-254`); it moves onto the cursor too.
6. **Go migration steps** in the migration framework, alongside the SQL ones, with the `Signer` available; the one-time migration (§5.4) as the first, after the `irori.db.v0.3` copy.
7. `ObserveBounded` in `hlc`, and the future-HLC hold in `Insert`.

## 6. Cross-device features

### 6.0 Owners and requests

Each entity has one owning device, and only it writes the rows that take effect:

| Entity | Owner | Rows only the owner writes | Requests anyone may write |
|---|---|---|---|
| a delivery with `To` set | the device whose id prefixes `To` | `delivery.state` (hold, release, dismiss, move, delivered), `wake.issued`, `turn.*` | `delivery.decided` |
| a delivery with no `To` yet (repo-addressed) | the device that wrote its first row | the assigning `delivery.state` | `delivery.decided` |
| a lease | the holder's device | `lease.renewed`, `lease.released`, `lease.refused` | `lease.stolen` (actor `user` only) |
| an ask | the asking agent's device | `ask.resolved` | `ask.answered` |
| a revive | the target session's device | the wake itself | `revive.requested` |
| a home server's addresses | the server's device | `node.addr` | none |

- **Every fold checks the writer.** A row of an owner-only kind from any other device is ignored and counted ("N rows ignored: wrong device" in Devices). Each kind gets a test with a row from the wrong device.
- **The owner applies the first request it folds** and writes the result. Every device shows the owner's row, not the requests, so they all agree even when two requests crossed.
- A revoke is the one exception: it ends the revoked device's leases and deliveries everywhere without a row from that device (§3).

### 6.1 Folding other devices' rows

Today each service folds rows only at startup replay and through its own writes (`inbox/state.go:259`, `coord/impl.go:573`, `capture/service.go:215`). Nothing applies the rows that `Insert` brings in.
- **Every service gets a subscribe-and-apply loop.** Each loop handles the store's resync signal (the zero event, `sqlite.go:440`) by replaying from its cursor.
- **Folds must accept late rows.** A row from a device that was offline arrives with an older HLC than rows already applied.
- **The rule:** each entity (a delivery, a task, a lease, a card) keeps its newest snapshot by `(hlc, device_id, seq)` among the rows it accepts, not by arrival order. Folds that are not order-free re-fold that one entity from the log when a late row lands, or when a row is moved to `refused_events` (§5.5).
- Each service gets one test that feeds the same rows in two orders and compares state.

### 6.2 One roster

There is no Roster tab any more (§9); the mesh roster is what the Inbox's recipient picker, routing and the Board read.

- `Core.Agents()` (`core/core.go:275`) splits in two:
  - **`LocalAgents()`** is presence plus local Grok members. It feeds attach (`api/stream.go:83`), Revive (`roster_service.go:275-300`) and presence recording.
  - **`MeshAgents()`** folds every device's `agent.*` rows. It feeds inbox routing (`inbox/route.go:16-44`), coord `observe`, the bypass sender check (decision 10 reads the sender's `PermissionMode`) and the GUI.
- **A remote `device.started` retires that device's earlier cards.** Without it, a host that crashed would leave its cards live forever, because `record` only writes `gone` while it is running.
- **Cards cross between your own devices** with cwd and permission mode (Tier 0), without `LastText`, `Transcript` or `PID` (§2). Names resolve across the mesh. A name that matches live agents on two devices is an error naming both (v0.2 §2), with the device in each candidate.

**Device liveness** comes from go-room's peer up and down, mesh-topic presence (§4.2), `ping` and the time of the last sync. It is kept in memory and never logged. It has three states:

| State | Meaning |
|---|---|
| **connected** | a ping arrived within 45 s |
| **recent** | not connected, but synced within the last 10 minutes |
| **offline** | neither |

**An offline device is not the same as its agents being gone.** Its cards show with a "Mac offline" chip, its deliveries and leases **freeze**, and nothing is reassigned or force-released automatically. You can ask to release a lease (`lease.stolen`) or move work off an offline device (`delivery.decided`) by hand; a move takes effect when the owner folds it, or at once if the owner is revoked. The grace clocks in `coord.observe` and `inbox.sweep` apply to local holders only.

### 6.3 Inbox: delivery and wakes to remote sessions

**Who writes what** follows §6.0 (research/01 §5: the target's device holds the take-lock).
- `message.sent` and the first `delivery.state queued` are written by the sender's device, **with no hold decision**.
- Everything after that is written by the delivery's owner.

**The host decides holds.** Today `messages.go:141` calls `b.hold(&m, recipient, cards)` on the sending Core with the sender's own policy (`policy.go:60-84`: Pause, allowlist, block list, bypass). Across devices that would let the PC bypass the Mac's block list and the Mac's Pause all. So in v0.4 the owner runs `hold()` (block, allow, bypass, Pause, hop limit, rate limit) with **its own** policy when it folds the `queued` row, and writes `held` or proceeds to wake. The sender's `queued` is only a suggestion. For a message between two sessions on one device nothing changes in effect.

**The path for a message to `mac/<session>` sent from the PC:**
1. The PC writes `message.sent` and `delivery.state queued`.
2. The rows replicate.
3. The Mac's inbox folds them, runs `hold()` with the Mac's policy, and either writes `held` or fires `WakeReady`.
4. The Mac's attach stream wakes the session through the mod (or the Grok channel push), and writes `wake.issued` and `delivery.state delivered`.
5. Those rows replicate back, and the PC's inbox shows "delivered".

If the Mac is asleep, the node holds the rows and the Mac picks them up when it wakes. Wakes reach only streams registered on the hosting Core (`api/stream.go:140`); that stays the rule.

**Release, Dismiss and Move from any device.** Today Release and Dismiss (`inbox_service.go:111,116`) write `delivery.state` from whichever GUI you click. In v0.4 the GUI writes `delivery.decided {deliveryId, choice: release|dismiss|move, to?, by, at_device}`, with actor `user`. The owner applies the first one it folds and writes the real `delivery.state`; any later one shows as "already handled". On this device's own deliveries the owner is this device, so the click still takes effect at once. A move hands ownership to the new `To`'s device through the owner's move row.

**Sweep:**
- `sweep` (`inbox/sweep.go:139-165`) plans **only deliveries this device owns**. Today a remote recipient counts as gone (its card isn't in `cards`), so its work would be moved after `GoneGrace`.
- **No sweeper election.** Repo-addressed work with no owner yet (`To == ""`, `actAssign`) is owned by the device that wrote it, so only that device assigns it, using `MeshAgents()` for front-desk selection. No partition can give two assigners. If that device is offline its unassigned work waits, and you can move it by hand.

**Rate and hop limits.** The hop limit reads replicated rows. `DIRECT_LIMIT`'s counts (`b.pairs`) are filled in the delivery fold (`inbox/state.go:335`) as well as in `sendLocked`, so once the apply loop (§6.1) folds remote `message.sent` and delivery rows, they count rows from every device. A test proves it.

**Policy** (allow and block lists, Pause all) stays per device (`policy.set` is local), and because the host decides holds, Pause all on the Mac pauses wakes into the Mac's sessions no matter which device sent the message. A "pause every device" switch would need its own replicated kind (decision D5). The bypass rule (decision 10) reads the sender's card from `MeshAgents()`. Your own agents on another device count as yours: same person, so the usual rule applies.

**Reviving a closed session on another device.** The sending device writes `revive.requested {target, deliveryId, by}`, and only the host acts on it. research/04 §5's gate applies:
- your own message to your own session on the same device: automatic;
- **cross-device, or into bypass mode: an approval** (§6.7). The approval counts only as an `ask.answered` row with actor `user`, written by a GUI (§2), whose payload names `{askId, target, deliveryId}` matching the request. The host checks all three before it wakes anything.

### 6.4 Board across devices

- `task.*`, `lease.*` and `blocker.closed` replicate, so one Board shows every device's work.
- Tasks have many writers and fold in `(hlc, device, seq)` order. Card times use the row's `at` (the writer's wall clock), which §5.6 bounds.
- **Leases are soft across devices:**
  - `acquire` checks only rows it already has (`coord/impl.go:945`), so two devices that acquire while partitioned both write `lease.acquired`;
  - `apply` detects two live leases on one resource and keeps both, marked **conflict**;
  - **the lease of the lower device id stands** and the other holder's Core writes `lease.refused` for its own lease and tells its agent at its next turn. Device ids can't be moved by a fast or slow clock, unlike "earlier HLC wins";
  - the Board shows the conflict on the lease card.
- **A remote lease never expires by local time.** `until` is the writer's wall clock, so `acquire` and `observe` never treat another device's lease as lapsed. It ends only with a row from its holder's device (`lease.released`, or expiry written by the holder's own Core), a `lease.stolen`, or a revoke.
- **Steal.** `lease.stolen {leaseId, by}` with actor `user` ends the named lease on every device, even if the holder renewed it at the same time on the other side of a partition: a renewal doesn't revive a stolen lease. The holder's Core tells its agent at its next turn. A test covers the steal crossing a renewal.
- Only the holder's device releases a lease automatically (`releaseGone` at `coord/impl.go:1039`, `observe` at `:629-676`), and the fold ignores a release from any other device (§6.0).
- Needs-you counts across devices, through `isOwner` and the owner set in `BoardFilter` (§2).

### 6.5 Capture per device

- Each device tails its own transcripts and watches its own repos, as in v0.3. Its capture rows replicate.
- `capture-cursors.json`, the repo watch list and commit linking stay per device, because linking needs the local worktree root (decision 15).
- `internal/scrub` already runs at ingest, before a row is signed; that ordering is now load-bearing, since a replicated row can't be scrubbed later (§5.1). The same scrubber now also runs on card `Title` (§2).
- **`show` and `why` for another device's edit:** the patch blob is fetched from the origin device on demand over a blob channel (§4.3), cached locally and checked against its sha256. If the origin is offline, the tool says "patch on Mac (offline)".
- Transcripts are never fetched.
- `timeline` and `why` work across devices for agents, because turns, edits and commit links replicate.

### 6.6 Attachments (decision 28)

- **Writing:** `send` and `task_comment` gain `attach: [path]` (and the GUI composer a file picker). The writing Core:
  1. resolves the path to its canonical form, **following symlinks**, and applies the never-leave rules to the resolved path: anything inside the data dir, `.env*`, private keys, credential stores. A path that resolves into one of them is refused with a reason;
  2. copies the file into a separate attachment store, `<dataDir>/files/<aa>/<sha256>`, stored uncompressed and with no 4 MiB cap (v0.3 §4's blob store is gzip, capped and meant for patches);
  3. scrubs nothing inside it (it's your file);
  4. puts `{sha256, name, size, mime, device}` refs on the row.
- **Size cap:** 256 MiB per file between your own devices (decision D6).
- **Fetching:** the receiving agent calls `attachment_get {sha256, to?}`. Its Core fetches over its own blob channel (§4.3; resumable by offset) from the origin, or from any device that already has it (any device that fetched a file can serve it), checks the hash, and writes it to `to` (default: a per-session folder in the data dir). The result is the local path.
- **`name` comes from a remote row**, so it is reduced to a single safe file name (no separators, no `..`, no drive letters, no reserved Windows names) before the default path is built. A row can't choose where a file lands.
- Files are fetched when asked for, never pushed eagerly. A device serves only hashes its log references.
- People's boards reuse this unchanged with a board-scoped fetch.

### 6.7 Approvals and notifications on every device (decision 26)

- **Held deliveries and Needs-you tasks are already rows,** so each desktop Core's `notify.Watch` posts the card from replicated rows and clears it when the owner's resolving row arrives. The card id (`held:<deliveryId>`, `needs:<taskId>`) is already stable across devices. Release and Dismiss on any device write `delivery.decided` (§6.3).
- **The `notify` tool's asks move to rows.** Today `tools/notify.go:22` waits in memory for 5 minutes, so only the asking device could answer. Now:
  - `ask.posted {askId, by, text, actions, until}` from the asking device; `ask.answered {askId, choice, at_device}` from any GUI;
  - every desktop device shows the card;
  - **the asking device decides**: it takes the first answer it folds, writes `ask.resolved {askId, choice, answerRef}`, and every device shows that choice and clears the card;
  - the asking Core delivers the answer to its agent as before, at its next turn if it has gone.
- **A headless Core never shows cards** (`notify.Post` returns false), so approvals are answered from a desktop device and the node acts on the row.

### 6.8 API

- `/v1/events/stream`'s `since` becomes a vector (`?since=<deviceId>:<seq>,...`). Today it resumes by this device's seq only (`routes_events.go:89,140`), which would silently skip remote rows. The old single-seq form still works and means "my device only, the rest from now". Event JSON doesn't gain `sig` (§5.3).
- `GET /v1/devices` returns `[{deviceId, name, role, os, state, warning?}]`, matching the Devices dialog (§9). The detail behind a warning (skew, refused and ignored counts, rows behind) is in `?detail=1` for debugging.
- `/v1/device` and health stay this device. Health gains `net: {state, peers}`.
- No pairing or revoke routes exist (GUI only, §3). No route accepts a `user:` key from the caller (§2).
- The `events` tool shows the writing device on each row.
- **The person's view needs the GUI's credential** (decision D10). Today a bearer token with no identity header is "the person's view" (`routes_board.go:18`), and it sees everything. The token is in `irori.json`, which any agent on the machine can read, so in v0.4 an agent on the PC holding it would read every device's messages and capture. The recommended fix: the person's view requires a per-run secret that only the GUI process holds in memory (handed to the frontend through a Wails binding, never written to disk); a bearer token alone gets the same view as an unidentified agent. As built, the GUI never reads the person's view over the API (it uses Wails bindings), so the secret is never handed on at all.

## 7. The always-on node and the home server

The node is the Windows desktop that stays on (decision 2). Its cert has `role: "node"`. Since decision 33 it is also **Irori's server for your devices**: the persistent instance that coordinates every device connecting, at home or away.

**Recommended: run the normal desktop app there, minimised to the tray** (decision D3). It gets the updater, notifications if you sit at it, and the same pairing screens. A headless Core has no updater (`InstallOnExit` is wired only from `tray.go:229`), so a headless node would drift until its peers refuse it as too old (§5.2).

The fallback is `irori serve --headless` (decision 8), started by a Task Scheduler entry at logon that `irori node install` writes (it shows the exact command it registers). At boot without a logon it would forward rows but not wake sessions, so logon is the default. Updating a headless node is by hand. Headless runs the home server too.

What it does:
- **Store and forward.** It holds every row and relays them. With the Mac asleep and the PC off, messages to either wait on the node. Wakes still need the host device to be up.
- **The home server** (below): the signaling hub, the TURN relay, port mapping and its `node.addr` row.
- **Hosts its own agents** if you run sessions there, exactly like any device. Wakes there use the mod or `--resume`; channel pushes don't register under `-p` (research/04 §5).
- **Shows no notifications** when headless. Approvals for its sessions are answered from another device.

It is not a sweeper, and its hub is for signaling only: repo-addressed work is owned by the device that wrote it (§6.3), and rows still travel device to device (§4.6).

**Pairing it:** from the desktop app on that machine, like any device. If it runs headless later, the pairing already holds. In practice it is the first device: Stephen's PC creates the person, turns the server on and pairs the rest to it.

### 7.1 The home server

**Turning it on.** Settings → Devices → "Home server: run it on this PC", device-local in `home-server.json`, offered first on the device whose cert says `node`. Any device may run it, and a device that knows of two servers connects to both (one Signaler, two hub carriers, de-duplicated, §4.2), but one is the normal setup. Switching it off writes `node.addr {reach: "off"}` and closes everything below.

**When it runs.** By §4.5's rule: once the device has a peer cert or an open pairing window, and from then on at every start, before the first presence. A server with no other device yet binds nothing.

**What it starts,** in this order, each failure leaving the rest running and one line in Devices:
1. **The port.** One number N for TCP and UDP. On first start it is picked at random from 20000–29999 (below the ephemeral ranges of Windows and macOS, and not a fixed well-known port, so a scan for Irori's default port finds nothing), and saved in `home-server.json`. Later starts reuse it, so a manual port forward keeps working. If N is taken at a start, another is picked and saved, a new `node.addr` is written, and Devices says the forward (if manual) must change.
2. **Listeners:** TCP N on the wildcard address, split by `SplitTCP` into the hub and TURN over TCP (§4.2), and UDP N for STUN and TURN (§4.4). These are the listeners that must be on real interfaces, which is the point of the server. **Windows asks once to allow `irori.exe` on private networks** (Defender's dialog makes a program rule, which covers every port Irori uses); the turn-on screen says so first, and denying it means nothing reaches the server. On Windows, if the home network itself is on the Public profile, Devices says so (§4.4).
3. **The hub** (`Hub`, §4.2) with `Authorize` = a certified, unrevoked device whose key matches its cert, `AllowTopic` = this Core's open mesh topics, the TURN server for `turn.get`, and the LAN carrier as its bridge. The server's own mesh and pairing rooms use `Hub.Local()` beside its LAN carrier.
4. **The TURN server** (§4.4), relayed sockets on the primary LAN IPv4 address, `turn.key` made on first start.
5. **Port mapping,** when "Reachable from outside home" is on (the default once the server is on): `portmap.Start` for TCP N and UDP N, asking for the same external numbers. UPnP-IGD first, then NAT-PMP; a lease of 1 h (or whatever the router grants; some grant only permanent mappings, which are then removed on shutdown), renewed at half. A conflict on the external port takes another and keeps it in `home-server.json`. The mappings are removed on a clean exit and when the option is switched off.
6. **`node.addr`** (§4.2) from all of the above, written only when it changes, with `reach`:
   - `ok`: a mapping is up and the external address is public;
   - `cgnat`: the mapping is up, but the external address is in 100.64.0.0/10 or private space;
   - `unmapped`: the router answered neither UPnP nor NAT-PMP, refused, or mapping is off;
   - a public address you entered (below) is published as `via: "manual"` with `reach: "ok"`, since the server can't test it from inside.

**When mapping fails.** The server's Devices row shows one line with the fix: "Away from home your devices can't reach this PC. Turn on UPnP on your router, or forward TCP and UDP port 24817 to 192.168.1.20." Below it is an optional "Public address" field (an IP, or a host name you already have, with an optional port). Irori runs no dynamic-DNS service and never looks your address up through a third party, so with a dynamic public IP and no UPnP the manual address goes stale when the ISP changes it; the line says so. With `cgnat` the line says instead: "Your internet provider shares your public address (CGNAT), so devices away from home can't reach this PC, and a port forward won't help."

**Address changes.** A new DHCP lease, interface or network re-runs steps 4 to 6: TURN moves its relayed sockets to the new LAN address, mappings are made again for the new address, and one new `node.addr` is written. Connections already up keep running when they can.

**What the other devices do with it.** They fold `node.addr` (§4.2) and dial the hub at every address in it, plus the LAN address its datagrams come from, plus the last one that worked. They build the ICE list from whichever address the hub answered on (§4.4). A device that can't reach the server says, once, in Devices: "Can't reach your home server (PC). Away from home your devices connect through it."

**The physics** (accepted in decision 33):
- server on, device anywhere with internet, mapping up: the device reaches the server's hub and TURN, and through them every other device that is up;
- server on, device away, no mapping (or CGNAT) and no manual address: that device can't connect;
- server off, device away: it can't connect. Connections already up keep running;
- server off, two devices on one network: they still find each other on the LAN carrier and sync directly (§4.2).

## 8. Security

**Trust boundary:**
- A connection carries sync frames only after the handshake verifies a `devicePub` with a valid, unrevoked cert for your person (§4.3). The home server's hub and TURN admit only the same devices, by the same check, plus guests for an open pairing window (§4.2, §4.4). Everyone else is refused before any frame is read, and an open connection is closed the moment its device is revoked.
- `Insert` independently refuses rows that are unsigned, signed by an uncertified device, past a cut, out of HLC order, too far ahead, or of a local kind, and the folds ignore owner-only rows from the wrong device (§6.0). **Both layers hold:** a test runs the mesh with the handshake's cert check turned off and an uncertified peer connected, and proves `Insert` and the folds stand alone.

**A stolen device.** It holds the person secret (research/06 decision 8, recommendation (a)), so the person signature adds nothing inside your mesh (§2). The controls:
- a cert row must chain to the pinned root through valid certs (§2), so a device the thief certifies after its cut is refused, and a fresh "root" is refused;
- a device that signs two rows for one seq is caught and flagged (§5.2);
- revoke is one click from any other device, works the same whatever order the rows arrive in, and rotates the person key (§3, §5.5);
- if the thief revokes you back, both are out until you re-pair yours from a third device; if it revokes everything, you make a new person and your rows come with you (§3);
- Devices lists every certified device, so a stranger shows up.

Key storage at rest is decision D2.

**Who sees metadata.** No third party sees anything: there are no brokers and no public STUN servers (decision 33). The home server is one of your own devices; its hub sees which of your devices are connected, from which IP addresses, and when sealed envelopes go by, never their content (it could open them, since it holds the person secret, but it has no reason to and doesn't). Anyone on a network a device is on sees its LAN datagrams: their size, timing and source address, with a tag that changes every 5 minutes (§4.2). An advanced TURN relay, if you set one, sees IP addresses and DTLS-encrypted bytes. Data channels are DTLS end to end, and the handshake binds them to your device keys (§4.3). Settings says so on the Devices page.

**The home server's hub.** Everything that reaches a topic goes through two checks:
- **Who:** a member proves its device key over the TLS session's exporter, and the hub admits only a certified, unrevoked device whose key matches its cert (§4.2). A revoke drops that device's hub connection, its guest topics and, at its next refresh, its TURN allocations (§3).
- **What:** a member may subscribe only to the mesh topics the server's Core has open and to open guest topics; a guest only to the one pairing topic a certified device opened, while its window is open. So the hub isn't a relay for anyone else's traffic: it carries no topic it didn't compute or wasn't asked to open by one of your devices.

**The home server's exposure.** With mapping up, TCP N and UDP N on the router's public address lead to the PC, and only those: pion's own ICE sockets and TURN's relayed sockets are never mapped. **What someone scanning that address can learn or do:**
- **TCP, TLS:** a TLS 1.3 server with a self-signed certificate that has no names and changes at every start, requiring ALPN `go-room-hub/1`. After TLS it says nothing until it gets a valid `hello`, and anything invalid closes the connection without a reply. So a scanner learns that something speaks TLS there (and, with work, that it is Go's stack), not that it is Irori, whose it is, which devices exist, or any topic.
- **A guest `hello`** gets in only with a topic an open pairing window registered. That topic is derived from a 79-bit code through scrypt, it exists for at most 10 minutes, and a wrong guess looks the same as no window. Even inside, a guest sees only sealed bytes on that one topic, and the pairing words (§3) still stand between it and a cert.
- **TCP or UDP, STUN:** a Binding request is answered with the scanner's own address, as every STUN server does, which marks the port as STUN/TURN. An Allocate gets 401 with the realm `relay` and nothing that names Irori or you. Credentials are HMAC-SHA1 over a 256-bit key that never leaves the PC.
- **Floods:** the hub's connection, handshake and per-IP limits and TURN's allocation caps (§4.2, §4.4) bound what a flood costs the PC. A determined flood can still use the home upload; closing the mapping (switching "Reachable from outside home" off) ends it.
- **What a certified device can do through TURN:** send UDP to any host on the home LAN. Never to the internet, never to the PC's loopback (§4.4). That is the price of relaying to LAN devices; a stolen device keeps it only until it is revoked.

**Port mapping asks the router to open ports,** which is why it runs only on the device you made the server, only while "Reachable from outside home" is on, only for N, and removes its mappings when it stops.

**There is no LAN discovery for strangers.** A device's LAN datagrams open only with a room key; others drop them unopened. A device on the Public firewall profile (café Wi-Fi) sends none on that network (§4.2).

**The loopback API reaches further now.**
- An agent on the PC holding the loopback token can write rows that wake your Mac's sessions. That is intended (it is what cross-device wakes are). The Mac's own policy decides the hold (§6.3), and the hop and rate limits still apply.
- It can no longer mint `user` rows: no route takes a `user:` key from the caller, and `user` rows come only from Wails bindings (§2).
- Without the GUI credential it can no longer read the person's view, which now spans every device (§6.8, decision D10).
- `asUser` stays GUI-only. Pairing, revoke and any future person-key action go through Wails only.

**Rows carry no secrets:**
- wake tokens stay in memory;
- attach and member secrets are never logged;
- scrub runs before signing, on capture rows and on card titles; card `LastText` and transcript paths stay off rows (§2);
- the lockfile token, policy, keys and the person secret are device-local; the rotated secret travels only in a `person.secret` frame to certified devices (§5.2);
- go-room gets a `Sign` function, never the device key itself (§2), and nothing logs an envelope body or a TURN credential; `turn.key` stays on the home server and is never sent;
- peer text reaching an agent keeps the `trust=untrusted` fence. Your own other device's agents are fenced as `trust="member"` with the device named, so an agent sees where a message came from.

**Frame and resource limits:**
- 1 MiB frames from Go, an 8 MiB `Channel` message cap, 16 KiB SCTP messages, and at most 4 blob channels per peer (§4.3);
- at most 500 rows per batch, and a per-peer cap on rows held for a missing cert (§5.2);
- a device serves only blob hashes its log references, and attachment names are sanitized (§6.6);
- refused, ignored and fork counts are kept, and a nonzero one shows as the single warning line on that device (§9).

**The window**

  - Reviving a gone session moves to the agent chip on a card.

## 10. Tests that prove v0.4

- **Unit:**
  - row signing and verification vectors;
  - the handshake (§4.3): a valid `auth` passes; one signed by another key, over swapped or SDP-only fingerprints, or for a revoked or uncertified `devicePub` is refused, and no sync frame is read before it passes;
  - person certs: the chain to the pinned root, a self-cert other than the root refused even with a valid `personSig`, and the cut rules;
  - revokes: mutual revoke gives both revoked in either arrival order; the min-cut rule; `cutHash` mismatch flags a fork;
  - duplicate (device, seq): same bytes is a no-op, different bytes lands in `forks` and stops the stream;
  - own rows coming back: accepted when they verify, `Append` blocked until caught up;
  - HLC: a row not above its device's previous HLC is refused; a row 10 minutes ahead waits and then lands; `ObserveBounded`;
  - the SAS derivation (both sides agree; a different device key, DTLS fingerprint or code changes the words); the HMAC failure closes the window; a second `pair.hello` closes the window and that second joiner sees `pair.busy`;
  - the pairing code codec (normalizing typed codes), and the mesh topic derivation (a new epoch gives a new topic; the previous one stays open until every device has the new epoch);
  - `IsLocal` covering every kind;
  - the `(hlc, device, seq)` cursor at a page boundary with equal HLCs;
  - the one-time migration (the `.v0.3` copy, back-sign, `local.moved`, replay skips it, idempotent);
  - `isOwner` at every site in §2, including Needs-you for another device's owner key and a made-up `user:` key refused;
  - the API refuses a caller-supplied `user:` key, and a bearer-only request doesn't get the person's view (if D10 picks (a));
  - attachment names with `../`, separators and reserved names; an attach path that is a symlink into the data dir is refused;
- **Fold order:** for inbox, coord and capture, the same rows in arrival order and in a shuffled order that keeps each device's seq order give the same state. Also: rows moved into `refused_events` after they were folded (a delivery marked delivered, a lease taken) re-fold to the same state as if they had never arrived.
- **Writer rules:** one test per owner-only kind (§6.0) with the row written by the wrong device, ignored and counted.
- **Multi-Core in-process (`internal/mesh` test harness):** three Cores (PC, Mac, node) in one process with real stores and keys and a **fake transport**. The fake replaces go-room with Go channels and can partition, drop and reorder links. It must show:
  - pairing B from A copies the person, the root and certs, and B's earlier rows replicate and verify;
  - local kinds never cross, and a forged row (bad sig, uncertified device, local kind) is refused;
  - with the handshake's cert check turned off and an uncertified peer connected, nothing it sends is stored or folded;
  - Mac → PC catch-up through the node with the Mac gone;
  - a message from PC to a Mac session wakes only on the Mac, and `delivered` comes back;
  - **the Mac's Pause all and block list hold a message sent from the PC** (the host decides holds);
  - `DIRECT_LIMIT` counts messages sent from two devices to one pair;
  - Release clicked on the PC for a Mac delivery takes effect through the Mac's row; two Releases that crossed give one result;
  - a remote recipient is never swept as gone, and an offline device's lease freezes and doesn't lapse on another device's clock;
  - repo-addressed work is assigned only by its originating device, even across a partition;
  - partitioned lease acquires surface as a conflict, the lower device id keeps the lease, the other writes `lease.refused`;
  - a steal that crosses the holder's renewal ends the lease on all three;
  - a held delivery and an `ask.posted` clear on every device after one answer, and two answers that crossed show the one `ask.resolved` names;
  - a cross-device revive wakes only on a matching `user` answer from a GUI;
  - revoke with a cut gives the same fold on all three devices in every arrival order, refused rows land in `refused_events`, vectors converge, and the person key rotates on the remaining two;
  - a revoked device's open connection is dropped, and it can't connect again on the old mesh topic or through a pairing room;
  - a device restored from an old copy of its data dir gets its own rows back before writing; one that wrote over them is flagged as a fork;
  - a clock 10 minutes ahead: its rows wait, then land; nothing it wrote wins a lease or an answer;
  - an attachment fetched from the origin, then from a second holder with the origin gone, while live rows keep flowing on the sync stream.
- **go-room under Irori, on 127.0.0.1 only:** a Go integration test runs two real `internal/mesh` nodes on `MemHub` signaling (and on `MemLAN`, below) with `LoopbackOnly` peers (a loopback IP filter with loopback candidates, so a fresh test binary never opens a non-loopback listener or raises a firewall dialog). It pairs them, types the words, reconnects on the mesh topic, passes frames and a blob both ways while a backfill fills the sync channel, revokes one and sees its connection close. A second run forces TURN through the advanced setting's path: pion's `turn` server and an `httptest` credential endpoint, both on 127.0.0.1. It **fails rather than skips** when the peers can't connect.
- **Home server, on 127.0.0.1 only.** No test opens a wildcard, multicast or broadcast socket or reaches the internet: LAN tests run on `MemLAN`, or on a 127.0.0.1 socket whose `Targets` are 127.0.0.1 ports; the hub and TURN listen on 127.0.0.1:0; port mapping talks to fake gateways on 127.0.0.1; pion peers use `LoopbackOnly`. Each of these **fails rather than skips** when it can't connect.
  - *go-room, carriers:* one Signaler on two carriers (`MemLAN` and a hub) delivers each envelope once and makes one `PeerConnection` per peer; `Connected` counts carriers; presence fires on each carrier's connect.
  - *go-room, LAN:* the tag changes with the window and the previous window's still opens; a datagram with an unknown tag is never opened; a datagram sealed with another key, too old or a replay is dropped; unicast goes to the address an authentic envelope came from; the rate limit drops the excess; `OnHeard` reports the sender's address.
  - *go-room, hub:* a member with a certified key gets in and one with an unknown key, a bad signature, or a signature over another TLS session's exporter (relayed from a second connection) is closed with no reply; a missing ALPN, TLS 1.2, a late or malformed `hello`, and garbage are closed the same way; `AllowTopic` refusals; a guest gets only an open guest topic, and is dropped when it closes or expires; `Drop` closes a member and its guest topics; the welcome signature is checked and a hub signing with an unexpected key is refused; frame, topic, publish-rate and connection limits; `SplitTCP` sends TLS to the hub, STUN to TURN and closes anything else; the LAN bridge forwards an open guest topic both ways and never a mesh topic.
  - *go-room, TURN:* two `LoopbackOnly` peers forced to relay-only ICE connect through the TURN server on 127.0.0.1 with `Issue` credentials, over UDP and over TCP through `SplitTCP`; expired credentials, a wrong HMAC and a user `Authorize` refuses (mid-session, at the allocation refresh) are refused; the default `AllowPeer` refuses loopback, link-local, multicast and public addresses and admits the host's private subnets (a unit test of the filter, since the connect test must allow 127.0.0.1); guest credentials reach only relayed addresses; `RelayConfig.Fetch` feeds the credential loop and `Relay.TURN` lists only TURN.
  - *go-room, portmap:* against a fake IGD (an `httptest` server on 127.0.0.1 serving a description and the SOAP actions): map, external address, a conflict that takes another port, renewal at half the granted lease, a router that grants only permanent leases, removal on `Close`; the same against a fake NAT-PMP responder on a 127.0.0.1 port; CGNAT flagged for a 100.64.0.0/10 external address; a gateway that answers nothing gives `failed` without blocking.
  - *Irori:* two `internal/mesh` nodes pair and sync over `MemLAN` alone (no hub); three nodes with the "server" node stopped still sync the two others over `MemLAN`; a device on the hub alone (no LAN) pairs as a guest with the address typed, then connects through the hub with relay-only ICE through the server's TURN; B on the LAN alone pairs with A on the hub alone through the server's bridge; `node.addr` is written once per change, not per renewal, ignored from a wrong writer or a revoked device, and dialed LAN first; a revoke drops the hub connection and the next TURN refresh fails; the address shown on Add matches the row; the Devices lines (mapping failed, CGNAT, Public profile, server unreachable, port changed) come from fake mapper and listener states.
  - *No brokers:* a check, run with the other local checks, that `go list -deps ./...` for Irori names neither `go-room/mqtt` nor paho.
- **Single device:** with no hub reachable, the LAN port taken, or the net layer failing to start, the app works on its own and Devices says why.
- **Mac smoke (before the live run):** on the Mac alone, attach, wake and capture a session, and confirm the Local Network prompt appears.

## 12. Decisions for Stephen

1. **D1. Mesh or hub?** Recommended: **mesh.** Three devices is two connections each, and vectors already carry rows transitively. The node is the peer that's usually up, not a hub.
2. **D2. Where do the person key and device key live?**
   - (a) 0600 files (no ACL on Windows).
   - (b) DPAPI on Windows and the Keychain on macOS, with the files as wrapped blobs.

   Recommended: **(b)**. The person key can certify devices, and Go already owns the key (go-room gets only a `Sign` function), so this changes only `internal/identity`.
3. **D3. How the always-on node runs.**
   - (a) The normal desktop app, minimised to the tray, paired from its own screen.
   - (b) Headless (`irori serve --headless` via `irori node install`), paired once from the desktop app first.

   Recommended: **(a)**. It keeps the updater, which headless lacks; (b) stays as the fallback.
4. **D4. macOS in v0.4.** The Mac is one of the three devices. `release.yml` builds an unsigned `.app` today (b8729b0). Recommended: **signing and notarizing it is in scope**, with the Apple secrets copied into the irori repo. With go-room there is only the one binary to sign. The alternative is the unsigned build until a later release.
5. **D5. Pause all.** Recommended: **per device**, labelled with the device (research/06). Because the host decides holds, the Mac's Pause all covers messages from every device. The alternative is a replicated "pause every device" kind as well.
6. **D6. Attachment size cap between your own devices.** Recommended: **256 MiB per file**, fetched on demand.
7. **D7. The cards window first, as v0.3.3.** Decided by Stephen's prototype feedback (2026-10-27): only cards of shared work (§9).
8. **D8. Rotate the person key when a device is removed?**
   - (a) Yes, automatically: a new key goes to the remaining devices over their encrypted connections.
   - (b) Not in v0.4, because nothing outside your devices trusts the person key yet; add it with Shared Boards.

   Recommended: **(a)**. Removal is when a stolen key matters, and it is one row and one frame.
9. **D9. Agents' last-message text on other devices.**
   - (a) Keep it off the replicated rows; each device shows it only for its own agents.
   - (b) Scrub it and replicate it.

   Recommended: **(a)**. With the Roster gone nothing shows it prominently, and a scrub miss would be copied to every device forever.
10. **D10. Who gets the "person's view" of the loopback API (every message and capture row, now from every device)?**
    - (a) Only the GUI, through a per-run secret it holds in memory; a bearer token alone gets the agent view.
    - (b) Anything holding the bearer token in `irori.json`, as today, stated plainly in the docs.

    Recommended: **(a)**. Any agent on the PC can read `irori.json`, and with v0.4 that token would read your Mac's conversations too.
