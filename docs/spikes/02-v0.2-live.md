# Live check 02: v0.2 messaging on Windows

*2026-10-26, Windows 11, Claude Code 2.1.311, `v0.2-talk` @ d80ec0d.*

**Claude ↔ Claude through the mod.** A headless Core (`irori serve --headless`) and two `claude --bg` sessions loaded with `--plugin-dir mod`, `iroriPath` set through `--settings` `pluginConfigs["irori@inline"]`. Both sessions run with bypassed permissions, so the bypass hold rule let them through, as designed.

1. `irori-live-a` called `mcp__irori__send` to `irori-live-b`: "What is 17 times 23?"
2. The Core issued a wake to B; B's mod submitted it, reported `delivered`, then `engaged` at turn start.
3. B called `reply` with "391" (hop 1); the delivery became `answered`.
4. The reply woke A, which answered `GOT 391`; A then closed its delivery with `skip`.
5. Stopping both sessions ended both `irori attach` children.
6. The GUI's Inbox tab showed both messages with their final states.

**Grok path through `irori mcp`.** Two `irori mcp` processes over real pipes against the running GUI's Core: both declare `experimental["claude/channel"]`, both `irori_join`, one `irori_send`s to the other, and the other receives one `notifications/claude/channel` push with meta `delivery_id`, `delivery_ids`, `message_id`, `from`, `trust` and a fenced `<irori-message>` body; `irori_reply` marks it answered.

**Mod findings (from the mod package's own live checks).**
- `$.http.fetch` to 127.0.0.1 sends no `Origin` header, and `authorization` arrives as given.
- `$.prompt.submit` during a running turn is queued, not rejected; its promise resolves when its own turn starts.
- `$.tool.register` after `session.start` has returned works.

**Not covered.** A real Grok (`grok-fork --channels`) session; Code-tab (desktop) sessions; macOS.
